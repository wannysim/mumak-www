A note to keep in the [[digital-garden-expansion-plan|digital garden]].
This is less of a plain wine logging app and more of an _interactive coach that makes the wine-drinking experience feel more premium and delightful_.

## One-line definition

An app that records wine tasting through _touch only_ with minimal effort, while making the user's world map and taste profile gradually fill in and become clearer over time.

## Core concept

- Free-text input is not the main path.
- The user mostly taps buttons, chips, sliders, and swipes.
- The app gradually opens up more precise choices and nudges the user into deeper tasting.
- At the same time, it accumulates the **winery / region / country** of each wine on maps.
- Every new wine should make the maps feel a little more filled in.

## Map-based experience

The fun is not just in logging _what_ was drunk, but in seeing _where_ the wines came from.

### 1) World map

- Shows the country and continent of each winery.
- Coverage expands country by country.
- New regions should feel visually rewarding.

### 2) Country / region map

- France can zoom into Bordeaux, Burgundy, Rhône, and so on.
- Italy can show Piedmont, Tuscany, etc.
- The color density makes it easy to see which regions the user drinks most often.

### 3) Personal taste map

- This does not have to be a literal geographic map.
- It can be a coverage view of countries, grape varieties, and styles the user tends to drink.
- Example dimensions: Old World vs New World, acidity-led vs body-led, red vs white.

## What we have so far

- This app is meant to make the wine-drinking experience feel more premium and delightful.
- Tasting notes should be captured through _touch_ rather than long natural-language input.
- As entries accumulate, the world map, region map, and taste map become more complete.
- Mobile and web should feel like the same product, delivered through one webapp / webview-style experience.
- Because UI/UX matters a lot here, the project needs help from product and design-oriented workflows.

## UX direction

### Step 1: the big shape of the sensation

Start with something very simple.

- Light / medium / full-bodied
- Fresh / balanced / rich
- Fruit / flower / herb / wood / spice

### Step 2: go deeper based on the choice

If the user taps _fruit_, the next screen can narrow it down to:

- Citrus
- Apple / pear
- Berries
- Ripe fruit

If the user taps _high acidity_, the next screen can become:

- Sharp acidity
- Lively acidity
- Bright acidity

In other words, it starts with easy words and then moves into more precise tasting language.

### Step 3: the app summarizes

At the end, the app can turn the taps into:

- A tasting note summary
- Similar wine recommendations
- An updated taste profile
- A colored winery / region map

## Product spec draft

### Core user flow

1. Log a wine.
2. The app fetches or accepts the wine metadata.
3. It asks one tasting question at a time.
4. The user answers with taps.
5. The tasting note is saved.
6. The three map views update together.

### Required data fields

- Wine name
- Producer / winery
- Country
- Region / subregion
- Grape variety
- Vintage
- Tasting tags
- User rating
- Drinking date

### MVP

- Add wine entry
- Auto-map winery location
- Show three map views: world / region / taste coverage
- Touch-based tasting question flow
- Entry list
- Personal stats

### Later additions

- Blind tasting mode
- Label photo OCR
- Compare with friends
- Link wine history to travel history
- Taste-profile recommendations

## Screen notes

- One question per screen
- Big buttons, 3–6 choices
- The selected trail stays visible at the top
- The next question becomes more precise over time
- The map should stay visible in a separate tab or a persistent lower area

## Webapp / mobile implementation direction

- Build it as **one webapp** so mobile and web behave the same.
- Mobile should be handled with **webview / PWA / responsive web**, not a separate native app.
- Map interactions must work the same with touch and click.
- By screen size:
  - Mobile: prioritize the question flow, keep maps collapsed or tabbed
  - Web: show map and form side by side when possible
- It would be best to use the same state machine and the same data model everywhere.

## Open questions

- How should the three maps be divided — country / region / taste, or something else?
- Should winery coordinates come from an automatic dataset or manual correction?
- Should map coloring be based on drinking count or on discovering new regions?
- Where should we split beginner-friendly language from expert language?
- Should there be a blind tasting mode?
- When should the app start showing taste-profile insights?
- Should label/photo input be a secondary feature or an early core feature?
