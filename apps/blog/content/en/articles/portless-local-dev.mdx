As a monorepo gains more apps, one thing tends to grow with it.

Port numbers.

At first, it is not a big problem. But over time, it gets annoying. Another app appears, E2E needs a separate server, preview and dev servers become different paths, and one day a server is already running so the port gets pushed elsewhere.

Browser history starts filling up with port numbers.

```text
http://localhost:3000
http://localhost:3001
http://localhost:3002
http://localhost:3003
```

The numbers have no meaning.
Only the unfortunate person who has to remember them does.

The reason I added `portless` was simple. I just did not want to think about port numbers anymore when opening local apps.
But once I applied it, there were a few things I had to consider. This post records what Portless does and the troubleshooting I ran into while adopting it.

## 1. What Portless does

[Portless](https://portless.sh) is a tool that puts a small proxy in front of local dev servers and gives each app a name-based URL.

Before, I accessed apps like this.

```text
http://localhost:3000
http://localhost:3001
http://localhost:3002
```

With Portless, I can access them like this.

```text
http://next.mumak.localhost:1355
http://react.mumak.localhost:1355
http://blog.mumak.localhost:1355
```

At first glance, it looks like Portless just replaces port numbers with names, but there is another layer.
The Portless proxy receives requests through a shared entry point such as `1355`, reads the `Host` header, and forwards the request to the actual dev server.

```text
blog.mumak.localhost:1355  ->  localhost:4070
next.mumak.localhost:1355  ->  localhost:4211
```

The browser uses a name-based URL, but each app still runs on an internal temporary port.
Portless manages that mapping.

That is also why `:1355` appears in the URL.
Since this repo runs the proxy on port 1355, the browser address needs that port too.
If the proxy runs on HTTP's default port 80, the port can be omitted as in `http://blog.mumak.localhost`. If it runs on HTTPS's default port 443, `https://blog.mumak.localhost` is also possible.

But ports 80 and 443 usually involve administrator privileges or a certificate trust flow.
For this repo, I chose the path that does not involve sudo or certificate setup when starting local development, so `:1355` is explicit.

## 2. Why it helps this repo

This repo has several web apps.

- `apps/mumak-next`
- `apps/mumak-react`
- `apps/blog`
- `apps/mumak-native`

Each app has a different dev server and a different E2E server.
Next uses `next dev`, Vite uses `vite`, the blog uses a standalone-based E2E server, and native serves the Expo web export.

In a setup like this, if port numbers start acting like app identities, things get confusing quickly.

```text
3000: mumak-next dev / e2e
3001: mumak-react dev / preview
3002: blog dev / e2e
3002: mumak-native / e2e
```

While applying this, I noticed again that `blog` and `mumak-native` were both using 3002 for E2E.
In CI, the matrix is separated by app, so it may not be an immediate problem. But locally, if I change the order, reuse a server, or check multiple apps at the same time, a shared port always becomes something to care about.

So I split the roles.

```text
local dev:
  use Portless name-based URLs

E2E/CI verification:
  keep fixed ports per app
```

And I made the E2E ports stop overlapping.

```text
mumak-next:   3000
mumak-react:  3001
blog:         3002
mumak-native: 3003
```

Now local development no longer requires looking at port numbers.
On the other hand, E2E keeps explicit fixed ports.

I think this boundary matters.
Portless is a tool that improves the development experience, not a tool that should blur the port model of the test infrastructure.

## 3. The setup was simple, but it did not work as-is

At first, I thought changing each app's dev script would be enough.

```json
{
  "dev": "portless"
}
```

But in practice, there were a few things to step through.

### 3-1. Default HTTPS/443 asks for sudo

Portless can use HTTPS and port 443 by default.
The problem is that 443 is a privileged port, so a sudo prompt appears locally.

Having sudo involved every time I start a dev server is too much friction for this repo's normal development flow.
So I chose to run a local proxy over HTTP on a separate port.

```json
{
  "dev": "PORTLESS_PORT=1355 PORTLESS_HTTPS=0 portless run --name next.mumak next dev"
}
```

This makes the URL a bit longer.

```text
http://next.mumak.localhost:1355
```

But it starts reliably without sudo.
Here, I cared more about repeatable execution than a pretty URL.

### 3-2. Wrapping the script once more can break port injection

At first, I tried to keep another app-level script like this.

```json
{
  "dev": "portless run --name react.mumak pnpm dev:app",
  "dev:app": "vite"
}
```

But Vite did not receive the internal port assigned by Portless.
The proxy was running, but the actual app was on a different port, so I got a 502.

The answer was simpler.

```json
{
  "dev": "PORTLESS_PORT=1355 PORTLESS_HTTPS=0 portless run --name react.mumak vite"
}
```

Portless needs to inject the port directly into the framework command.
For Vite, values such as `--port`, `--strictPort`, and `--host 127.0.0.1` are attached internally.

If an extra wrapper such as `pnpm dev:app` sits in the middle, that injection path can become unclear.
That was the first thing I learned while applying it.

### 3-3. Dev ports and E2E ports should not be mixed

For a moment, I wondered, "Should E2E also access apps through Portless?"
I quickly dropped the idea.

E2E is not a developer experience path. It is a verification environment.
A verification environment needs reproducibility more than pretty URLs.

Playwright's `webServer` should know exactly which command starts each app and which URL it should wait for.
So only the `dev` script moved to Portless, and E2E-related scripts kept fixed ports.

```json
{
  "dev": "PORTLESS_PORT=1355 PORTLESS_HTTPS=0 portless run --name blog.mumak next dev",
  "start:e2e": "node scripts/start-e2e.mjs",
  "test:e2e": "playwright test"
}
```

That principle made CI verification relatively clear.

- `mumak-next` uses `next start` on 3000
- `mumak-react` uses `vite preview` on 3001
- `blog` uses the standalone server on 3002
- `mumak-native` serves the Expo web export on 3003

Portless changes the entry point for local dev, and E2E/CI verification keeps the explicit port contract as before.

### 3-4. Next dev checks the origin

When I opened the blog through `blog.mumak.localhost`, I first saw this warning.

```text
Blocked cross-origin request to Next.js dev resource /_next/webpack-hmr from "blog.mumak.localhost".
```

Next dev server does not let any origin call its internal development resources and endpoints.
If the server starts as `localhost` but the browser accesses it through `blog.mumak.localhost`, Next sees it as a different development origin requesting an internal dev resource.

The fix was to explicitly list the development origin in `next.config`.

```js
const nextConfig = {
  allowedDevOrigins: ['blog.mumak.localhost'],
};
```

For the same reason, I added `next.mumak.localhost` to `mumak-next`.

## 4. What I verified after applying it

This kind of change should not end with a few package script edits.
This repo also runs E2E in GitHub Actions.
If local dev gets nicer but CI becomes unstable, the change is not worth it.

So I checked two paths.

The first was a Portless dev smoke test.

```text
http://react.mumak.localhost:1355
http://next.mumak.localhost:1355
```

Both apps returned 200 through the Portless proxy.
Vite and Next were running on internal ports assigned by Portless, while the outside used name-based URLs.

The second was E2E in the same style as CI.

```text
mumak-next:   chromium/firefox/webkit passed
mumak-react:  chromium/firefox/webkit passed
blog:         chromium/firefox/webkit passed
mumak-native: chromium/firefox/webkit passed
```

The important part was not that "the tests passed," but "which server they passed through."
The E2E logs showed fixed servers per app, not Portless.

```text
next start --port 3000
vite preview --port 3001
node scripts/start-e2e.mjs        # blog, 3002
serve dist --listen 3003          # mumak-native
```

Only after checking that could I feel comfortable.
It meant the Portless change had not invaded the CI path.

## 5. Extra insight from applying it

After adding Portless, saying "the app is broken" is too vague and can hide the actual cause.
In this setup, I had to separate two layers.

First, is the proxy route alive?
At one point, the internal Next dev server returned 200, but `blog.mumak.localhost:1355` returned a Portless 404.
In that case, the thing to check is not app code but the Portless route registration state.

```text
pnpm exec portless list
pnpm exec portless proxy stop
```

If `list` has no route but the proxy is still running, restarting the app is the first thing to do.
I also saw a state that looked like a stale lock, and stopping the proxy before restarting made the route register correctly.

Second, is the Next dev resource allowed?
A Portless URL looks like a simple alias, but to the browser and the Next dev server, the origin has changed.
That is why Next apps also need `allowedDevOrigins`.

Once I separated those two layers, the debugging order became clearer.

```text
1. Is the Portless route registered?
2. Are Next dev resources connected without origin blocking?
```

Portless hides ports, but it does not hide the layers involved in a problem.
Because the URL has one more abstraction, proxy and framework dev resources need to be checked more deliberately.

## 6. The main point of this change was the boundary, not the port

The first goal was to remember fewer port numbers.

But what I actually got was slightly different.

In local development, humans use readable names.
In E2E/CI verification, machines use reproducible fixed ports.

Not mixing the two was the core point.

```text
dev:
  http://next.mumak.localhost:1355
  http://react.mumak.localhost:1355
  http://blog.mumak.localhost:1355
  http://native.mumak.localhost:1355

e2e/ci:
  3000, 3001, 3002, 3003
```

The address a developer sees should have meaning.
The address a test sees should be stable.

Portless became a good reason to separate those two.

## Checklist

If I were adding Portless to another monorepo with a similar shape, I would check roughly this list.

- [ ] Does each app have a unique `--name`?
- [ ] Is the proxy port explicit so local dev does not trigger a sudo prompt?
- [ ] Does `portless run` wrap the framework command directly?
- [ ] Are old fixed ports removed from `dev` scripts?
- [ ] Are `start:e2e`, `preview:e2e`, and Playwright `webServer` separated from Portless?
- [ ] For Next apps, is the Portless hostname added to `allowedDevOrigins`?
- [ ] Did I verify both a Portless proxy smoke test and E2E in the same style as CI?
- [ ] When a problem occurs, did I check the proxy route and framework dev resource separately?

Adding a tool can look small.
But adopting a good tool does not end with "adding a few commands."

It matters more to draw the line between what the tool is responsible for and where the existing system should take over.
This Portless adoption was ultimately about drawing that line again.
