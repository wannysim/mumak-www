내가 만든 퀀트 시스템은 AI가 매번 매수와 매도를 결정하는 구조가 아니다. AI는 전략을 연구하고 운영 문제를 분석한다. 확정된 규칙에 따라 데이터를 수집하고, 수량을 계산하고, 위험 조건을 검사하고, 장부를 기록하는 일은 일반 코드가 맡는다.

2026년 9월 21일 구축 기록을 기준으로 현재 단계는 미국 시장의 실제 시세를 이용한 모의운용이다. 실거래와 모의를 병행하는 연결 기능도 구현했지만, 실계좌 가동은 별도 검증과 승인 전까지 닫아 두었다. 이 글은 투자 성과 소개보다, 그 시스템 안에서 사람과 에이전트가 어떻게 일을 나눴는지에 관한 기록이다.

## 시작은 역할보다 반복 작업의 구분이었다

평일마다 돌아갈 시스템의 모든 작업에 깊은 추론 모델을 호출하면 사용량이 부담스러울 것 같았다. 그렇다고 중요한 전략 검토까지 전부 같은 수준의 추론으로 처리하고 싶지는 않았다. 모델별 실제 비용 차이를 확정하기보다, 작업에 맞게 호출 범위와 추론 수준을 나누는 데서 시작했다.

처음 생각한 분업은 단순했다. 깊은 연구는 Astra, 운영 작업은 Sol, 자료 정리는 Luna가 맡으면 되지 않을까. 그런데 모델을 배정하기 전에 먼저 구분해야 할 일이 있었다. **애초에 모델이 필요하지 않은 작업**이다.

이미 정의된 수익률 계산, 포지션 수량 계산, 장부 갱신을 자연어 추론에 맡길 이유는 없다. 이런 작업은 규칙을 코드로 작성하고 입력과 결과를 확인할 수 있어야 한다. 일일보고 역시 장부의 값을 정해진 형식에 넣는다면 모델 없이 생성할 수 있다.

그래서 정상적인 반복 운용은 코드로 유지하고, 해석과 판단이 필요한 작업에만 모델을 호출하도록 나눴다. 모델 비용을 줄이기 위한 선택이면서, 같은 규칙을 계속 적용하고 문제를 추적하기 위한 선택이기도 했다.

## 전체 구조: 연구와 실행 사이에 검증을 둔다

```text
사용자: 투자 목표·자금·위험 한도·최종 승인
  │
  ▼
Hermes의 주 대화: 작업 분해·역할 선택·결과 검증
  ├─ Astra: 전략 가설·편향·위험 검토
  ├─ Sol: 운영 예외 분석·범위가 정해진 작업
  └─ Luna: 제공 자료의 사실·출처·날짜 정리
  │
  ▼
검증·승인 후 확정한 전략과 설정
  │
  ▼
일반 코드: 수집 → 신호·수량 계산 → 위험 검사
  │
  ▼
현재 모의체결 → 장부·평가 → 일일보고
  │
  └─ 관측 결과를 다음 연구와 월말 검토에 사용
```

이 그림은 논리적인 역할을 나타낸다. AI 세 개가 각각 증권 계좌를 들고 있거나, 별도 서버에서 계속 대화하는 구조는 아니다. 역할 분리를 위해 새로운 증권 연결이나 금융 자격증명을 만들지도 않았다.

Hermes는 대화, 하위 작업 위임, 예약 실행과 결과 전달을 담당한다. 실제 금융 실행 경로는 기존 통합 실행부 하나로 유지한다. 에이전트를 늘린다고 주문 권한까지 복제하지 않는다는 원칙이다.

## Astra: 전략을 더 엄격하게 의심하는 역할

Astra는 전략 가설, 실험 설계, 편향과 과최적화, 중요한 위험 판단을 맡는다. 연구용 주 대화도 Astra로 유지했다.

전략 연구의 목표는 좋은 수익을 찾는 것이지만, 검토할 때는 수익률만 보지 않는다. 특정 기간에만 유리했던 규칙인지, 당시 알 수 없었던 정보를 사용했는지, 비용을 반영하면 결과가 달라지는지 따져야 한다. 짧은 모의운용의 좋은 결과를 장기적인 우위로 해석하는 것도 경계한다.

Astra의 산출물은 가설과 근거, 실험 제안, 불확실성이다. 자연어 답변 자체가 운영 정책은 아니다. 전략을 바꾸려면 검증과 확정 절차를 거쳐야 하고, 실거래 전환에는 사용자의 별도 승인이 필요하다.

## Sol: 승인된 범위에서 운영 문제를 좁히는 역할

Sol은 범위가 명확한 위임 작업과 운영 예외 분석을 맡는다. 예를 들어 수집 실패의 로그를 읽고, 원인이 데이터 제공처인지 입력 형식인지 구분하며, 안전한 다음 점검을 제안하는 일이다.

여기서 운영 담당이라는 말은 주문 담당이라는 뜻이 아니다. 정해진 매매는 실행 코드가 수행한다. 역할 실행기로 호출한 Sol은 금융 실행기, 정책, 원본 장부를 직접 수정하지 않는 규칙을 따른다. 코드 수정이 필요하면 별도 작업 사본에서 수행하고, 상위 담당자가 결과와 테스트를 확인한 뒤 반영한다.

기본 하위 위임 모델도 Sol로 지정했다. 다만 오류가 생기면 Sol이 자동으로 출동해 무제한 복구하는 구조는 아니다. 기존의 오류 알림을 받고, 상위 담당자가 필요한 작업을 골라 위임한다.

## Luna: 판단 재료를 정리하는 역할

Luna는 제공된 문서에서 사실, 출처, 날짜와 불확실성을 정리한다. 문서에 없는 숫자를 채우거나, 정리한 사실을 곧바로 투자 추천으로 바꾸지 않도록 범위를 제한했다. 세션 제목 생성 같은 보조 작업에도 Luna를 사용한다.

예를 들어 발표문에 매출이 늘었다고만 적혀 있다면, 증가율을 추정해서 넣지 않는다. 출처가 말한 것과 아직 모르는 것을 구분한 짧은 요약이 다음 판단의 입력이 된다.

Luna를 사용한다는 이유만으로 모든 데이터를 모델에 통과시키지는 않는다. CSV 정렬이나 손익 집계처럼 규칙이 명확한 처리는 계속 코드가 맡는다.

## 에이전트는 어떻게 일을 주고받나

현재의 협업 방식은 주 대화가 중심에 있는 작업 위임 방식이다. 전체 대화를 모든 에이전트에게 복사하지 않고, 수행할 일과 필요한 자료만 전달한다.

로컬 역할 실행기는 `research`, `operations`, `organize` 중 하나를 선택하면 모델과 도구 범위, 시간과 턴 제한을 고정해 새로운 CLI 세션을 연다. 기본 하위 위임은 Sol을 사용하고, Astra나 Luna가 필요한 작업은 명시적으로 해당 역할 경로를 선택한다. 기본 위임 호출 하나가 매번 세 모델 중 하나를 자동 분류하는 것은 아니다.

프롬프트에서는 수행할 명령과 참고 자료를 구분한다. 참고 문서 안에 명령처럼 보이는 문장이 있어도, 그것을 위임받은 작업으로 취급하지 않게 한다. 역할 실행기는 결과와 오류 출력, 종료 상태, 요청한 모델 등의 실행 기록을 저장한다.

전달 내용을 이해하기 쉽게 풀면 다음과 같다. 아래는 설명용 예시이며 실제 장애 기록이나 강제된 메시지 스키마는 아니다.

```text
상위 담당자 → Sol
  작업: 시세 수집 실패의 원인을 좁힐 것
  자료: 관련 오류 로그와 입력 형식
  금지: 원본 장부·전략·금융 실행부 변경
  요청 결과: 확인한 사실, 미확인 원인, 다음 점검

Sol → 상위 담당자
  관측한 사실과 가능한 원인을 구분해 반환
  실행한 점검이 있다면 결과와 한계를 함께 반환

상위 담당자
  실제 로그·파일·테스트로 답변을 대조
  수정이 필요하면 승인 범위 안에서 별도로 진행
```

연구 작업도 같은 원칙을 따른다. 필요하면 Luna가 자료를 정리하고 Astra가 그 자료를 검토할 수 있지만, 매일 Luna → Sol → Astra를 순서대로 부르는 자동 파이프라인을 만든 것은 아니다. 역할 프롬프트는 추가 모델 호출을 금지하며, 실행기에는 실패 시 상위 모델로 자동 전환하는 경로를 두지 않았다. 프롬프트의 금지 지시 자체가 프로세스 수준의 차단을 뜻하지는 않는다.

**프로세스가 정상 종료됐다는 사실과 작업이 올바르게 끝났다는 사실은 다르다.** 하위 에이전트가 테스트를 통과했다고 답하면 실제 실행 결과를 확인한다. 요청한 모델로 처리됐는지도 실행 영수증만 믿지 않고 세션·사용량 기록과 대조한다.

도구 목록과 프롬프트 제한은 OS 수준의 보안 격리가 아니다. 특히 파일과 터미널을 사용할 수 있는 역할은 신뢰된 로컬 작업자라는 전제에 서 있다. 역할 이름을 나눴다고 강한 보안 경계가 생겼다고 설명해서는 안 된다.

## 시장이 열릴 때 돌아가는 것은 코드다

현재 모의운용의 수집, 확정 전략 계산, 위험 검사, 장부 기록과 정형 일일보고는 `no_agent` 예약 작업으로 실행한다. 예약된 일반 프로그램을 돌리며, 이 반복 경로에서 LLM을 호출하지 않는다는 뜻이다. 개발, 연구, 예외 분석이나 월말 해석에 드는 모델 사용량까지 없어진 것은 아니다.

거래일과 거래시간을 확인하고, 데이터를 수집해 정해진 규칙을 적용한다. 현재 시험하는 것은 저빈도 추세 전략이므로 매일 반드시 거래할 필요는 없다. 거래가 없었던 날, 데이터가 부족했던 날, 실행이 실패한 날을 구분해 기록하는 것도 운용의 일부다.

결과는 장부에 남기고 오전 9시 한국어 일일보고로 묶는다. 일반적인 체결마다 밤새 메시지를 보내는 대신, 긴급한 안전 문제나 실패는 별도로 알리도록 구성했다. 예약과 로컬 실행을 검증한 사실이 앞으로의 모든 전송 성공을 보장하지는 않는다.

월말에는 그 기록을 해석한다. 수익과 손실뿐 아니라 비용, 위험, 의사결정의 질과 다음 실험을 검토한다. 중간 결산은 Sol, 최종 전략 결산은 Astra에 배정했다. 월말 보고가 다음 달의 자동 실거래 시작 신호는 아니다.

## 모의운용도 목적에 따라 나눴다

모의라는 이름 아래 다른 목적을 섞으면 결과를 오해하기 쉽다. 이 시스템에서는 다음을 구분한다.

- 현재의 전진 모의운용은 실제로 시간이 흐르는 시장에서 전략과 운영 과정을 관측한다. 자금과 체결은 가상이다.
- 같은 전략의 그림자 모의는 향후 실거래와 동일한 전략 결정을 받아 독립적으로 체결과 장부를 계산한다. 체결 조건과 비용 때문에 두 경로가 얼마나 달라지는지 비교하기 위한 기능이다.
- 대안 전략 실험은 일부 규칙을 바꾼 전략을 별도 장부에서 시험한다. 실행 차이가 아니라 전략 차이를 보는 실험이다.

실거래와 그림자 모의가 공유하는 것은 버전이 고정된 전략 결정과 데이터 계약이다. 자금, 체결, 장부와 중지 상태는 분리한다. 실거래 체결을 모의 장부에 복사해서 두 결과를 같게 만들지 않는다. 대안 전략의 성과가 좋다고 자동으로 운영 전략에 올리지도 않는다.

병행운용 연결 기능은 구현·설치하고 격리된 환경에서 검증했다. 기존에 실행 중인 금융 프로세스가 새 모듈을 로드하고 해당 도구를 사용하도록 연결됐는지는 아직 검증하지 않았다. 실제 계좌 기준잔고, 비용과 정산 근거, 운영 데이터 공급을 맞추기 전에는 실거래 비교를 대기로 둔다. 과거 데이터를 다시 실행한 결과를 새로운 전진 운용 성과로 합산하지 않는다.

## 토큰 비용에도 한계와 검증이 필요하다

현재 설정에서는 역할 실행의 시간·턴 수를 제한하고, 기본 하위 위임의 동시성을 두 개로 제한했다. 필요한 자료만 전달하고, 실패했다고 자동으로 상위 모델로 올리지 않는다. 제목 생성처럼 눈에 잘 띄지 않는 보조 호출도 사용량 확인 대상에 넣었다.

하지만 이것은 하루 토큰 수나 요금을 강제로 차단하는 예산 시스템은 아니다. 모델별 구독 한도 가중치와 실제 절감률도 아직 검증하지 않았다. 지금 말할 수 있는 것은 반복 운용에서 모델 호출을 제외했고, AI가 필요한 작업의 범위를 좁혔다는 것까지다.

## 지금 확인한 것과 앞으로 확인할 것

구축 기록에서는 세 역할의 실제 모델 호출, Sol 기본 위임, 설정과 예약의 보존을 확인했다. 모의·실거래 연결부는 오프라인 테스트와 설치 검증을 거쳤다. 이 검증들은 역할 배정과 소프트웨어 경로가 동작한다는 근거다.

실계좌에서의 성과나 수익성을 증명하는 근거는 아니다. 실거래 활성화는 하지 않았고, 실제 자본과 최종 전략, 계좌 기준을 확정한 뒤 별도의 운영 검증이 필요하다. 짧은 모의운용으로 장기 수익을 결론낼 수도 없다.

다음 판단은 기능을 얼마나 더 붙일지보다 모의운용에서 무엇을 배웠는지에 달려 있다. 데이터 누락이나 재시작 뒤에도 기록이 일관적인지, 비용을 반영한 결과를 설명할 수 있는지, 전략을 유지하거나 바꿀 근거가 있는지 확인하려 한다.

이 시스템에서 AI에게 맡긴 것은 연구와 해석의 일부다. 반복 실행은 코드에 두고, 변경에는 검증을 두고, 투자 방향과 실거래 전환의 책임은 사람이 갖는다. 에이전트 수보다 각 역할이 끝나는 지점을 명확히 하는 데 더 많은 주의를 기울였다.
