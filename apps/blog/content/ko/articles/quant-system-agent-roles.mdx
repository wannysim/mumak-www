최근 Hermes를 이용해 퀀트 투자 시스템을 만들고 있다. 투자 규칙을 정하고, 시장 데이터를 받아 그 규칙대로 운용한 뒤, 결과를 보면서 다음 전략을 고민하는 시스템이다. 지금은 미국 시장의 실제 시세와 가상 자금으로 모의운용 중이다.

만들면서 꽤 신경 쓴 부분은 AI에게 어떤 일을 맡길지였다. 전략 연구부터 매일의 계산까지 전부 한 모델이 처리할 필요는 없었다. 그래서 Astra는 연구, Sol은 운영 보조, Luna는 자료 정리를 맡기고, 반복되는 운용은 코드로 분리했다.

## 매번 AI에게 물어볼 필요는 없었다

평일마다 돌아갈 시스템이다 보니 모델 사용량이 신경 쓰였다. 깊게 생각해야 하는 전략 검토에는 충분한 추론을 쓰고 싶지만, 이미 정해진 수익률 계산이나 장부 갱신까지 매번 모델을 부를 이유는 없었다.

먼저 일을 두 종류로 나눴다.

- 가설을 세우고, 결과를 해석하고, 문제의 원인을 찾는 일은 AI가 돕는다.
- 정해진 규칙으로 데이터를 처리하고, 수량을 계산하고, 기록을 남기는 일은 코드가 한다.

일일보고도 마찬가지다. 장부에 있는 값을 정해진 형식에 넣는 작업이라면 일반 프로그램으로 충분하다. 모델은 그 결과를 읽고 다음에 무엇을 바꿀지 고민할 때 사용한다.

## 전체 구조는 이렇게 생겼다

```text
나: 투자 방향과 운용 기준 결정
  │
  ▼
Hermes: 작업을 나누고 결과를 모으는 창구
  ├─ Astra: 전략 연구·중요 판단
  ├─ Sol: 운영 점검·문제 분석
  └─ Luna: 자료 정리
  │
  ▼
검토를 마친 전략과 규칙
  │
  ▼
코드: 시세 수집 → 신호·수량 계산 → 위험 검사
  │
  ▼
모의체결 → 장부 기록 → 일일보고
  │
  └─ 결과를 다음 연구에 활용
```

나는 Telegram에서 Hermes와 대화하며 방향을 정한다. Hermes는 필요한 작업을 나누고, 적절한 역할에 맡기고, 결과를 다시 모은다. 정해진 시간에 프로그램을 실행하고 보고를 전달하는 것도 Hermes가 담당한다.

세 역할은 각각 별도의 투자 봇이라기보다, 같은 시스템에서 필요할 때 불러 쓰는 담당자에 가깝다. 계좌 연결과 주문 경로는 기존 실행부 하나로 유지했다.

## 에이전트마다 맡긴 일

### Astra는 전략을 연구한다

Astra는 투자 아이디어와 실험 설계, 결과 해석을 맡는다. 연구용 주 대화에도 Astra를 사용한다.

수익률이 좋아 보이는 전략을 찾았더라도 특정 기간에만 잘 맞았던 것은 아닌지, 거래 비용을 넣으면 결과가 달라지는지 따져보는 역할이다. 어떤 전략을 더 시험할지, 무엇을 바꿔볼지처럼 생각이 많이 필요한 일에 집중시켰다.

### Sol은 운영을 돕는다

Sol은 범위가 분명한 작업과 운영 문제 분석을 맡는다. 시세 수집이 실패했다면 관련 로그를 읽고 원인을 좁히거나, 코드 수정이 필요할 때 작업 사본에서 수정하고 테스트하는 식이다. 기본 하위 위임 모델도 Sol로 지정했다.

매매할 때마다 Sol이 판단하는 것은 아니다. 매매 규칙은 코드가 실행하고, Sol은 점검이 필요할 때 호출한다. 원본 장부나 운용 규칙을 마음대로 바꾸는 대신, 작업 결과를 주 대화로 돌려주고 확인을 거쳐 반영한다.

### Luna는 자료를 정리한다

Luna는 제공된 문서의 사실, 출처, 날짜를 정리한다. 긴 자료를 다음 판단에 쓸 수 있는 짧은 형태로 만드는 역할이다.

예를 들어 발표문에 매출이 늘었다고만 적혀 있다면, 증가율을 추측하기보다 확인되는 내용만 정리한다. 세션 제목 같은 작은 보조 작업도 맡겼다. 반면 CSV 정렬이나 손익 집계는 굳이 모델을 쓰지 않고 코드로 처리한다.

## 서로 어떻게 일을 주고받나

협업의 중심은 주 대화다. 모든 에이전트가 전체 대화를 공유하며 계속 토론하는 방식은 아니다. 필요한 역할을 골라 작업 목적과 관련 자료만 전달한다.

가령 시세 수집에 문제가 생겼다면 이런 식으로 일을 나눌 수 있다.

```text
주 대화 → Sol
  "이 로그를 보고 수집 실패의 원인을 좁혀줘.
   장부는 건드리지 말고, 다음 점검을 제안해줘."

Sol → 주 대화
  확인한 사실, 가능한 원인, 점검 결과를 반환

주 대화
  실제 로그와 테스트를 확인한 뒤 다음 작업 결정
```

연구에서는 Luna가 정리한 자료를 Astra의 검토에 활용할 수도 있다. 다만 매일 세 모델을 차례로 호출하는 흐름을 만든 것은 아니다. 그때 필요한 작업만 맡긴다.

역할별로 사용할 도구와 시간·턴 수를 정해 두었고, 결과와 실행 기록도 남긴다. 에이전트가 "완료했다"고 답하는 것만으로 끝내지 않고 파일이나 테스트 결과를 확인한다. 이렇게 해야 다음 담당자가 무엇을 믿고 이어서 작업할지 분명해진다.

## 하루의 운용과 다음 연구를 연결하기

시장이 열릴 때 반복해서 돌아가는 것은 일반 코드다. 거래일과 시간을 확인하고, 시세를 받아 정해진 전략으로 신호와 수량을 계산한다. 위험 조건을 확인한 뒤 모의체결과 장부 기록으로 이어진다. 이 과정과 정형 일일보고는 LLM을 부르지 않는 `no_agent` 예약 작업으로 구성했다.

현재 시험하는 것은 저빈도 추세 전략이라 매일 거래할 필요는 없다. 거래하지 않은 날도 기록하고, 결과는 한국 시간 오전 9시 보고로 묶도록 했다. 미국장이 열리는 동안 잠들어 있는 경우가 많아서, 일반 체결 알림은 모으고 긴급한 문제만 따로 받는 방식을 골랐다.

월말에는 쌓인 기록을 놓고 전략을 다시 살펴본다. 중간 결산은 Sol, 최종 전략 검토는 Astra에 맡기도록 배정했다. 손익뿐 아니라 비용이나 운영 중 겪은 문제를 함께 보고 다음 실험을 정하는 흐름이다.

모의운용도 목적을 나눴다. 지금의 모의운용은 현재 전략을 관측하는 데 쓰고, 다른 규칙을 시험하는 실험은 별도 장부에 둔다. 나중에 실거래를 시작하면 같은 전략을 독립적인 모의 경로에도 적용해 체결과 비용 차이를 비교할 수 있도록 연결 기능을 만들어 두었다. 아직 실거래는 켜지 않았다.

당장은 모델을 더 붙이기보다 이 흐름을 꾸준히 돌려보려 한다. 반복 작업은 코드가 맡고, AI는 연구와 문제 해결에 집중하고, 나는 결과를 보면서 다음 방향을 정한다. 혼자 만드는 시스템이지만 모든 일을 한꺼번에 붙잡지 않도록 역할을 나눈 셈이다.
