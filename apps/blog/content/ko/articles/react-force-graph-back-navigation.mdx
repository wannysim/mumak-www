이 블로그에는 글들을 노드로 잇는 [3D 그래프 페이지](/ko/graph)가 있다.
`react-force-graph-3d`로 만들었는데, 어느 날 이상한 제보를 받았다.

> 그래프를 한 번 보고, 다른 글로 갔다가, **브라우저 뒤로가기로 그래프로 돌아오면** 그래프는 그대로 보이는데 드래그도 줌도 노드 클릭도 안 돼요.

새로고침하면 멀쩡하다. 뒤로가기로 돌아왔을 때만 죽는다.
"보이는데 안 만져지는" 이 증상이 결국 React 외부 라이브러리 wrapper의 lifecycle 한 줄까지 내려가는 추적으로 이어졌다.

## 1. 증상부터 정확히

먼저 재현 조건을 좁혔다.

1. `/ko/graph`에 들어간다. 그래프가 뜨고 드래그/줌/클릭이 다 된다.
2. 글 하나로 client-side navigation한다.
3. 브라우저 **뒤로가기**로 그래프로 돌아온다.
4. 캔버스는 다시 보이지만 어떤 인터랙션도 먹지 않는다.

핵심은 두 가지였다.

- **새로고침(full reload)으로 진입하면 멀쩡하다.** 즉 SSR/초기 마운트 경로엔 문제가 없다.
- **client-side로 떠났다가 history로 돌아오는 경로에서만** 죽는다.

우리 그래프 페이지의 뒤로가기 버튼은 history가 있으면 `router.back()`을 부른다.

```tsx
const hasHistory = window.history.length > 1 && document.referrer !== '';
if (hasHistory) {
  router.back();
} else {
  router.push(`/${locale}`);
}
```

그래서 사용자는 "떠났다가 history로 되돌아오는" 경로를 평소에 자주 밟는다.
재현이 어쩌다 한 번이 아니라 정상 동선이었다는 뜻이다.

## 2. 의심 가는 곳을 한 겹씩

캔버스 DOM은 멀쩡히 거기 있는데 조작만 죽는다. 그러면 의심 순서가 정해진다.
DOM은 다시 그려졌지만 **그 위에 붙어 있어야 할 컨트롤러/렌더러/이벤트 리스너가 다시 살아나지 않았다**는 가설이다.

쌓인 레이어를 위에서 아래로 적으면 이렇다.

1. `react-force-graph-3d` -- React 컴포넌트 wrapper
2. `react-kapsule` -- kapsule 인스턴스의 생명주기를 React 생명주기에 연결하는 어댑터
3. `3d-force-graph` / `three-render-objects` -- 실제 Three.js 씬·컨트롤·렌더러

새로고침하면 멀쩡하다는 건, 처음부터 마운트되는 경로의 초기화 코드는 정상이라는 뜻이다.
그러니 문제는 "정상 초기화"가 아니라 **"언마운트 후 다시 마운트될 때 초기화가 한 번 더 일어나야 하는데 안 일어나는" 경로**에 있다.

여기서 Next.js App Router의 동작과 React Strict Mode를 같이 떠올려야 한다.
개발 모드 Strict Mode는 effect를 의도적으로 두 번 호출한다(setup → cleanup → setup). 라이브러리들은 이 더블 인보크를 견디려고 "한 번만 진짜로 초기화한다"는 가드를 흔히 둔다.
문제는 그 가드가 **진짜 언마운트 이후의 재마운트까지 막아버릴 때** 생긴다.

## 3. 범인: react-kapsule의 useEffectOnce

`react-force-graph-3d`는 직접 Three.js를 만지지 않는다.
내부적으로 `react-kapsule`을 써서 kapsule 컴포넌트를 React에 연결한다.
그리고 `react-kapsule`에는 `useEffectOnce`라는 훅이 있다.

이 훅이 풀려는 문제는 정당하다. **Strict Mode가 개발 모드에서 effect를 두 번 부를 때, 무거운 kapsule 초기화/파괴를 두 번 돌리고 싶지 않다.**
그래서 `effectCalled`, `renderAfterCalled` 같은 ref 플래그로 "이미 했음"을 기록하고, 두 번째 호출을 건너뛴다.

문제는 cleanup 쪽이다. 단순화하면 이런 모양이었다.

```js
// 개념적으로 단순화한 형태
const effectCalled = useRef(false);
const renderAfterCalled = useRef(false);

if (!effectCalled.current) {
  comp(domEl.current); // 진짜 초기화
  effectCalled.current = true;
}

return () => {
  // Strict Mode의 더미 cleanup이면 진짜 파괴를 건너뛴다
  if (!renderAfterCalled.current) return;
  destroyFunc.current?.();
};
```

여기서 일어나는 일을 시간 순으로 따라가 보자.

1. 첫 마운트: `effectCalled = true`로 표시하고 초기화한다.
2. 진짜 언마운트: destructor가 돈다. **그런데 `effectCalled`는 `true`로 남는다.**
3. 뒤로가기로 재진입: React가 같은 hook state/ref를 재사용하는 경로에서, `effectCalled`가 이미 `true`이므로 **초기화를 건너뛴다.**
4. 결과: `comp(domEl.current)`가 다시 호출되지 않는다. 캔버스 DOM은 다시 보일 수 있어도 내부 컨트롤·렌더러·리스너는 복구되지 않는다.

"보이는데 안 만져진다"의 정체가 이거였다.
**진짜 cleanup 이후에 lifecycle 플래그가 reset되지 않아서, 다음 마운트가 자신을 "초기화 끝난 인스턴스"로 착각**한다.

> "한 번만 실행"을 위한 가드가, "다시는 실행하지 않음"으로 새어 나간 셈이다. 이 일반화된 교훈은 가든 노트 [Strict Mode cleanup와 useEffectOnce](/ko/garden/react-strict-mode-cleanup-and-effect-once)에 따로 정리해 두었다.

참고로 연관 이슈로 `3d-force-graph`의 `_destructor`가 컨트롤/렌더러/씬 리소스를 충분히 정리하지 않는다는 이야기도 있었다. 다만 그쪽은 maintainer가 `three-render-objects`의 destructor가 처리한다고 답했고, 최신 버전에서 별도로 다뤄진 상태에 가깝다. **#596의 핵심은 리소스 정리가 아니라 `react-kapsule`의 재초기화 skip**이라, 둘을 섞지 않는 편이 분석에도 수정에도 깔끔하다.

## 4. 일단 막는 임시 workaround

upstream을 고치기 전까지 사용자 경험은 지켜야 한다.
가장 안전한 임시 처방은 **문제의 컴포넌트를 통째로 강제 remount**하는 것이다.
React에서 `key`를 바꾸면 같은 자리의 컴포넌트라도 새 인스턴스로 다시 만들어진다 -- 즉 재사용되던 hook state/ref가 버려진다.

```tsx
const hasMountedRef = useRef(false);
const [graphKey, setGraphKey] = useState(0);

useEffect(() => {
  // 같은 인스턴스가 다시 effect를 받는 상황이면 key를 올려 강제 remount
  if (FORCE_GRAPH_REMOUNT_WORKAROUND && hasMountedRef.current) {
    setGraphKey(prev => prev + 1);
  }
  hasMountedRef.current = true;
}, []);

<ForceGraph key={FORCE_GRAPH_REMOUNT_WORKAROUND ? graphKey : undefined} />;
```

`key`가 바뀌면 `react-kapsule`의 ref도 새것이 되므로 `effectCalled`가 다시 `false`에서 시작하고, 초기화가 정상적으로 다시 돈다.
플래그(`FORCE_GRAPH_REMOUNT_WORKAROUND`)로 감싼 이유는, upstream이 고쳐지면 **이 우회로를 깔끔히 걷어내기 위한 표식**을 남겨두기 위해서다.

workaround는 어디까지나 임시다. 근본 원인은 라이브러리에 있으니, 거기서 고쳐야 한다.

## 5. 진짜 고치기: upstream PR

PR 대상은 `react-force-graph`가 아니라 **`react-kapsule`**이다. 문제의 lifecycle 가드가 거기 있기 때문이다.
maintainer도 이슈 #596에서 "언마운트 후 다시 remount되는 동작은 익숙하지 않은 영역이지만, 설명한 접근이 기존 앱에 부작용을 만들 것 같진 않다. `react-kapsule`로 PR을 열어도 된다"는 취지로 답했다.

그래서 [react-kapsule#15](https://github.com/vasturiano/react-kapsule/pull/15)를 열었다. 수정은 작다. **진짜 destructor가 돈 뒤에 내부 ref들을 reset**해서, 재사용된 fiber가 remount될 때 다시 초기화되도록 한 게 전부다. 실제 diff는 `src/index.js`의 `useEffectOnce` cleanup에 다섯 줄을 더한다.

```diff
       // if the comp didn't render since the useEffect was called,
       // we know it's the dummy React cycle
       if (!renderAfterCalled.current) return;
+
+      // reset refs after teardown so a reused fiber re-initializes on remount
       if (destroyFunc.current) destroyFunc.current();
+      destroyFunc.current = undefined;
+      effectCalled.current = false;
+      renderAfterCalled.current = false;
```

`if (!renderAfterCalled.current) return;` 가드는 그대로 둔다 -- 이게 Strict Mode의 개발 전용 더미 cleanup에서 destructor를 건너뛰게 하는 기존 보호 장치다. 변경은 "진짜 cleanup이 끝난 뒤"에만 닿으므로, 개발 모드 동작은 바뀌지 않는다.

지켜야 할 불변식은 이렇다.

- Strict Mode의 개발 전용 더미 cleanup에서는 destructor를 **실행하지 않는다**(기존 가드 유지).
- 진짜 cleanup에서는 destructor를 **정확히 한 번 실행한다.**
- 진짜 cleanup 이후에는 다음 마운트에서 setup이 다시 돌도록 ref를 **reset한다.**

### 재현을 결정론적으로: React `<Activity>`

이 버그의 가장 까다로운 점은 "브라우저 뒤로가기"가 곧 "React가 fiber/ref를 재사용하는 경로"라는 걸 테스트로 안정적으로 재현하는 것이다. 그런데 다행히 React에는 **그 상태를 의도적으로 만들 수 있는 public API**가 있다 -- `<Activity>`다.

`<Activity mode="hidden">`은 자식을 언마운트하면서도 **fiber와 hook state는 보존**한다. 그래서 "destructor는 돌았는데 ref는 살아 있는" 바로 그 상황을 손으로 만들 수 있다.

```tsx
// visible → hidden: destructor가 돈다 (fiber/ref는 보존)
// hidden → visible: 같은 ref를 들고 다시 setup된다 = 우리가 재현하려던 그 경로
<Activity mode={visible ? 'visible' : 'hidden'}>
  <KapsuleWrappedComponent />
</Activity>
```

수정 전에는 `hidden → visible`에서 kapsule 초기화가 다시 돌지 않고, 수정 후에는 돈다. 브라우저 history를 E2E로 흉내 내는 것보다 훨씬 단순하고 결정론적인 회귀 재현이다. 기존 `example/strict-mode-example.html`로는 "더미 cleanup에서 `destroy`가 호출되지 않고, 진짜 unmount에서 정확히 한 번 호출된다"는 기존 보호 동작이 깨지지 않았음을 확인한다.

PR 본문에는 `Refs vasturiano/react-force-graph#596`을 넣어 이슈와 명시적으로 연결했다.

## 6. PR이 머지된 뒤: 우리 코드 정리 순서

이 글은 PR이 release된 뒤 공개할 예정이라, 머지 이후 `apps/blog`에서 밟을 순서를 체크리스트로 남긴다.

**1) `react-kapsule` 버전 끌어올리기**

- `react-force-graph-3d`가 새 `react-kapsule`을 dependency range로 자동으로 끌어오는지 `pnpm-lock.yaml`에서 확인한다.
- 자동 반영이 안 되면 `package.json`의 `pnpm.overrides`로 `react-kapsule`을 새 버전에 고정한다.
- `pnpm why react-kapsule`로 실제 해석된 버전이 올라갔는지 확인한다.

**2) workaround를 끄고 fix가 실제로 동작하는지 먼저 확인**

- `apps/blog/src/features/graph/ui/graph-canvas.tsx`의 `FORCE_GRAPH_REMOUNT_WORKAROUND`를 임시로 `false`로 둔다.
- 로컬에서 그래프 진입 → 다른 글로 이동 → 브라우저 뒤로가기로 복귀했을 때 drag/zoom/click이 살아 있는지 수동으로 확인한다.

**3) E2E로 회귀를 고정한 뒤 workaround 제거**

- `apps/blog/e2e/graph.spec.ts`에 "뒤로가기/앞으로가기 후 인터랙션이 살아 있는가" 시나리오를 추가한다.
- 이때 DOM이 보이는지만 확인하면 부족하다. 이 버그가 정확히 "보이는데 안 만져지는" 종류였기 때문이다. 노드 클릭 후 detail 패널이 열리는지, 휠/드래그 후 관찰 가능한 UI 상태가 바뀌는지처럼 **인터랙션의 결과**까지 본다.
- 새 E2E가 통과하면 `FORCE_GRAPH_REMOUNT_WORKAROUND` 분기와 `graphKey` 관련 코드를 걷어낸다.

**4) (선택) `3d-force-graph` 업데이트는 별개 작업**

- 리소스 정리 개선을 위한 것이며 이번 fix와 무관하므로, 섞지 말고 별도 PR로 다룬다.

이 순서를 다 밟고 나면 이 글의 `draft`를 해제해 공개한다.

## 마치며

한 줄 증상("뒤로가면 안 만져져요")에서 시작해, React wrapper → 어댑터 → Three.js로 이어지는 레이어를 내려가며 결국 `useEffectOnce`의 cleanup 한 곳에 도달했다.
교훈을 하나로 줄이면 이렇다.

**"한 번만 실행"을 보장하려고 둔 가드는, "다시는 실행하지 못함"으로 새어 나가기 쉽다.** setup만 보지 말고, 진짜 cleanup 이후 다음 lifecycle을 위한 상태가 원래대로 돌아오는지까지 봐야 한다.

라이브러리 lifecycle 가드의 일반적인 함정은 [가든 노트](/ko/garden/react-strict-mode-cleanup-and-effect-once)에 따로 정리해 두었다.
