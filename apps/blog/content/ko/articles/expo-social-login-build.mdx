## 7. 카카오 성공 — 시뮬레이터에서 토큰 획득

dev client를 재빌드하고 카카오 버튼을 눌렀다. 성공이었다.

```typescript
// useSocialLogin.ts — Phase A에서는 백엔드 연동 전, 토큰 획득 자체만 콘솔로 확인
if (__DEV__) {
  console.log(
    `[socialAuth] ${provider} 성공 · token=${result.token.slice(0, 8)}… · profile=${result.profile ? '있음' : '없음'}`
  );
}
```

로그에 `profile=없음`이 찍혔는데, 이건 정상이자 의도된 동작이다.
카카오 provider는 SDK 로그인에서 accessToken만 받아 넘긴다. 프로필은 백엔드가 카카오 API로 조회하거나 동의항목에 따라 따로 처리한다. Apple과 달리 카카오의 `signIn()`은 `profile`을 채우지 않는다.

토큰을 통째로 찍지 않고 앞 8자만 슬라이스한 건 의도적이다. DEV 로그라도 토큰 평문은 남기지 않는다.

## 8. 카카오 취소 코드 — 문서에 없어서 직접 실측했다

로그인은 됐는데, 사용자가 시트를 닫는 취소 케이스를 처리해야 했다.
취소는 에러가 아니다. 조용히 무시해야지, "로그인 실패" Toast를 띄우면 안 된다.

문제는 카카오 SDK의 취소 에러 코드가 공식 문서에 없었다는 것이다. 네이티브 enum 파생값이라 플랫폼마다 다를 수 있고, 명시된 상수도 못 찾았다.

그래서 직접 실측했다. 취소를 일으키고 catch에서 에러 객체를 통째로 찍어봤다.

iOS 취소 코드는 `"Cancelled"`였다. 카카오계정 웹(`ASWebAuthenticationSession`)을 닫았을 때 "The authentication session has been canceled by user"와 함께 떨어진다.

```typescript
// kakaoProvider.ts
const KAKAO_CANCEL_CODES = [
  'Cancelled', // iOS — 실측 확인됨
  // TODO(JIRA-204): Android 취소 코드 실측 후 추가 (값이 다를 수 있음)
];

const code = getErrorCode(error);
if (code !== undefined && KAKAO_CANCEL_CODES.includes(code)) {
  throw socialAuthError('kakao', 'canceled', '로그인을 취소했습니다.', error);
}
```

그리고 오케스트레이션 훅에서 `canceled`는 잡아서 즉시 return한다.

```typescript
// useSocialLogin.ts
if (isSocialAuthError(error) && error.kind === 'canceled') {
  return; // 취소는 조용히 무시
}
```

SDK의 취소/에러 코드가 문서에 없으면, 임시 디버그 로그로 직접 실측하는 게 가장 빠르고 정확하다.
다만 실측값은 플랫폼별로 다를 수 있으니 iOS 값을 Android에 그대로 가정하지 않았다. TODO로 명시해 뒀다.

## 9. Apple 시뮬레이터 실패 — 코드가 아니라 환경이었다

Apple 버튼을 눌렀더니 실패했다.

```text
AuthorizationError Code=1000
AKAuthenticationError -7026
```

처음엔 "내 코드가 뭘 잘못 보냈나" 싶어 `requestedScopes`, entitlement, plugin 등록을 다 뒤졌다.
그런데 아니었다.

이 조합은 시뮬레이터가 iCloud에 로그인돼 있지 않을 때(또는 SIWA가 시뮬레이터에서 불안정할 때) 발생하는 알려진 문제다.
요청은 AuthKit까지 정상적으로 발사되고 있었다. 우리 쪽 구성은 맞았고, Apple의 인증 환경에서 막힌 것이다.

`-7026`은 AuthKit 계층의 인증 실패, `Code=1000`은 일반적인 authorization 실패다.
시뮬레이터에서 Apple Sign In은 신뢰할 수 없다고 결론 내리고, 실기기 검증으로 방향을 틀었다.

> 사실 이 결론은 절반만 맞았다. `Code 1000`의 진짜 범인은 [3부](/ko/blog/articles/expo-social-login-backend)에서 다시 밝혀진다.

## 10. Apple Developer — 두 App ID에 capability 활성화

실기기 검증을 위해 Apple Developer 콘솔로 갔다. 우리는 dev/prod 두 개의 번들 ID를 쓴다.

- `com.example.myapp.dev` (development)
- `com.example.myapp` (production)

`app.config.ts`의 variant 설정에서 번들 ID가 갈린다.

```typescript
const variantConfig = {
  development: { bundleIdentifier: 'com.example.myapp.dev' },
  production: { bundleIdentifier: 'com.example.myapp' },
}[variant];
```

이 두 App ID **각각에** "Sign in with Apple" capability를 활성화했다.
dev 번들 ID를 빠뜨리면 개발 빌드에서 SIWA가 안 된다. 멀티 variant 앱은 `.dev`를 놓치기 쉬우니 둘 다 켜야 한다.

## 11. 재빌드 — capability는 entitlement에 박힌다

capability를 켰다고 끝이 아니었다.

"Sign in with Apple"은 단순한 코드 플래그가 아니라 provisioning profile과 entitlement에 박히는 네이티브 설정이다.
기존 dev client는 이 entitlement 없이 빌드된 바이너리라, capability를 켜도 그 빌드에는 반영되지 않는다. 새 profile로 재빌드해야 한다.

여기서 규칙 하나가 명확해졌다.

```text
네이티브 변경(모듈/capability/config plugin) → 재빌드
JS 변경 → 핫리로드(Fast Refresh)로 충분
```

카카오/Apple 모듈 추가, plugin 등록, capability는 전부 네이티브 변경이라 재빌드가 필수였다.
반대로 `useSocialLogin` 로직 수정 같은 JS 변경은 핫리로드로 즉시 반영됐다.

마침 실기기 케이블이 없어서 EAS 클라우드 빌드를 돌렸고, 두 가지를 마주쳤다.

- **Export compliance(`usesNonExemptEncryption`)**: 빌드/제출 과정에서 암호화 사용을 묻는다. 우리는 HTTPS/표준 암호화만 쓰고 자체 비표준 암호화는 없으므로 면제 대상이다. `app.config.ts`/`Info.plist`에 `ITSAppUsesNonExemptEncryption`을 박아두면 매번 묻지 않는다.
- **인증서/프로파일 자동화**: EAS에 Apple 계정으로 로그인하면 인증서와 provisioning profile을 자동 생성/갱신해주고, 켜둔 capability도 자동 반영한다. 손으로 profile을 내려받아 관리할 필요가 없었다. 클라우드 빌드의 가장 큰 편의였다.

## 2부에서 챙길 것

- [ ] SDK의 취소/에러 코드가 문서에 없으면 임시 디버그 로그로 실측한다. 취소는 에러가 아니라 정상 흐름이므로 조용히 무시한다.
- [ ] 실측값은 플랫폼별로 다를 수 있다. iOS 값을 Android에 그대로 가정하지 않는다.
- [ ] Apple은 시뮬레이터를 신뢰하지 않는다. `Code=1000`/`-7026`이면 코드보다 환경을 먼저 의심한다.
- [ ] 멀티 variant 앱은 모든 번들 ID(특히 `.dev`)에 capability를 빠짐없이 켠다.
- [ ] capability/모듈/plugin 같은 네이티브 변경은 재빌드, JS만 바뀌면 핫리로드. 케이블이 없으면 EAS 클라우드 빌드 + Apple 계정 연동으로 인증서를 자동화한다.

여기까지가 Phase A다. 네이티브 SDK로 토큰을 얻는 데까지 왔다.

하지만 토큰을 얻는 건 절반이다. 그걸 백엔드에 보내 진짜 로그인으로 만들어야 한다.
다음 [3부](/ko/blog/articles/expo-social-login-backend)에서는 OIDC와 nonce 개념, 그리고 Apple `Code 1000`의 진짜 범인을 다룬다.
