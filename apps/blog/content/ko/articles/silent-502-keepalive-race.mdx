사용자가 문자로 받은 인증번호 6자리를 **올바르게** 붙여넣었는데, 화면에는 "인증번호가 올바르지 않습니다"가 떴다. 더 이상한 건 그다음이었다. API 서버를 까보니 **그 시점에 인증 API가 호출된 기록 자체가 없었다.**

앱이 요청을 안 보낸 걸까? 우리 로직 어딘가에 실패가 숨어 있는 걸까? 이 글은 그 하나의 오류 메시지에서 출발해, 프론트엔드 코드 → Datadog RUM → 서버 로그의 부재 → 30일치 에러 분포를 거쳐 **Node와 로드밸런서의 keep-alive 타임아웃 레이스**라는 결론에 도착한 과정의 기록이다.

> **TL;DR** — 502의 원인은 Node 서버의 `keepAliveTimeout`(기본 5초)이 ALB idle timeout(60초)보다 짧아서였다. 서버가 먼저 끊은 유휴 연결에 ALB가 요청을 실어 보내면, 요청은 서버에 도달하지 못한 채 502가 된다. 서버 로그에 아무것도 없는 게 당연했다. 수정은 `main.ts` 3줄. 그리고 그 502를 "인증번호가 올바르지 않습니다"로 번역해 보여준 건 프론트엔드의 잘못된 폴백 문구였다.

## 1. 시작하기 전에: 무엇을 찾아야 하는지부터 확정한다

Datadog을 열기 전에 프론트엔드 코드부터 읽었다. 순서가 중요했다. **"그 문구가 나올 수 있는 경로"를 전부 열거**하니 세 개였고, 사용자가 준 두 가지 제약과 교집합을 내면:

- "N회 남음" 접미사가 없었다 → 서버가 시도 횟수를 내려준 게 아니다 → **서버의 판정이 아니다**
- 서버에 호출 기록이 없다 → **요청이 서버에 닿지 않았다**

남는 경로는 하나였다. 우리 에러 핸들러는 401도, 네트워크 단절도, 타임아웃도 아닌 **미분류 에러 전부**를 `"인증번호가 올바르지 않습니다"`라는 폴백 문구로 뭉뚱그리고 있었다. 즉 무언가 전송 계층에서 실패했고, 그게 "네가 번호를 잘못 쳤다"로 번역된 것이다.

이 시점에 원인은 몰랐지만, **무엇을 확인해야 하는지는 확정**됐다. "verify 요청이 실제로 나갔는가, 나갔다면 무엇을 받았는가." 가설을 세웠다기보다 판별 기준을 먼저 만든 셈인데, 뒤에서 이게 결정적으로 작동한다.

## 2. 첫 쿼리는 빗나갔다: 신원이 아니라 행위로 찾기

Datadog RUM에서 해당 유저 ID로 검색했다. **30일간 0건.**

여기서 "데이터가 없네"로 끝낼 수도 있었다. 하지만 RUM SDK가 앱에 붙어 있다는 걸 코드로 이미 확인했으니, 데이터가 아니라 **내 쿼리의 가정이 틀렸을** 가능성이 높았다. 필터링을 멈추고 열거로 전환했다 — 앱 목록을 aggregate로 뽑고, 유저 ID가 붙은 세션을 세어 보니 한 달간 **4명뿐**. 유저 식별 자체가 거의 안 붙고 있었고, 애초에 가입 플로우는 로그인 전이라 식별될 수도 없었다. 이 검색 축은 구조적으로 막힌 길이었다.

그래서 방향을 바꿨다. **사람을 못 찾으면 그 사람이 남긴 행위를 찾는다.** OTP 인증이라는 행위는 반드시 특정 엔드포인트를 때리고, URL은 로그인 여부와 무관하게 기록된다.

```
@type:resource @resource.url:*verification-codes*
```

첫 페이지 결과 안에 그게 있었다.

```
POST /auth/signup/verification-codes/verify
→ 502, 소요 1.08초, 응답 본문 122바이트
```

솔직히 이 쿼리는 "요청이 나가긴 했나"를 확인하려고 던진 것이지 502를 예상한 게 아니었다. 하지만 1장에서 판별 기준을 만들어뒀기 때문에, 마주친 순간 무슨 의미인지 즉시 알 수 있었다 — _502 → 401도 네트워크 에러도 아님 → 폴백 → 접미사 없는 그 문구._ 퍼즐의 앞뒤가 맞았다.

타임라인도 완벽하게 재구성됐다. 발송 200 → **6초 뒤 verify 502** → 5초 뒤 같은 코드로 재시도 200. 사용자는 아무것도 잘못하지 않았다.

## 3. 부재를 증거로 쓰려면 기준선부터 세운다

이제 "서버에 기록이 없다"를 검증할 차례다. 그런데 **"없음"은 그 자체로는 증거가 아니다.** 원래 로그를 안 남기는 시스템일 수도 있으니까.

그래서 먼저 서버 로그를 아무거나 뽑아 **"이 서버는 모든 요청에 START/END 로그를 남긴다"는 전제부터 확인**했다. 그다음에 문제의 시각을 봤다:

| 시각         | 서버 로그                                          |
| ------------ | -------------------------------------------------- |
| 10:36:07     | `sendSignUpVerificationCode` — 36ms 완료           |
| **10:36:14** | **없음** ← 502가 난 그 시각                        |
| 10:36:19     | `verifySignUpVerificationCode` — 7ms 완료 (재시도) |

모든 요청을 기록하는 서버가 이 요청만 기록하지 않았다. APM 스팬도 없었다. 결론: **요청은 서버에 도달하지 않았다.** 그리고 응답 본문 122바이트는 ALB가 자체 생성하는 502 페이지의 크기였다. 요청은 로드밸런서까지 갔고, 로드밸런서와 서버 사이 어딘가에서 죽었다.

가장 흔한 용의자인 배포도 확인했다 — 내 결론을 깨기 위한 쿼리였다. ECS 이벤트를 보니 직전 배포는 18분 전에 완료됐고, 문제 시각 전후로 태스크 변동은 0건. 배포 탓이 아니었다.

## 4. 30일치를 펼치니 502가 두 종류로 갈라졌다

단서가 하나뿐이면 우연일 수 있다. 30일치 502 전체(104건)를 시간대별로 버킷하니 뚜렷한 **이봉 분포**가 나왔다.

```
건수
 32 │                        █ ← 배포 시각
 29 │      █ ← 배포 시각
 19 │              █ ← 배포 시각
  3 │  ▂ ▂   ▂  ▂ ▂  ▂ ▂  ▂ ▂ ▂  ← 상시 산발 (우리 사례)
    └─────────────────────────────▶ 30일
```

그리고 **502까지 걸린 시간**이 두 무리를 갈랐다.

| 모드             | 발생 시점                 | 502까지       | 의미                                |
| ---------------- | ------------------------- | ------------- | ----------------------------------- |
| 뭉치 (19~32건씩) | ECS 배포 창과 정확히 일치 | **20~240ms**  | 죽어가는 타깃이 연결을 즉시 거부    |
| 단발 (~16건)     | 배포와 무관, 상시         | **1.0~2.0초** | 응답 없는 곳에 보냈다가 뒤늦게 실패 |

수십 ms와 1초 사이에는 아무것도 없었다. 같은 502인데 실패 소요 시간이 두 덩어리로 깨끗이 나뉜다는 건 **원인이 두 개**라는 뜻이다. 뭉치는 배포 드레인 문제로 설명이 됐고, 남은 단발의 프로필은 — 배포와 무관하고, 서버에 안 닿고, 실패까지 ~1초 — 어떤 패턴의 교과서적 시그니처였다.

~1초라는 숫자도 우연이 아니다. 죽은 연결에 보낸 패킷은 응답이 없고, TCP가 첫 재전송까지 기다리는 초기 RTO가 표준으로 **1초**다(RFC 6298, Linux `TCP_TIMEOUT_INIT`). 패킷 캡처가 없으니 이 부분은 정황 추론으로 남겨뒀지만, 실측값 1.05~1.20초와 맞아떨어진다.

## 5. 왜 서버는 요청을 받지 못했나: 두 개의 타이머

이제 코드를 읽으러 갈 차례다. 서버의 부트스트랩은 이렇게 끝났다.

```ts
await app.listen(process.env.PORT ?? 3001); // 타임아웃 설정 없음
```

레포 전체에서 `keepAliveTimeout` 0건. 베이스 이미지는 Node 22. 즉 **Node 기본값 5초**가 살아 있었다. 그리고 앞단 ALB의 idle timeout은 기본 **60초**.

이 두 숫자의 관계가 사고의 전부다. HTTP keep-alive는 연결을 재사용해 handshake 비용을 아끼는 최적화이고, ALB와 서버 사이에는 재사용을 위한 연결 풀이 유지된다. 그런데 "놀고 있는 연결을 언제 끊을지"를 양쪽이 각자 정한다:

```
서버: 유휴 5초 → 내가 끊는다 (FIN)
ALB:  유휴 60초까지 → 재사용 대상으로 본다

서버가 끊은 직후, 그 사실이 ALB에 반영되기 전의 짧은 창.
그 창에 ALB가 죽은 연결에 새 요청을 실으면 —
받을 사람이 없고, ALB는 이미 보낸 요청을 재시도하지 않는다(POST는 비멱등).
→ 502. 서버는 요청을 받은 적이 없으므로 로그도 없다.
```

**연결을 재사용할지 결정하는 쪽(앞)보다 받는 쪽(뒤)이 먼저 끊으면 안 된다.** AWS 권고도 "타깃의 keep-alive timeout을 ALB idle timeout보다 크게"인데, 우리는 아무도 설정하지 않아 기본값끼리 정확히 반대로 어긋나 있었다. 잘못 건드린 사람이 없는데 고장 나 있는, 기본값 충돌이었다.

## 6. 수정: 3줄, 그리고 반드시 한 쌍으로

```ts
const server = app.getHttpServer();
server.keepAliveTimeout = 65_000; // ALB idle(60초)보다 길게 → 항상 ALB가 먼저 끊는다
server.headersTimeout = 66_000; // 규칙: keepAliveTimeout보다 항상 크게
```

- **왜 65초인가** — ALB보다 크기만 하면 된다. 서버가 더 오래 기다리면 유휴 연결은 항상 ALB가 먼저 정리하고, ALB는 자기가 끊은 연결을 재사용하지 않으므로 레이스가 구조적으로 사라진다.
- **왜 headersTimeout도** — Node는 keep-alive 대기 중 도착한 요청의 헤더 수신 시간을 이 값(기본 60초)으로 잰다. keepAlive만 올리면 역전이 생겨 같은 부류의 조기 절단이 다른 경로로 재발한다.
- **"너무 길면 문제 없나"** — 없다. 유휴 연결의 실제 수명은 `min(ALB, 서버)` = ALB 값이 지배한다. 서버 쪽 값은 "먼저 끊지 않겠다"는 안전핀이지 실제 수명이 아니다. 적정값을 트래픽으로 계산하는 공식 같은 건 없고, 이건 용량 노브가 아니라 **순서 제약**이다.

검증도 명확하다. 배포 후 "1초대 산발 502"가 0으로 떨어지면 끝. 미시 메커니즘(1초=RTO)이 틀렸더라도 이 수정은 유효하다 — 서버가 먼저 끊지 않으면 어느 시나리오든 발생 자체가 안 되니까.

## 7. 남은 숙제 둘

**프론트엔드의 죄도 있다.** 502를 "인증번호가 올바르지 않습니다"로 보여준 건 FE의 폴백 문구다. 서버가 mismatch라고 판정한 경우에만 그 문구를 쓰고, 미분류 에러는 "일시적인 오류가 발생했으니 다시 시도해 주세요"로 분리해야 한다. 인프라 장애가 사용자에게 "네 잘못"으로 번역되는 건 최악의 UX다.

**관측 공백이 조사를 배로 힘들게 했다.** ALB 액세스 로그가 있었다면 `elb_status_code` vs `target_status_code` 비교로 1분 만에 끝났을 일이다. 없어서 "서버 로그의 부재"라는 간접 증거로 역추론해야 했다. 다음 장애를 위해 액세스 로그부터 켜기로 했다.

## 8. 이 과정에서 건진 것들

1. **도구를 열기 전에 판별 기준을 만든다.** "무슨 일이 있었나"가 아니라 "무엇이 후보들을 갈라놓나"를 먼저 정하면, 우연히 마주친 데이터도 즉시 알아볼 수 있다.
2. **쿼리가 0건이면 데이터가 아니라 내 가정을 의심한다.** 필터링 전에 열거로 그 축에 값이 존재하는지부터 확인한다.
3. **신원으로 못 찾으면 행위로 찾는다.** URL·엔드포인트는 로그인 여부와 무관하게 기록된다.
4. **부재를 증거로 쓰려면 존재의 기준선을 먼저 세운다.** "모든 요청을 기록하는 시스템"임을 확인한 뒤에야 "이 요청만 없다"가 증거가 된다.
5. **에러의 latency 분포는 지문이다.** 즉시 실패와 1초 실패가 갈리면 원인이 하나가 아니다.
6. **내 결론을 깨는 쿼리를 일부러 던진다.** 배포 탓이라는 가장 흔한 설명을 먼저 반증하고 나서야 다음으로 갔다.
7. **정황과 확정을 구분해 기록한다.** "1초 = TCP RTO"는 끝까지 정황 추론으로 표기했다. 수정의 유효성이 거기 의존하지 않는다는 것까지 포함해서.

타임아웃 순서 규칙과 TCP 재전송 타임아웃은 디지털 가든에 별도 노트로 정리해뒀다 — [Keep-Alive 타임아웃 순서](/ko/garden/keep-alive-timeout-ordering), [TCP 재전송 타임아웃(RTO)](/ko/garden/tcp-retransmission-timeout).
