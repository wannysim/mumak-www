바깥 함수는 이미 반환돼서 호출 스택에서 사라졌는데, 안쪽 함수는 어떻게 그 바깥 변수를 계속 읽고 쓸 수 있을까? 이 질문 하나를 끝까지 따라가면 렉시컬 스코프, 클로저, 그리고 React의 stale closure까지 한 줄로 꿰어진다.

> 한 줄 요약: **클로저는 "함수 + 그 함수가 선언된 렉시컬 환경에 대한 참조"다. 스코프는 호출한 곳이 아니라 적은 곳으로 정해지고, 환경은 스택이 아니라 힙에 살기 때문에 함수가 변수를 기억할 수 있다.**

## 렉시컬 스코프: 호출이 아니라 "적은 위치"로 정해진다

스코프는 변수를 어디서 찾을 수 있는지를 정하는 규칙이다. 자바스크립트는 렉시컬(정적) 스코프를 쓴다. 어떤 변수를 참조할 수 있는지가 **코드를 어디에 적었는가**로 결정된다는 뜻이다. 런타임에 누가 어디서 호출했는지는 아무 상관이 없다.

```js
const x = 'global';

function outer() {
  const x = 'outer';
  inner();
}

function inner() {
  console.log(x); // ?
}

outer(); // 'global'
```

`inner`는 `outer` 안에서 호출됐지만 `outer`의 `x`를 보지 못한다. `inner`가 **적힌 위치**가 전역이기 때문이다. 호출 위치를 따라갔다면(동적 스코프) `'outer'`가 찍혔을 것이다.

왜 이 설계를 택했을까? 정적 스코프는 코드만 보고 어떤 변수가 잡히는지 확정할 수 있다. 함수를 어디서 호출하든 결과가 같으니 사람도 추론하기 쉽고, 엔진도 변수 위치를 미리 최적화할 수 있다. 동적 스코프는 호출 경로마다 의미가 달라져서 추론이 불가능에 가깝다. 자바스크립트는 예측 가능성과 최적화를 택했다.

## 멘탈 모델: 실행 컨텍스트와 렉시컬 환경

함수가 실행되면 엔진은 실행 컨텍스트를 만든다. 그 안에 렉시컬 환경(Lexical Environment)이 들어 있는데, 두 부분으로 나뉜다.

- **환경 레코드(Environment Record)**: 이 스코프에 선언된 변수/함수가 실제로 담기는 곳
- **외부 참조(outer)**: 바깥 렉시컬 환경을 가리키는 포인터

이 `outer` 포인터가 핵심이다. 그리고 이 포인터는 함수가 **정의되는 순간** "내가 적힌 자리의 바깥 환경"으로 고정된다. 호출될 때 정해지는 게 아니다. 렉시컬 스코프가 코드를 따른다는 말의 실체가 바로 이 포인터다.

```
inner 의 렉시컬 환경
┌───────────────────────────┐
│ 환경 레코드: { }           │
│ outer ──────────┐         │
└─────────────────┼─────────┘
                  ▼
전역 렉시컬 환경
┌───────────────────────────┐
│ 환경 레코드: { x: 'global',│
│   outer, inner }          │
│ outer ──► null            │
└───────────────────────────┘
```

## 스코프 체인: 못 찾으면 outer를 따라 올라간다

변수를 읽을 때 엔진은 현재 환경 레코드부터 본다. 없으면 `outer` 포인터를 따라 한 칸 올라가서 다시 찾는다. 전역(outer가 `null`)까지 갔는데도 없으면 `ReferenceError`다. 이 연쇄가 스코프 체인이다.

```js
const a = 1;
function f() {
  const b = 2;
  function g() {
    const c = 3;
    console.log(a + b + c); // 6
  }
  g();
}
f();
```

`g` 안에서 `a`를 찾는 과정: `g`의 레코드(없음) → `f`의 레코드(없음) → 전역 레코드(`a` 발견). 안쪽이 바깥을 가리지 않는다는 점이 중요하다. 체인은 항상 안에서 밖으로 한 방향이다.

## 클로저: 함수 + 선언된 렉시컬 환경에 대한 참조

이제 정의를 내릴 수 있다. **클로저는 함수와, 그 함수가 선언된 렉시컬 환경에 대한 참조를 함께 묶은 것**이다. 자바스크립트의 모든 함수는 사실 클로저다. 다만 그 사실이 눈에 띄는 건 바깥 함수가 끝난 뒤에도 안쪽 함수가 살아남을 때다.

```js
function makeCounter() {
  let count = 0;
  return function () {
    count += 1;
    return count;
  };
}

const next = makeCounter();
console.log(next()); // 1
console.log(next()); // 2
console.log(next()); // 3
```

`makeCounter`는 첫 줄에서 이미 반환됐다. 그런데 `next`를 호출할 때마다 `count`가 1씩 늘어난다. 반환된 함수가 `makeCounter`의 렉시컬 환경(여기 `count`가 산다)을 `outer`로 붙잡고 있기 때문이다.

## 스택은 사라져도 환경은 힙에 남는다

여기서 "바깥 함수가 끝났는데 어떻게?"라는 첫 질문의 답이 나온다. 두 가지가 별개라는 게 핵심이다.

| 구분                     | 사는 곳   | 함수 반환 시       |
| ------------------------ | --------- | ------------------ |
| 호출 프레임(call frame)  | 호출 스택 | 즉시 사라짐        |
| 렉시컬 환경(변수 저장소) | 힙        | 참조가 있으면 유지 |

`makeCounter`가 반환되면 호출 스택의 프레임은 사라진다. 하지만 변수가 담긴 렉시컬 환경은 힙에 있는 객체다. 반환된 함수가 그 환경을 `outer`로 참조하고 있으므로, GC(가비지 컬렉터)는 "아직 도달 가능한 객체"로 보고 회수하지 않는다. 즉 `next`가 살아있는 한 `count`도 살아있다.

```
[ next 함수 ] ──참조──► [ makeCounter의 환경 { count } ]  ← 힙, GC 안 함
( makeCounter 프레임 )  ← 스택에서 이미 제거됨
```

반대로 `next`를 더 이상 아무도 참조하지 않게 되면, 그 환경도 함께 도달 불가능해져 회수된다. 클로저가 메모리를 잡는 것도, 푸는 것도 결국 "이 환경에 도달할 길이 남아 있는가"라는 한 가지 규칙으로 설명된다. 엔진이 도달 가능성을 어떻게 추적하는지는 [[js-v8-under-the-hood]]에서 더 깊이 다룬다.

## 고전 함정: for + var 루프가 다 같은 값을 찍는 이유

클로저를 제대로 이해했는지 가르는 시금석.

```js
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 3, 3, 3
```

직관적으로는 0, 1, 2를 기대하지만 3이 세 번 찍힌다. 왜일까? `var`는 함수 스코프라 `i`는 **루프 전체가 공유하는 단 하나의 바인딩**이다. 세 개의 콜백은 전부 그 하나의 `i`를 `outer`로 참조한다. `setTimeout` 콜백이 실제로 실행되는 시점(이벤트 루프가 한 바퀴 돈 뒤, [[js-event-loop]] 참고)에는 이미 루프가 끝나서 `i`가 3이 되어 있다. 세 콜백이 같은 상자를 보고 있으니 같은 값이 나온다.

`let`은 이걸 어떻게 고칠까?

```js
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// 0, 1, 2
```

`let`은 블록 스코프이고, 명세상 for 루프는 **반복마다 새로운 바인딩**을 만든다. 즉 `i`라는 상자가 매 반복마다 새로 생긴다. 명세는 이전 반복의 값을 새 상자로 옮긴 뒤 `i++`를 그 새 상자에 적용하므로, 각 콜백은 자기 반복 시점의 `i`(0, 1, 2)를 따로 캡처한다. 상자가 세 개니까 0, 1, 2가 나온다.

`var`로도 같은 효과를 내려면 직접 새 스코프를 만들어 줘야 했다.

```js
for (var i = 0; i < 3; i++) {
  (j => setTimeout(() => console.log(j), 0))(i);
}
// 0, 1, 2 — 즉시실행함수가 매번 새 j를 만든다
```

`let`은 이 패턴을 언어 차원에서 자동으로 해 주는 셈이다.

## 클로저의 실용: 은닉, 모듈, 부분 적용

**데이터 은닉**. 위 카운터의 `count`는 바깥에서 직접 건드릴 방법이 없다. 오직 반환된 함수를 통해서만 접근한다. 클래스의 private 필드가 없던 시절부터 자바스크립트는 클로저로 캡슐화를 해 왔다.

**모듈 패턴**. 같은 환경을 공유하는 여러 함수를 한 객체로 묶으면 공개 API와 내부 상태를 분리할 수 있다.

```js
const counter = (() => {
  let count = 0;
  return {
    increment: () => (count += 1),
    reset: () => (count = 0),
    value: () => count,
  };
})();
counter.increment();
console.log(counter.value()); // 1, count는 외부에서 접근 불가
```

**커링/부분 적용**. 인자를 미리 고정한 함수를 만든다. 고정된 인자가 클로저에 캡처된다.

```js
const multiply = a => b => a * b;
const double = multiply(2); // a=2 를 기억하는 클로저
console.log(double(10)); // 20
```

## 클로저와 메모리: 의도치 않은 캡처

클로저는 환경 **전체**를 붙잡는다. 큰 데이터를 가진 스코프 안에서 작은 클로저 하나만 밖으로 내보내도, 그 환경 전체가 살아남아 회수되지 않을 수 있다.

```js
function setup() {
  const huge = new Array(1_000_000).fill('x'); // 큰 데이터
  return () => 'hello'; // huge를 안 쓰는데도...
}
const fn = setup();
// 엔진 최적화에 따라 huge가 회수되지 않고 남을 수 있다
```

V8은 클로저가 실제로 참조하는 변수만 환경에 남기는 최적화를 하지만, 같은 스코프에 살아있는 다른 클로저가 `huge`를 참조하면 함께 묶여 남는다. 의도치 않게 무거운 데이터를 캡처하지 않도록, 필요 없는 참조는 끊고(`ref = null`) 큰 데이터는 클로저 밖으로 빼는 게 안전하다.

## React로 연결: 매 렌더가 새 클로저다

React 함수 컴포넌트는 렌더링될 때마다 함수 본문이 처음부터 다시 실행된다. 그 말은 **렌더마다 새로운 스코프, 새로운 클로저가 생긴다**는 뜻이다. 그 렌더 시점의 props와 state는 그 렌더의 클로저에 박제된다.

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      console.log(count); // 항상 0이 찍힌다
    }, 1000);
    return () => clearInterval(id);
  }, []); // 빈 배열: effect는 첫 렌더에만 실행

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

버튼을 아무리 눌러도 인터벌은 계속 `0`을 찍는다. effect 안의 콜백은 **첫 렌더의 클로저**에 갇혀 있고, 그 클로저의 `count`는 영원히 0이기 때문이다. 이게 stale closure(낡은 클로저)다. for + var 함정과 정확히 같은 원리다. "콜백이 캡처한 시점의 변수를 본다"는 것.

해결은 의존성 배열에 `count`를 넣어 effect를 새 클로저로 다시 만들거나, `setCount(c => c + 1)`처럼 최신 값을 인자로 받는 업데이터 함수를 쓰는 것이다. 이 메커니즘이 훅 내부에서 어떻게 동작하는지는 [[react-hooks-under-the-hood]]에서 이어진다.

## 흔한 오해

**오해: 클로저는 변수의 "값"을 복사해서 저장한다.**
실제: 값이 아니라 변수(바인딩)에 대한 참조를 잡는다. 그래서 바깥에서 변수가 바뀌면 클로저가 보는 값도 바뀐다. for + var에서 3이 찍히는 게 바로 이 증거다.

**오해: 스코프는 함수를 호출한 위치로 정해진다.**
실제: 함수를 선언(작성)한 위치로 정해진다. 렉시컬 스코프다. 호출 위치는 무관하다.

**오해: 클로저는 특별한 문법이거나 일부 함수만 가진다.**
실제: 자바스크립트의 모든 함수가 클로저다. 단지 바깥 함수가 끝난 뒤에도 안쪽 함수가 살아남을 때 그 효과가 드러날 뿐이다.

**오해: 함수가 반환되면 그 안의 지역 변수는 무조건 사라진다.**
실제: 그 변수를 참조하는 클로저가 살아있으면, 변수가 담긴 렉시컬 환경은 힙에 남아 회수되지 않는다.

## 스스로 점검하기

- 렉시컬 스코프와 동적 스코프의 차이를 한 문장으로 말할 수 있는가? 자바스크립트가 전자를 택한 이유는?
- 렉시컬 환경의 두 구성 요소는 무엇이고, `outer` 포인터는 언제 정해지는가?
- `makeCounter` 예제에서 바깥 함수가 끝났는데도 `count`가 살아있는 이유를 호출 스택과 힙의 차이로 설명할 수 있는가?
- for + var 루프가 같은 값을 찍는 이유와, `let`이 이를 해결하는 메커니즘(반복마다 새 바인딩)을 설명할 수 있는가?
- 클로저가 의도치 않은 메모리 누수를 일으키는 패턴은 무엇이고, 어떻게 완화하는가?
- React의 stale closure가 발생하는 원리를 "매 렌더가 새 클로저"라는 사실과 연결해 설명할 수 있는가?
