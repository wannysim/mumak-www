동적 타입에 인터프리터 언어인 JS가 어떻게 네이티브에 가까운 속도를 내는가? V8이 코드를 실행하는 동안 뒤에서 몰래 하는 일들을 따라가 본다.

> 한 줄 요약: **V8은 "처음엔 빠르게 시작, 자주 쓰이는 코드만 골라서 최적화"한다. 그 최적화는 전부 "타입이 일정할 것"이라는 가정 위에 서 있다.**

## 왜 처음부터 다 컴파일하지 않는가

C++ 같은 언어는 실행 전에 전체 코드를 기계어로 컴파일한다. V8도 마음만 먹으면 그렇게 할 수 있는데 일부러 안 한다. 이유는 트레이드오프다.

- **전부 미리 최적화 컴파일하면**: 시작이 느리다. 웹 페이지는 대부분의 함수가 딱 한 번만 실행되고 끝난다. 한 번 쓸 코드를 정성껏 최적화하는 건 손해다.
- **전부 인터프리트만 하면**: 시작은 빠른데 반복문이 많은 핫 코드에서 영영 느리다.

그래서 V8은 둘을 섞는다. 일단 빠르게 시작하고, 실행하면서 "이 함수 자주 불리네?"를 관찰하다가, 핫한 놈만 골라서 최적화 컴파일한다. 이게 **JIT(Just-In-Time) 컴파일**의 핵심 동기다. 실행 시점의 정보(어떤 타입이 들어오는지)를 알고 나서 컴파일하면 미리 컴파일하는 것보다 더 공격적으로 최적화할 수 있다는 점도 크다.

## 실행 파이프라인: 파싱부터 최적화까지

V8이 소스 문자열을 받아서 돌리기까지의 흐름은 이렇다.

```
소스 코드
   │  파싱
   ▼
  AST (추상 구문 트리)
   │  Ignition이 컴파일
   ▼
 바이트코드  ───────► Ignition 인터프리터가 실행
   │                      │
   │              실행하면서 "타입 피드백" 수집
   │              (이 변수엔 항상 숫자가 들어오네 등)
   │                      │
   │  핫 코드로 판정되면        │
   ▼                      ▼
 TurboFan이 최적화 기계어 생성 ◄── 피드백을 가정으로 사용
   │
   ▼
 가정이 깨지면 → 디옵티마이제이션 → 다시 바이트코드로
```

각 단계의 역할을 한 줄씩 짚으면 이렇다.

| 단계       | 담당        | 하는 일                                          |
| ---------- | ----------- | ------------------------------------------------ |
| 파싱       | Parser      | 소스를 AST로 변환 (실제 안 쓰는 함수는 게으르게) |
| 바이트코드 | Ignition    | AST를 작고 이식성 좋은 바이트코드로 컴파일·실행  |
| 최적화     | TurboFan    | 핫 코드를 타입 가정 기반 기계어로 컴파일         |
| 되돌리기   | Deoptimizer | 가정이 틀리면 최적화 코드를 버리고 복귀          |

여기서 중요한 건 **Ignition이 그냥 실행만 하는 게 아니라 "타입 피드백"을 모은다**는 점이다. "이 덧셈 자리엔 지금까지 항상 정수만 들어왔다" 같은 메모를 남긴다. TurboFan은 이 메모를 보고 "그럼 정수 덧셈으로 간주하고 빠른 기계어를 깔자"고 결정한다. 즉 최적화의 재료는 정적 분석이 아니라 **실제 실행 기록**이다.

## 히든 클래스: 동적 객체에 몰래 구조를 부여한다

JS 객체는 런타임에 속성을 자유롭게 더하고 뺄 수 있다. 사전(딕셔너리)처럼 "키로 값을 찾는" 방식이면 매번 해시 조회가 필요해서 느리다. V8은 이걸 피하려고 **히든 클래스(Hidden Class)**라는 걸 객체마다 몰래 붙인다. V8 소스 코드에서는 이걸 `Map`이라 부르고, 다른 엔진이나 일반 설명에서는 Shape라고도 한다.

히든 클래스는 "이 모양의 객체에서 `x`는 0번 슬롯, `y`는 1번 슬롯에 있다"는 **구조 정보**다. C 구조체처럼 속성을 고정 오프셋으로 만들어 두는 것이다. 같은 모양의 객체들은 같은 히든 클래스를 공유한다.

```js
function Point(x, y) {
  this.x = x; // 여기서 히든 클래스 C0 → C1 (x 추가)
  this.y = y; // C1 → C2 (y 추가)
}

const a = new Point(1, 2);
const b = new Point(3, 4);
// a와 b는 같은 히든 클래스 C2를 공유한다 → 빠르다
```

속성을 추가할 때마다 새 히든 클래스로 **전이(transition)**가 일어나고, 같은 순서로 같은 속성을 추가한 객체는 같은 전이 경로를 타서 결국 같은 히든 클래스에 도달한다. 그래서 `a.x`를 읽을 때 V8은 "C2 모양이면 0번 슬롯"이라고 바로 알 수 있다. 해시 조회가 사라진다.

## 속성 추가 순서가 갈리면 히든 클래스도 갈린다

여기서 흔히 발 헛디디는 지점이 나온다. 추가 **순서**가 다르면 전이 경로가 갈라져서 다른 히든 클래스가 된다.

```js
const a = {};
a.x = 1;
a.y = 2; // 히든 클래스: {} → {x} → {x,y}

const b = {};
b.y = 2;
b.x = 1; // 히든 클래스: {} → {y} → {y,x}
// a와 b는 "같은 속성"을 가졌지만 히든 클래스가 다르다
```

`a`와 `b`는 똑같이 `x`, `y`를 가졌지만 V8 입장에선 다른 모양의 객체다. 이 둘을 같은 함수에 섞어 넣으면 뒤에 나오는 인라인 캐싱이 둘 이상의 모양을 상대해야 해서 느려진다.

여기서 "생성자에서 모든 속성을 같은 순서로 초기화하라"는 조언이 나온다. 객체를 만들 때 항상 같은 순서로 같은 속성을 채우면 같은 히든 클래스로 수렴하고, 나중에 `obj.z = ...`로 속성을 추가해 모양을 바꾸는 일도 줄어든다. 이것도 [[js-prototype-and-this]]에서 `this`로 속성을 다루는 패턴과 맞물린다.

## 인라인 캐싱: "지난번에 본 그 모양이면 바로 그 오프셋"

`obj.x` 같은 속성 접근이 함수 안에서 반복 실행된다고 하자. 매번 "obj의 히든 클래스가 뭐지? x는 몇 번 슬롯이지?"를 다시 묻는 건 낭비다. **인라인 캐싱(Inline Cache, IC)**은 그 접근 지점(call site)마다 "지난번에 봤던 히든 클래스와 슬롯 번호"를 적어 둔다.

다음번에 같은 모양의 객체가 오면 조회를 건너뛰고 바로 캐시된 오프셋을 쓴다. IC는 그 지점이 본 모양의 가짓수에 따라 상태가 달라진다.

| 상태     | 본 모양의 수 | 동작                                  |
| -------- | ------------ | ------------------------------------- |
| 모노모픽 | 1개          | 가장 빠르다. 캐시 한 방에 끝          |
| 폴리모픽 | 2~4개        | 후보 몇 개를 순서대로 확인. 약간 느림 |
| 메가모픽 | 너무 많음    | 캐시 포기. 일반 조회로 폴백. 느림     |

핵심은 **call site를 모노모픽으로 유지하는 게 가장 빠르다**는 점이다. 함수 하나에 제각각 다른 모양의 객체를 자꾸 흘려보내면 그 자리가 폴리모픽, 메가모픽으로 떨어지면서 최적화 효과가 사라진다. 앞서 본 "같은 모양 유지"가 왜 중요한지가 여기서 보상으로 돌아온다.

## 디옵티마이제이션: 가정이 깨지면 최적화 코드를 버린다

TurboFan이 깐 최적화 기계어는 전부 가정 위에 있다. "이 인자는 항상 정수"라는 가정으로 정수 전용 빠른 경로를 깔았는데, 어느 날 문자열이 들어오면? 그 기계어는 더 이상 안전하지 않다. V8은 그 자리에서 최적화 코드를 폐기하고 바이트코드 인터프리터로 되돌아간다. 이게 **디옵티마이제이션(deoptimization)**이다.

```js
function add(a, b) {
  return a + b;
}

// 루프를 돌며 정수만 넘긴다 → TurboFan이 "정수 덧셈"으로 최적화
for (let i = 0; i < 100000; i++) add(i, i);

// 갑자기 문자열을 넣으면 가정이 깨진다 → 디옵트 발생
add('a', 'b'); // 최적화 폐기, 다시 바이트코드로
```

한 번 디옵트되고 다시 같은 가정으로 최적화했다가 또 깨지면, V8은 "이 함수는 타입이 안정적이지 않다"고 판단해 아예 최적화를 포기하기도 한다. **같은 함수에 여러 타입을 섞어 넣으면 느려진다**는 통념의 정체가 이거다. 함수가 늘 같은 모양·같은 타입을 받도록 짜면 디옵트가 안 일어나고 빠른 경로에 머문다.

## 가비지 컬렉션: 안 쓰는 메모리를 언제 어떻게 치우나

JS는 `free()`를 직접 호출하지 않는다. 더 이상 도달할 수 없는(어떤 변수로도 닿을 수 없는) 객체를 GC가 알아서 회수한다. V8의 GC(Orinoco)는 **세대 가설(generational hypothesis)** 위에 설계됐다.

> 세대 가설: 대부분의 객체는 만들어지자마자 금방 죽는다. 오래 살아남은 객체는 앞으로도 더 오래 살 확률이 높다.

이 가설이 맞다면, 갓 만든 객체들이 모인 영역만 자주 청소하면 효율이 좋다. 그래서 힙을 두 영역으로 나눈다.

```
                 V8 Heap
   ┌──────────────────┬──────────────────────┐
   │  Young Generation │   Old Generation      │
   │  (작다, 자주 청소) │   (크다, 가끔 청소)    │
   │   Scavenger       │   Mark-Sweep-Compact  │
   └──────────────────┴──────────────────────┘
       금방 죽는 객체        살아남아 승격된 객체
```

- **Young Generation — Scavenger(복사 방식)**: 영역을 둘로 나눠(From/To) 살아있는 객체만 반대편으로 복사하고, 원래 영역은 통째로 버린다. 죽은 객체는 건드리지도 않으니 빠르다. 두 번의 청소에서 살아남은 객체는 Old로 **승격(promotion)**된다.
- **Old Generation — Mark-Sweep-Compact**: 도달 가능한 객체를 표시(Mark)하고, 표시 안 된 걸 회수(Sweep)하고, 메모리 파편화를 줄이려 모아 압축(Compact)한다. 영역이 크니 한 번 돌면 비싸다.

왜 두 방식을 쓰나? **복사 방식은 죽는 객체가 많을수록 유리**하고(살아있는 것만 복사하면 되니까), **표시 방식은 살아있는 객체가 많을 때 메모리 낭비가 적다**. 세대별로 객체의 생존 양상이 다르니 거기 맞는 알고리즘을 쓰는 것이다.

### 멈춤(pause)을 줄이는 법

GC가 도는 동안 JS 실행을 멈추는 걸 stop-the-world라 한다. 큰 Old Generation을 한 번에 멈추고 청소하면 화면이 끊긴다. V8은 이걸 잘게 쪼개고 분산한다.

- **점진적(incremental)**: 큰 표시 작업을 여러 조각으로 나눠 JS 실행 사이사이에 끼워 돌린다.
- **병렬(parallel)·동시(concurrent)**: 백그라운드 스레드에서 메인 스레드와 함께/동시에 청소한다.

목적은 하나다. 한 번에 길게 멈추는 대신, 여러 번 짧게 멈춰 끊김을 사람이 못 느끼게 만드는 것이다. 이 "메인 스레드를 막지 않는다"는 감각은 [[js-event-loop]]에서 다루는 이벤트 루프 멈춤 문제와도 같은 고민이다.

## 실무 시사점: 측정이 먼저다

여기까지 읽으면 "그럼 객체 모양을 강박적으로 맞춰야겠다"는 생각이 들 수 있는데, 그게 함정이다.

- **엔진은 계속 바뀐다.** 오늘의 "이렇게 쓰면 빠르다"가 다음 V8 버전에서 무의미해지거나 역전될 수 있다. 특정 버전의 내부 동작에 코드를 맞추면 부채가 된다.
- **대부분의 코드는 핫 패스가 아니다.** 한 번 실행되고 마는 코드의 객체 모양을 다듬는 건 가독성만 깎는다.
- **추측하지 말고 측정하라.** 느린 곳을 프로파일러로 먼저 찾고, 거기가 정말 핫 패스이며 디옵트나 메가모픽이 확인됐을 때만 모양·타입 안정화를 적용한다.

엔진의 동작 원리를 아는 진짜 이유는 마이크로 최적화를 하기 위해서가 아니라, **느릴 때 "왜 느린지"를 설명할 수 있는 모델을 갖기 위해서**다. 평소엔 읽기 좋은 코드를 쓰고, 측정으로 병목이 드러났을 때 이 지식을 꺼내 쓰면 된다.

## 흔한 오해

- **오해: JS는 인터프리터 언어라서 항상 느리다.** → 실제: 핫 코드는 TurboFan이 기계어로 컴파일한다. 인터프리트는 시작 단계일 뿐이고, 자주 도는 코드는 네이티브에 가깝게 돈다.
- **오해: 객체에 같은 속성만 있으면 같은 취급을 받는다.** → 실제: 속성을 추가한 **순서**까지 같아야 같은 히든 클래스다. `{x,y}`와 `{y,x}`는 다른 모양이다.
- **오해: `delete obj.prop`은 그냥 속성 하나 지우는 가벼운 연산이다.** → 실제: 속성 삭제는 히든 클래스 전이를 망가뜨려 객체를 느린 딕셔너리 모드로 떨어뜨릴 수 있다. 핫 경로의 객체에서 `delete`는 조심해야 한다.
- **오해: GC가 있으니 메모리 누수는 없다.** → 실제: 도달 가능한 객체는 회수되지 않는다. 클로저나 전역에 의도치 않게 참조가 남으면 누수가 난다. 참조와 도달 가능성은 [[js-closure-and-scope]]에서 다룬다.

## 스스로 점검하기

- V8이 모든 코드를 처음부터 최적화 컴파일하지 않는 이유를 시작 속도와 피크 성능 관점에서 설명할 수 있는가?
- Ignition이 수집하는 "타입 피드백"이란 무엇이고, TurboFan은 그것을 어떻게 쓰는가?
- `{x,y}`와 `{y,x}`가 왜 다른 히든 클래스인지, 그리고 그게 인라인 캐싱에 어떤 영향을 주는지 말할 수 있는가?
