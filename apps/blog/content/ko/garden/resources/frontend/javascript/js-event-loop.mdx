싱글 스레드라는 JS가 어떻게 타이머·네트워크·클릭을 "동시에" 처리하는 것처럼 보이는가. 한 번에 한 줄만 실행하는 엔진이 어떻게 멈추지 않고 굴러가는지를 이벤트 루프로 정리한다.

> 한 줄 요약: **JS 엔진은 한 번에 한 가지 일만 한다. "동시에"처럼 보이는 건 기다리는 일을 엔진 밖(브라우저)에 맡기고, 끝난 것부터 큐에서 하나씩 꺼내 실행하기 때문이다.**

## 콜 스택: 한 번에 한 줄만

JS가 함수를 실행하는 방식은 **스택**이다. 함수를 호출하면 그 호출이 스택에 쌓이고(push), 반환하면 꺼낸다(pop). 맨 위에 있는 것만 실행된다.

```js
function a() {
  b();
}
function b() {
  console.log('b');
}
a();
// 스택: [a] → [a, b] → b 실행 → [a] → []
```

스택은 하나뿐이고, 동시에 두 칸을 실행하지 않는다. 이게 "싱글 스레드"의 출발점이다. 그래서 재귀가 끝없이 쌓이면 스택이 넘쳐 `RangeError: Maximum call stack size exceeded`가 난다.

**왜 스택인가?** 함수는 "가장 나중에 호출된 것이 가장 먼저 끝난다"는 후입선출 구조를 따르기 때문이다. `a`가 `b`를 부르면 `b`가 먼저 끝나야 `a`가 이어진다. 스택은 이 순서를 공짜로 보장한다.

## "JS는 싱글 스레드"의 정확한 의미

흔히 "JS는 싱글 스레드"라고 하지만, 정확히는 **JS 코드를 실행하는 스택이 하나**라는 뜻이다. 엔진 전체나 브라우저 전체가 스레드 하나로 돈다는 말이 아니다.

브라우저는 타이머를 세고, 네트워크 요청을 보내고, 사용자 입력을 감지하는 일을 **별도로** 처리한다. JS 함수를 실행하는 통로만 하나일 뿐이다.

**왜 하나로 설계했나?** DOM은 공유 상태다. 두 스레드가 동시에 같은 노드를 건드리면 락·경합 같은 동시성 지옥이 열린다. 실행 통로를 하나로 묶으면 "어떤 순간에도 내 코드 한 조각만 DOM을 만진다"가 보장돼서, 개발자가 락을 신경 쓸 필요가 없다. 단순함을 위해 의도적으로 택한 제약이다.

## 기다리는 일은 엔진 밖(Web API)이 한다

`setTimeout`, `fetch`, DOM 이벤트 리스너는 **JS 엔진의 기능이 아니다.** 브라우저(런타임)가 제공하는 Web API다.

```js
console.log('1');
setTimeout(() => console.log('2'), 1000);
console.log('3');
// 출력: 1 → 3 → 2
```

`setTimeout`을 호출하면 엔진은 "1초 뒤에 이 콜백을 큐에 넣어줘"라고 **브라우저에 맡기고 즉시 반환**한다. 스택은 멈추지 않고 `console.log('3')`으로 넘어간다. 1초를 세는 건 엔진 밖의 타이머가 한다.

```
┌─────────────┐        ┌──────────────────┐
│  Call Stack │        │   Web APIs        │
│  (JS 엔진)   │──맡김──▶│  타이머/fetch/DOM │
└─────────────┘        └──────────────────┘
       ▲                        │ (끝나면 콜백을)
       │                        ▼
       │  ┌──────────────── Task Queue ─────────┐
       └──│  끝난 콜백들이 줄을 선다              │
          └──────────────────────────────────────┘
```

**왜 밖으로 뺐나?** 1초를 세는 동안 스택이 멈춰 있으면 그동안 클릭도, 스크롤도, 다른 코드도 전부 막힌다. 기다림을 밖으로 보내야 엔진이 다른 일을 계속할 수 있다.

## 태스크 큐 vs 마이크로태스크 큐

끝난 콜백들이 서는 줄(큐)은 사실 **두 종류**다.

| 큐 종류           | 들어가는 것                                            | 우선순위 |
| ----------------- | ------------------------------------------------------ | -------- |
| 마이크로태스크 큐 | Promise.then/catch/finally, queueMicrotask, await 이후 | 높음     |
| 태스크 큐(매크로) | setTimeout, setInterval, DOM 이벤트, I/O               | 낮음     |

**왜 두 개로 나눴나?** Promise 같은 비동기 결과는 "지금 하던 일이 끝나는 즉시, 화면을 다시 그리기 전에" 처리되는 게 직관적이다. 만약 `then` 콜백이 setTimeout과 같은 줄에 섰다면, 그 사이에 렌더링이나 다른 타이머가 끼어들어 상태가 어긋날 수 있다. 마이크로태스크라는 우선 줄을 따로 둬서 "현재 작업의 뒷정리"를 다음 작업보다 먼저 끝내도록 보장한다.

## 이벤트 루프의 한 틱

이벤트 루프가 하는 일은 단순하다. **스택이 비면** 큐를 본다.

```
반복:
  1. 태스크 큐에서 태스크 1개 꺼내 실행 (스택이 빌 때까지)
  2. 마이크로태스크 큐를 전부 비운다 (중간에 새로 생긴 것도 포함)
  3. 필요하면 렌더링 (style → layout → paint)
  → 다시 1번으로
```

핵심은 비대칭이다. **태스크는 한 번에 1개**만 꺼내지만, **마이크로태스크는 큐가 빌 때까지 전부** 비운다. 그래서 `then`이 줄줄이 연결돼 있으면 그게 다 끝날 때까지 다음 태스크도 렌더링도 대기한다.

## 왜 setTimeout(fn, 0)은 즉시 실행되지 않는가

```js
setTimeout(() => console.log('나중'), 0);
console.log('먼저');
// 출력: 먼저 → 나중
```

`0ms`라도 콜백은 **태스크 큐에 들어가서 줄을 선다.** 현재 실행 중인 동기 코드가 전부 끝나고 스택이 빈 다음에야 큐에서 꺼내진다. 게다가 명세상 중첩 타이머에는 **최소 지연(약 4ms)**이 적용된다. `0`은 "최대한 빨리"라는 뜻이지 "즉시"가 아니다.

**왜?** 실행 중인 코드를 중간에 가로채면 콜 스택의 일관성이 깨진다. 큐는 "지금 일이 다 끝나면"이라는 약속을 지키는 장치다.

## 왜 Promise.then이 setTimeout보다 항상 먼저인가

```js
setTimeout(() => console.log('timeout'), 0);
Promise.resolve().then(() => console.log('promise'));
// 출력: promise → timeout
```

동기 코드가 끝나면 이벤트 루프는 **마이크로태스크 큐를 먼저 전부 비운 뒤** 태스크 큐로 간다. `then` 콜백은 마이크로태스크라 우선이고, `setTimeout` 콜백은 태스크라 뒤다. 둘 다 큐에 있어도 마이크로태스크가 항상 먼저 처리된다.

## 실행 순서 퀴즈

직접 따라가 보자. 출력 순서를 예측한 뒤 아래 추적과 맞춰 본다.

```js
console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve().then(() => console.log('3'));

async function run() {
  console.log('4');
  await null;
  console.log('5');
}
run();

console.log('6');
```

단계별 추적:

```
[동기 실행]
  console.log('1')        → "1"
  setTimeout(...)         → 콜백을 태스크 큐로
  Promise.then(...)       → 콜백을 마이크로태스크 큐로
  run() 호출
    console.log('4')      → "4"
    await null            → 여기서 함수가 중단,
                            나머지(5)는 마이크로태스크 큐로
  console.log('6')        → "6"
[스택 빔]

[마이크로태스크 전부 비우기]
  "3"  (then 콜백)
  "5"  (await 이후)

[태스크 1개]
  "2"  (setTimeout 콜백)
```

최종 출력: **1 → 4 → 6 → 3 → 5 → 2**

`await`는 마법이 아니다. `await 뒤의 코드`는 `.then(() => 뒤의 코드)`와 같다. 그래서 `5`는 `3`과 같은 마이크로태스크 무리에 들어가고, `2`(태스크)보다 먼저 나온다. 자세한 Promise 동작은 [[js-promise-and-async-await]] 노트로.

## 렌더링과의 관계: 긴 태스크가 프레임을 떨어뜨린다

브라우저는 보통 초당 60프레임(약 16.6ms마다 한 번)을 그리려 한다. 그런데 렌더링은 **태스크 사이사이에만** 끼어들 수 있다. 하나의 태스크가 16.6ms를 넘겨 오래 돌면, 그 시간 동안 화면은 갱신되지 못하고 **프레임이 떨어진다(버벅임).**

```js
// 메인 스레드를 200ms 점유 → 그동안 클릭도 스크롤도 멈춤
const end = Date.now() + 200;
while (Date.now() < end) {}
```

`requestAnimationFrame(cb)`의 콜백은 **렌더링 직전**에 실행된다. 그래서 위치·크기 같은 시각적 변경을 여기서 하면, 한 프레임 안에서 계산과 그리기가 깔끔하게 묶인다. 렌더링 파이프라인 자체는 [[browser-rendering-pipeline]] 노트에서 다룬다.

## 마이크로태스크 기아: 렌더링이 굶는다

마이크로태스크 큐는 "전부 비울 때까지" 처리된다. 그런데 마이크로태스크가 **또 마이크로태스크를 낳으면** 큐가 영원히 비지 않는다.

```js
function spin() {
  Promise.resolve().then(spin); // 끝없이 자기 자신을 다시 큐에 넣음
}
spin();
// 렌더링도, setTimeout도 영원히 차례가 오지 않는다 → 탭이 얼어붙음
```

이벤트 루프는 마이크로태스크를 다 비운 **뒤에야** 렌더링과 다음 태스크로 넘어간다. 그래서 마이크로태스크가 무한히 생기면 그 뒤 단계가 전부 굶는다. 반복 작업을 잘게 쪼개야 한다면 마이크로태스크 대신 태스크(`setTimeout`)로 양보(yield)해 렌더링 기회를 줘야 한다.

## 흔한 오해

- **오해**: "JS는 싱글 스레드라 비동기를 못 한다." → **실제**: 엔진의 실행 통로가 하나일 뿐, 기다리는 일은 브라우저가 병렬로 처리한다. 그래서 비동기가 가능하다.
- **오해**: "setTimeout(fn, 0)은 곧바로 실행된다." → **실제**: 태스크 큐에 들어가 현재 동기 코드가 끝나기를 기다린다. 최소 지연도 붙는다.
- **오해**: "await는 코드를 멈춰 세워 스레드를 블로킹한다." → **실제**: await는 함수를 중단하고 제어권을 돌려준다. 그동안 다른 코드가 돌고, 이후는 마이크로태스크로 재개된다.
- **오해**: "Promise는 새 스레드에서 돈다." → **실제**: Promise의 콜백도 결국 같은 콜 스택에서, 마이크로태스크로 실행된다. 별도 스레드가 아니다.
