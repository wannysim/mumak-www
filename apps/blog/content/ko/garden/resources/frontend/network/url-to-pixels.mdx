주소창에 `https://example.com`을 치고 엔터를 누른 그 0.5초 동안, 브라우저는 수십 단계를 순서대로 밟는다. 이 노트는 "픽셀이 그려지기까지 정확히 무슨 일이 어떤 순서로 일어나는가"를 단계별로, 그리고 각 단계가 "왜 존재하는가"까지 따라간다.

> 한 줄 요약: **URL 한 줄은 "글자 해석 → 주소 찾기 → 연결 만들기 → 안전하게 만들기 → 데이터 받기 → 그리기"라는 정해진 파이프라인을 거친다. 각 단계는 그 앞 단계 없이는 성립하지 않고, 거의 모든 단계에 캐시가 끼어들어 다음 방문을 빠르게 만든다.**

## 0단계 — 전체 그림부터

```
[URL 파싱·판단] → [DNS] → [TCP] → [TLS] → [HTTP 요청/응답] → [렌더러 파싱~페인트]
   검색? URL?     IP 찾기   연결    암호화     바이트 받기            픽셀
   HSTS 확인               수립
```

핵심은 이게 **그냥 나열된 단계가 아니라 의존 사슬**이라는 점이다. IP를 모르면 연결할 곳이 없고(DNS→TCP), 연결이 없으면 암호화할 통로가 없고(TCP→TLS), 안전한 통로가 없으면 요청을 못 보낸다(TLS→HTTP). 그래서 순서가 바뀔 수 없다.

## 1단계 — URL 파싱과 판단: 이건 검색어인가 주소인가

주소창은 사실 "주소창 겸 검색창"이다. 그래서 엔터를 누른 순간 브라우저가 가장 먼저 하는 일은 **입력이 URL인지 검색어인지 판단**하는 것이다.

- `리액트 렌더링` → 점도 없고 스킴도 없다 → 기본 검색 엔진으로 보낸다
- `localhost:3000` → 호스트로 해석 가능 → URL로 본다
- `example.com` → 점이 있고 TLD처럼 생겼다 → URL로 본다

**왜 이 판단이 먼저인가**: 뒤따르는 모든 단계(DNS, TCP, …)는 "목적지 호스트가 있다"를 전제로 한다. 검색어라면 호스트가 없으니 아예 다른 길(검색 결과 페이지로의 내비게이션)로 빠진다.

URL로 판단되면 곧바로 **HSTS 목록**을 확인한다. HSTS(HTTP Strict Transport Security)는 "이 사이트는 무조건 HTTPS로만 접속하라"고 브라우저가 기억해 둔 목록이다. `http://example.com`이라고 입력해도 이 목록에 있으면 네트워크에 나가기 전에 브라우저 내부에서 `https://`로 바뀐다(307 Internal Redirect).

**왜 이 단계가 존재하는가**: `http://`로 한 번이라도 평문 요청이 나가면 중간자(카페 와이파이 등)가 가로채 HTTPS 페이지로 못 가게 막을 수 있다(SSL stripping). HSTS는 **요청이 네트워크에 나가기 전에** 브라우저 안에서 강제로 업그레이드해 이 틈을 없앤다. 자세한 보안 맥락은 [[web-security-xss-csrf]]와 연결된다.

## 2단계 — DNS 해석: example.com이 사는 IP 찾기

브라우저는 `example.com` 같은 이름으로는 통신하지 못한다. 실제로 패킷을 보내려면 `192.0.2.1` 같은 IP가 필요하다(문서용 예시 주소). 이름을 IP로 바꾸는 게 DNS다.

찾는 순서는 **가까운 캐시부터** 훑는다.

```
브라우저 DNS 캐시 → OS DNS 캐시 → 리졸버(보통 ISP/공용 DNS, 재귀 질의)
                                        │
                          루트(.) → TLD(.com) → 권한 서버(example.com)
```

- **루트 서버**: ".com은 어느 TLD 서버가 아느냐"를 알려준다
- **TLD 서버(.com)**: "example.com은 어느 권한 서버가 아느냐"를 알려준다
- **권한 서버**: "example.com의 IP는 이거다"라고 최종 답을 준다

**왜 계층 구조인가**: 전 세계 모든 도메인 정보를 한 서버가 들고 있는 건 불가능하다. 책임을 단계별로 위임(루트는 TLD만, TLD는 도메인만 알면 됨)하면 각 서버가 작아지고, 새 도메인이 늘어도 그 도메인의 권한 서버만 추가하면 된다. 확장성을 위한 분할이다.

**왜 캐싱이 핵심인가**: 매번 루트부터 다 물으면 한 번 접속에 왕복이 여러 번 쌓인다. 그래서 각 단계 응답에 TTL(유효 시간)을 붙여 캐시한다. 두 번째 방문부터는 브라우저/OS 캐시에서 즉시 IP가 나오므로 DNS 단계가 사실상 사라진다. "처음만 느리고 그 다음은 빠르다"의 첫 번째 출처가 여기다.

## 3단계 — TCP 3-way handshake: 왜 악수를 세 번 하는가

IP를 알았으니 이제 그 서버와 **신뢰할 수 있는 통로**를 연다. TCP는 "보낸 게 빠짐없이, 순서대로 도착함"을 보장하는데, 그러려면 통신 시작 전에 양쪽이 서로 준비됐는지 확인해야 한다.

```
클라이언트            서버
   │   ── SYN ──────▶  │   "나 보낼게, 내 시작 번호는 x야"
   │  ◀─ SYN-ACK ───   │   "x 받았어. 나도 보낼게, 내 시작 번호는 y야"
   │   ── ACK ──────▶  │   "y 받았어. 이제 시작하자"
   연결 수립 완료
```

**왜 하필 3번인가**: 양쪽 모두 "내가 보낼 수 있고(송신), 상대가 받을 수 있다(수신)"를 서로 확인해야 한다. 클라이언트가 SYN을 보내고 서버가 SYN-ACK로 답하면 "클라이언트→서버" 방향은 검증된다. 하지만 서버는 아직 자기가 보낸 게 클라이언트에게 닿는지 모른다. 그래서 클라이언트의 ACK가 한 번 더 필요하다. 즉 **양방향을 각각 확인하려면 최소 3개의 메시지**가 든다(서버 쪽 ACK와 SYN을 SYN-ACK로 합쳐서 4개가 아니라 3개).

이 1왕복(RTT)이 "연결을 새로 여는 비용"이다. 그래서 뒤에 나올 **커넥션 재사용**이 중요해진다.

## 4단계 — TLS handshake: 통로를 안전하게

TCP로 통로는 뚫렸지만 아직 평문이다. `https`라면 그 위에 TLS로 암호화 계층을 올린다. 목적은 두 가지다.

1. **인증**: "지금 연결한 상대가 진짜 example.com이 맞는가" — 서버 인증서를 받아 신뢰할 수 있는 CA가 서명했는지, 도메인이 맞는지, 만료되지 않았는지 검증한다.
2. **키 교환**: 이후 주고받을 데이터를 암호화할 **공유 비밀 키**를 안전하게 만든다(엿보는 사람이 있어도 키를 못 알아내게).

**왜 인증이 키 교환보다 먼저 의미가 있는가**: 암호화만 하고 상대를 확인 안 하면, 중간자와 암호화 통신을 "안전하게" 하고 있을 수도 있다. 그래서 "누구와 통신하는지"부터 못 박는다.

```
TLS 1.2: TCP 1RTT + TLS 2RTT  → 첫 바이트까지 왕복이 길다
TLS 1.3: TCP 1RTT + TLS 1RTT  → 핸드셰이크를 1왕복으로 단축, 재방문 시 0-RTT까지 가능
```

**왜 TLS 1.3이 빨라졌는가**: 1.2는 "암호 방식 협상 → 키 교환"을 따로 왕복했지만, 1.3은 클라이언트가 첫 메시지에서 키 교환 재료를 미리 같이 보내 왕복을 한 번으로 줄였다. 사람이 체감하는 "접속 지연"의 상당 부분이 이 핸드셰이크 RTT라서, 이 단축이 크게 와닿는다.

## 5단계 — HTTP 요청/응답: 드디어 데이터를 주고받는다

안전한 통로가 생겼으니 이제 실제 요청을 보낸다.

```http
GET / HTTP/1.1
Host: example.com
Accept-Encoding: gzip, br
User-Agent: ...
```

서버 응답은 상태 코드와 헤더, 그리고 본문으로 온다.

| 상태 코드 | 의미                 | 브라우저의 다음 행동          |
| --------- | -------------------- | ----------------------------- |
| 200       | 성공                 | 본문(HTML)을 렌더러로 보낸다  |
| 301 / 308 | 영구 이동            | Location의 새 URL로 다시 요청 |
| 304       | 변경 없음            | 로컬 캐시 본문을 재사용한다   |
| 404 / 500 | 클라이언트/서버 오류 | 오류 페이지를 그린다          |

`Accept-Encoding: gzip, br` 헤더는 "압축해서 보내도 된다"는 신호다. **왜 압축이 끼는가**: HTML/CSS/JS는 텍스트라 반복이 많아 잘 줄어든다(흔히 70% 이상). 전송량이 줄면 마지막 바이트까지 받는 시간이 짧아진다. 프로토콜 버전별로 이 요청/응답을 어떻게 다중화하는지는 [[http-versions]]에서 다룬다.

## 6단계 — 브라우저 아키텍처: 받은 일을 누가 처리하는가

여기서 한 발 물러서서 "그동안 브라우저 안에서는 누가 무슨 일을 했나"를 본다. 현대 브라우저는 하나의 프로세스가 아니라 **여러 프로세스로 쪼개져** 있다.

```
┌─────────────────┐   탭/주소창/내비게이션 총괄
│ Browser 프로세스 │ ──────────────┐
└─────────────────┘               │
        │ 요청 위임                │ HTML 전달
        ▼                          ▼
┌─────────────────┐        ┌─────────────────┐
│ Network 프로세스 │ ─────▶ │ Renderer 프로세스 │  (사이트별로 격리)
│  DNS/TCP/TLS/HTTP│  바이트 │  파싱·레이아웃·페인트│
└─────────────────┘        └─────────────────┘
```

- **Browser 프로세스**: 주소창, 탭, 내비게이션 전체 조율
- **Network 프로세스**: 위 2~5단계(DNS/TCP/TLS/HTTP)를 실제로 수행
- **Renderer 프로세스**: 받은 HTML을 파싱해 화면으로 만든다 — **사이트마다 별도 프로세스**(사이트 격리)

**왜 멀티 프로세스인가**:

- **안정성**: 한 탭의 렌더러가 죽어도 그 탭만 죽고 브라우저 전체는 산다
- **보안/격리**: 렌더러는 신뢰할 수 없는 웹 콘텐츠를 실행하는 곳이라 샌드박스에 가둔다. 사이트 격리(Site Isolation)는 a.com과 b.com을 **다른 프로세스**로 나눠, 한 사이트의 메모리를 다른 사이트가 훔쳐보지 못하게 한다(Spectre류 공격 방어)
- **응답성**: 무거운 페이지 하나가 다른 탭의 반응성을 잡아먹지 않는다

즉 6단계는 새 작업이 아니라 **앞 단계들의 실행 주체를 보안 관점에서 다시 보는 시선**이다.

## 7단계 — 렌더러가 HTML을 픽셀로

Renderer 프로세스가 HTML 바이트를 받으면 친숙한 렌더링 파이프라인이 돌아간다.

```
HTML → DOM → (CSSOM) → Render Tree → Layout → Paint → Composite
```

이 과정 자체의 깊은 설명은 [[browser-rendering-pipeline]]에 있으니 여기서는 요약만 한다. 핵심은 **HTML 파싱이 스트리밍**이라는 점이다. 마지막 바이트를 기다리지 않고, 받은 만큼 바로 DOM을 만들어 가며 화면을 점진적으로 채운다. "위에서부터 점점 그려지는" 그 느낌이 이래서 나온다.

## 8단계 — 내비게이션 중 리소스 추가 로드

HTML 안에는 `<link>`, `<script>`, `<img>` 같은 **추가로 받아야 할 리소스**가 박혀 있다. 이걸 다 받아야 페이지가 완성된다. 브라우저는 **프리로드 스캐너(preload scanner)**를 둬서, 메인 파서가 `<script>`에서 막혀 있는 동안 별도의 가벼운 스캐너가 HTML을 앞질러 훑어 CSS/이미지 같은 리소스를 **미리 다운로드 시작**한다.

**왜 이게 필요한가**: 동기 `<script>`는 DOM 파싱을 멈춘다. 그동안 아무것도 안 받으면 시간이 버려진다. 프리로드 스캐너는 그 빈 시간에 뒤쪽 리소스를 당겨와 네트워크를 놀리지 않는다. 스크립트가 파싱을 막는 이유와 `async`/`defer`의 차이는 [[browser-script-loading]]에서 다룬다.

## 전체 타임라인 한눈에

```
t0  엔터 입력
│   URL 파싱 + HSTS 확인 (브라우저 내부, 네트워크 안 나감)
│
├─ DNS    [캐시 히트면 거의 0] ─ 없으면 재귀 질의 (루트→TLD→권한)
│
├─ TCP    SYN → SYN-ACK → ACK            (1 RTT)
│
├─ TLS    ClientHello → ... → Finished   (1.3: 1 RTT, 재방문 0-RTT)
│
├─ HTTP   GET → 200 + HTML (gzip/br)     (서버 처리 + 전송)
│         첫 바이트 도착 = TTFB
│
├─ 렌더   HTML 스트리밍 파싱 → DOM/CSSOM → Layout → Paint
│         프리로드 스캐너가 CSS/JS/IMG 병행 다운로드
│
▼   First Paint → 픽셀이 보이기 시작
```

## 캐시가 끼어드는 지점들

거의 모든 단계에 캐시가 있다. "두 번째 방문이 빠른 이유"를 한 번에 정리한다.

| 단계    | 무엇을 캐시하나          | 효과                             |
| ------- | ------------------------ | -------------------------------- |
| HSTS    | "이 도메인은 HTTPS 전용" | http 요청 없이 즉시 업그레이드   |
| DNS     | 이름→IP 매핑 (TTL)       | 재귀 질의 왕복 생략              |
| TCP/TLS | 살아있는 커넥션 재사용   | 핸드셰이크 RTT 자체를 생략       |
| HTTP    | 응답 본문/검증 토큰      | 304 또는 디스크 캐시로 전송 생략 |

**커넥션 재사용**이 특히 중요하다. keep-alive로 한 번 연 TCP+TLS 통로를 여러 요청이 공유하면, 두 번째 리소스부터는 3단계와 4단계의 RTT를 통째로 건너뛴다. HTTP 캐시의 동작 규칙(어떤 헤더가 무엇을 결정하는지)은 [[http-caching]]에서 자세히 다룬다.

## 흔한 오해

- **오해: 주소창은 URL만 받는다.** 실제: 주소창은 검색창을 겸하며, 1단계에서 입력이 URL인지 검색어인지부터 판단한다. 점/스킴 유무 등으로 갈린다.
- **오해: `http://`로 쳤으니 평문 요청이 한 번은 나간다.** 실제: HSTS 목록에 있는 도메인은 네트워크에 나가기 전에 브라우저 내부에서 https로 바뀐다. 평문 요청 자체가 발생하지 않는다.
- **오해: TLS만 켜면 안전하다.** 실제: TLS는 암호화 전에 인증서로 "상대가 진짜인지"부터 검증한다. 암호화만 있고 인증이 없으면 중간자와 안전하게(?) 통신하는 셈이 된다.
- **오해: 페이지가 다 받아진 뒤에 한 번에 그려진다.** 실제: HTML 파싱은 스트리밍이라 받은 만큼 점진적으로 DOM을 만들고 그린다. 그래서 위에서부터 차오른다.
