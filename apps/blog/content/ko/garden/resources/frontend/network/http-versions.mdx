HTTP는 왜 1.1, 2, 3로 계속 갈아엎어지는가? 새 버전마다 추가된 기능 목록을 외우는 건 의미가 없다. 모든 버전 변경을 관통하는 단 하나의 적, **Head-of-Line(HOL) 블로킹**을 따라가면 전부 한 줄로 꿰진다.

> 한 줄 요약: **HTTP의 역사는 "줄 맨 앞에서 막힌 놈 하나 때문에 뒤가 다 멈추는 문제"를 계층을 하나씩 갈아치우며 해결해온 과정이다.**

## HOL 블로킹이 뭐길래

은행 창구가 하나뿐인데 줄을 선다고 생각해보자. 앞사람이 거액 환전으로 10분을 잡아먹으면, 뒤에서 잔돈 바꾸려는 사람도 10분을 기다려야 한다. 일이 빨리 끝날 수 있는 사람조차 **맨 앞(Head of Line)에 걸린 사람** 때문에 막힌다. 이게 HOL 블로킹이다.

웹 페이지 하나는 HTML, CSS, JS, 이미지, 폰트 수십~수백 개의 요청으로 이뤄진다. 이 요청들을 어떻게 "줄 세우느냐"가 곧 HTTP 성능의 핵심이고, 버전마다 이 줄 서기 방식을 바꿔왔다. 중요한 건 HOL이 **두 군데**서 일어난다는 것이다. 하나는 HTTP 레벨, 하나는 그 아래 전송 계층(TCP) 레벨. 이 둘을 구분하는 게 이 노트의 전부다.

## HTTP/1.0: 요청 한 번에 연결 한 번

1.0은 가장 단순했다. 요청 하나 보낼 때마다 TCP 연결을 새로 맺고, 응답 받으면 끊었다.

```
GET /index.html  →  [TCP 연결] → 응답 → [연결 종료]
GET /style.css   →  [TCP 연결] → 응답 → [연결 종료]
GET /logo.png    →  [TCP 연결] → 응답 → [연결 종료]
```

**왜 문제였나?** TCP 연결은 공짜가 아니다. 맺을 때마다 3-way 핸드셰이크(SYN → SYN-ACK → ACK)로 왕복(RTT)이 한 번씩 든다. 여기에 HTTPS면 TLS 핸드셰이크 왕복이 더 붙는다. 리소스 100개짜리 페이지면 이 핸드셰이크 비용만 100번 반복된다. 정작 데이터는 얼마 안 되는데 "연결 세팅"에 시간을 다 쓰는 구조였다.

## HTTP/1.1: 연결은 재사용, 그런데 응답은 한 줄로

1.1은 `keep-alive`를 기본으로 만들어 연결을 끊지 않고 재사용했다. 핸드셰이크를 매번 안 해도 되니 큰 진전이었다.

```
[TCP 연결 1개]
GET /index.html → 응답
GET /style.css  → 응답
GET /logo.png   → 응답
... (같은 연결 계속 재사용)
```

**그런데 새 문제가 생겼다.** 한 연결에서 응답은 **보낸 순서대로** 돌아와야 한다. CSS 요청이 서버에서 1초 걸리면, 그 뒤에 보낸 이미지 요청은 이미 서버에서 처리가 끝났어도 CSS 응답이 나갈 때까지 기다려야 한다.

```
연결 1개:  [느린 CSS 응답 ......................] [빠른 이미지 응답]
                                                  ↑ 준비됐지만 못 나감
```

이게 **HTTP 레벨 HOL 블로킹**이다. 창구는 재사용하는데 여전히 한 줄로 세워서, 앞 응답이 느리면 뒤가 다 막힌다.

### 파이프라이닝은 왜 실패했나

1.1 스펙에는 사실 해결책이 있었다. **파이프라이닝** — 응답을 기다리지 않고 요청을 연달아 던지는 기법이다. 그런데도 거의 아무도 안 썼고, 브라우저들도 기본 비활성화했다. 이유는:

- **응답 순서 보장 요구**: 요청을 A, B, C 순으로 보내면 응답도 무조건 A, B, C 순으로 와야 한다. 즉 요청은 병렬로 보내도 응답 단계의 HOL은 그대로 남는다. 근본 해결이 아니었다.
- **중간 프록시 호환성**: 당시 수많은 프록시·서버가 파이프라이닝을 제대로 구현하지 않아, 응답이 깨지거나 순서가 꼬이는 일이 흔했다.

결국 "이론상 가능하지만 현실에서 못 쓰는" 기능으로 남았다.

### 1.1 시대의 우회 기술들: 전부 "연결이 부족해서"

브라우저는 한 도메인당 동시 연결을 보통 6개로 제한했다. 한 연결당 한 줄밖에 못 세우니, 사실상 동시에 처리 가능한 요청이 6개뿐이라는 뜻이다. 그래서 프론트엔드는 이 제약을 우회하는 기술들을 발명했다.

| 기법        | 무엇을 했나                            | 왜 했나                                    |
| ----------- | -------------------------------------- | ------------------------------------------ |
| 도메인 샤딩 | 리소스를 여러 서브도메인에 분산        | 도메인당 6개 제한을 도메인 수만큼 늘리려고 |
| 스프라이트  | 아이콘 수십 개를 이미지 한 장으로 합침 | 요청 수 자체를 줄이려고                    |
| 번들링      | JS·CSS를 파일 하나로 합침              | 요청 수를 줄이려고                         |
| 인라이닝    | 작은 이미지를 base64로 HTML에 박음     | 별도 요청을 아예 없애려고                  |

이 모든 게 **"한 연결에 한 줄, 연결은 6개"라는 제약**에서 나온 산물이다. 이 전제가 무너지면 이 기법들도 의미가 사라진다 — 실제로 그렇게 됐다.

## HTTP/2: 한 연결에 여러 줄 — 멀티플렉싱

2는 발상을 바꿨다. "연결은 하나만 쓰되, 그 안에서 요청을 동시에 여러 개 처리하자."

핵심은 세 가지다.

- **바이너리 프레이밍**: 1.1까지 사람이 읽는 텍스트였던 메시지를, 기계가 다루기 쉬운 **프레임(frame)**이라는 작은 바이너리 조각으로 쪼갠다.
- **스트림 멀티플렉싱**: 각 요청-응답을 **스트림(stream)**이라는 독립 논리 채널에 담는다. 여러 스트림의 프레임을 하나의 연결 위에서 **잘게 쪼개 번갈아(interleaving)** 보낸다.
- **헤더 압축(HPACK)**: 매 요청 반복되는 헤더(쿠키, User-Agent 등)를 압축해 중복을 제거한다.

```
연결 1개 (프레임 단위로 인터리빙):
[CSS프레임][이미지프레임][CSS프레임][JS프레임][이미지프레임]...
   stream1     stream3      stream1   stream5    stream3
→ 느린 CSS가 이미지·JS를 막지 않는다
```

이제 느린 응답 하나가 뒤를 막지 않는다. **HTTP 레벨 HOL이 해결**됐다. 그 결과 도메인 샤딩(연결을 여러 개로 쪼개면 단일 연결의 압축·우선순위 이점을 잃는다)이나 과도한 번들링(작은 파일을 동시에 받을 수 있으니 굳이 합칠 이유가 줄었다)은 오히려 손해가 됐다. 1.1 시대 우회 기법들이 무용지물이 된 이유다.

## 멀티플렉싱의 역설: TCP가 발목을 잡는다

여기서 HTTP의 역사가 한 번 더 꺾인다. HTTP/2는 HTTP 레벨 HOL을 없앴지만, 그 아래 **TCP**라는 토대를 그대로 썼다는 게 문제였다.

TCP는 "보낸 바이트를 순서대로 빠짐없이 전달한다"를 보장한다. 그래서 중간 패킷 하나가 유실되면, **그 패킷이 재전송돼 도착할 때까지 뒤따라온 모든 패킷을 애플리케이션에 넘기지 않고 버퍼에 묶어둔다.**

문제는 TCP가 그 안에 HTTP 스트림이 여러 개 섞여 있다는 걸 모른다는 것이다. stream1의 패킷 하나가 빠졌을 뿐인데, 멀쩡히 다 도착한 stream3·stream5까지 전부 멈춘다.

```
TCP가 보는 것:  [..][XX 유실][..][..][..]  ← 한 줄의 바이트 스트림
                       ↑ 이거 하나 때문에
HTTP/2가 원한 것: stream1만 멈추고 stream3,5는 진행
TCP의 현실:      전부 멈춤
```

이게 **TCP 레벨 HOL 블로킹**이다. HTTP 레벨에서 줄을 여러 개로 나눠놨는데, 그 아래 TCP가 다시 한 줄로 합쳐버리니 도로아미타불이다. 손실이 잦은 모바일·불안정 네트워크에서 특히 두드러졌다. HTTP 계층만으로는 더 이상 해결할 수 없는, **계층 자체의 한계**였다.

## HTTP/3: TCP를 버리고 UDP 위의 QUIC로

3의 결단은 과감하다. "TCP가 문제면, TCP를 안 쓰면 된다." HTTP/3는 TCP 대신 **UDP** 위에서 도는 **QUIC**라는 전송 프로토콜을 쓴다. UDP는 순서·재전송을 보장하지 않는 가벼운 토대라, 그 위에서 QUIC가 필요한 기능을 직접, **스트림을 인식한 채로** 구현한다.

- **스트림별 독립 손실 복구**: QUIC는 스트림이 여러 개라는 걸 안다. stream1 패킷이 유실되면 stream1만 멈추고, stream3·stream5는 그대로 흘려보낸다. TCP 레벨 HOL이 사라진다.
- **연결 수립 왕복 단축**: QUIC는 전송 핸드셰이크와 TLS 핸드셰이크를 **하나로 합쳤다.** TCP+TLS가 보통 2~3 RTT 걸리던 걸 1 RTT로, 재접속 시엔 0-RTT로 줄인다.
- **커넥션 마이그레이션**: TCP 연결은 (출발 IP, 포트, 도착 IP, 포트) 네 값으로 식별된다. 그래서 Wi-Fi에서 LTE로 바뀌어 IP가 변하면 연결이 끊긴다. QUIC는 연결을 IP가 아닌 **Connection ID**로 식별해서, IP가 바뀌어도 같은 연결을 이어간다.

```
HTTP/2:  HTTP 스트림 ── TLS ── TCP ── IP   ← TCP에서 HOL 재발
HTTP/3:  HTTP 스트림 ── QUIC(TLS 내장) ── UDP ── IP   ← QUIC가 스트림별로 독립
```

요점은 HTTP/3가 단순히 "더 빠른 HTTP"가 아니라, **HOL 문제를 풀려고 전송 계층까지 갈아치운 결과물**이라는 것이다.

## 프론트엔드에 미친 영향: 번들 전략이 달라졌다

1.1 시대의 황금률은 "요청 수를 줄여라"였다. 연결당 한 줄, 도메인당 6개라는 제약 때문에 작은 파일 여러 개는 곧 손해였다. 그래서 다 합쳤다.

HTTP/2·3에서는 한 연결로 수많은 파일을 동시에 받으니, **작은 파일 여러 개의 비용이 크게 줄었다.** 그래서 전략이 뒤집혔다.

- 거대 단일 번들 대신 **코드 스플리팅**으로 라우트·컴포넌트 단위로 잘게 쪼개는 게 유리해졌다.
- 작은 파일 하나가 바뀌어도 그 파일만 새로 받으면 되니 **캐시 효율**이 좋아진다(번들 하나면 일부만 바뀌어도 전체를 다시 받는다).
- 도메인 샤딩은 오히려 안티패턴이 됐다. 연결을 쪼개면 헤더 압축·우선순위·혼잡 제어 이점을 잃는다.

다만 무한정 쪼개도 되는 건 아니다. 파일마다 압축 효율이 떨어지고(작은 파일은 gzip/brotli 사전 학습이 덜 됨), 요청·응답 헤더 오버헤드와 캐시 무효화 관리 비용이 있다. 그래서 "잘게, 그러나 적정선까지"가 현재의 균형점이다. 이 적정선 판단에는 [[http-caching]] 전략이 함께 얽힌다. 페이지 로드 전체 흐름은 [[url-to-pixels]]에서 다룬다.

## 버전별 한눈 비교

| 버전     | 연결 사용            | HOL 발생 위치         | 헤더         | 전송 계층  |
| -------- | -------------------- | --------------------- | ------------ | ---------- |
| HTTP/1.0 | 요청마다 새 연결     | 핸드셰이크 반복 비용  | 평문, 비압축 | TCP        |
| HTTP/1.1 | keep-alive로 재사용  | HTTP 레벨 (응답 순서) | 평문, 비압축 | TCP        |
| HTTP/2   | 단일 연결 멀티플렉싱 | TCP 레벨 (패킷 유실)  | HPACK 압축   | TCP        |
| HTTP/3   | 단일 연결 멀티플렉싱 | 없음 (스트림별 독립)  | QPACK 압축   | QUIC (UDP) |

## 흔한 오해

**오해: HTTP/2가 HOL 블로킹을 완전히 없앴다.**
실제: HTTP/2는 **HTTP 레벨** HOL만 없앴다. 그 아래 **TCP 레벨** HOL은 그대로 남아서, 패킷 유실 시 모든 스트림이 멈춘다. 이 마지막 HOL을 없앤 건 전송 계층을 바꾼 HTTP/3다.

**오해: HTTP/3는 그냥 더 빨라진 HTTP/2다.**
실제: 기능 추가가 아니라 **토대 교체**다. TCP를 버리고 UDP 위의 QUIC를 쓴다. 이 한 줄이 스트림별 독립 손실 복구, 핸드셰이크 단축, 커넥션 마이그레이션을 전부 가능하게 한 핵심이다.

**오해: HTTP/2 시대에도 파일은 무조건 합칠수록 좋다.**
실제: 멀티플렉싱으로 작은 파일 여러 개의 비용이 줄어, 오히려 코드 스플리팅이 캐시 효율 면에서 유리해졌다. 다만 압축률·헤더 오버헤드 때문에 무한정 쪼개면 손해라 적정선이 있다.

**오해: 도메인 샤딩은 여전히 좋은 최적화다.**
실제: HTTP/1.1 시대의 우회책이었다. HTTP/2·3에서는 단일 연결의 압축·우선순위 이점을 깨뜨리는 안티패턴이다.

## 스스로 점검하기

- HTTP 레벨 HOL과 TCP 레벨 HOL은 각각 어느 버전에서 발생하고, 무엇이 원인인가?
- HTTP/1.1 파이프라이닝이 스펙에 있었는데도 실패한 두 가지 이유는 무엇인가?
- 도메인 샤딩·스프라이트·번들링·인라이닝이 전부 같은 하나의 제약에서 나왔다. 그 제약은 무엇인가?
- HTTP/2가 단일 연결로 여러 요청을 동시에 처리하는 세 가지 메커니즘은 무엇인가?
- HTTP/3가 TCP를 버린 결정이 가능하게 만든 세 가지 이점을 설명할 수 있는가?
- HTTP/2·3 시대에 와서 번들 전략이 "합치기"에서 "쪼개기"로 기울어진 이유는 무엇인가?
