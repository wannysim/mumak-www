프로덕션 502를 추적하다가 이상한 규칙성을 발견했다. 어떤 502는 20~240ms 만에 즉시 떨어지는데, 어떤 502는 **일관되게 1.0~2.0초** 걸려서 떨어졌다. 이 "1초 언저리"는 우연이 아니라 TCP 스펙에 박혀 있는 숫자였고, 결국 에러의 소요 시간만 보고 **두 가지 다른 장애를 구분하는 지문**이 됐다.

> 한 줄 요약: **TCP는 보낸 데이터의 응답(ACK)이 없으면 재전송하는데, 첫 재전송까지 기다리는 시간(초기 RTO)이 표준으로 1초다. 그래서 "죽은 연결에 요청을 보냈다"는 유형의 실패는 ~1초라는 시그니처를 남긴다. 즉시 실패(RST)와 1초 실패는 서로 다른 장애다.**

## TCP는 왜 재전송하나

TCP의 핵심 약속은 "보낸 데이터는 반드시 도착하거나, 도착 못 했음을 알려준다"다. 이를 위해 받는 쪽은 잘 받았다는 확인(ACK)을 돌려주고, 보내는 쪽은 ACK가 안 오면 **같은 데이터를 다시 보낸다**.

문제는 "얼마나 기다렸다가 다시 보낼 것인가"다. 너무 짧으면 멀쩡한 네트워크에 중복 패킷을 뿌리고, 너무 길면 유실 복구가 느려진다. 이 대기 시간이 **RTO(Retransmission TimeOut)** 다.

## 1초는 어디서 오는 숫자인가

연결이 한창 진행 중일 때의 RTO는 실측 왕복시간(RTT)으로부터 동적으로 계산된다(SRTT + 변동폭 기반, RFC 6298). 그런데 **참고할 RTT 표본이 없거나 응답이 아예 없는 상황**에서는 초기값으로 떨어진다.

- **RFC 6298 §2.1** — 초기 RTO는 **1초**를 권고 (전신인 RFC 1122는 3초였는데, 네트워크가 빨라지며 1초로 하향)
- **Linux 커널** — `TCP_TIMEOUT_INIT = 1 * HZ`, 즉 1초 하드코딩
- 재전송이 거듭 실패하면 **지수 백오프**: 1초 → 2초 → 4초 → 8초 …

그래서 "패킷을 보냈는데 상대가 조용히 사라진" 실패는 대략 이런 시간 프로필을 가진다: 전송 → (무응답) → **1초 대기** → 재전송 → 그제서야 RST/에러 → 실패 확정. 합쳐서 1초 남짓.

## 즉시 실패 vs 1초 실패: 지문이 된다

같은 502라도 실패까지 걸린 시간이 장애의 **종류**를 말해준다.

| 소요 시간                  | 저수준에서 벌어진 일                                       | 전형적 원인                                                                                                                 |
| -------------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **수십~수백 ms**           | 연결 시도/전송에 상대가 **즉시 RST**로 거부                | 프로세스가 죽어 있음, 포트 닫힘, 배포 중 태스크 교체                                                                        |
| **~1초 (또는 1→2→4 계단)** | 패킷이 **조용히 버려짐** → RTO만큼 기다린 뒤에야 실패 확정 | 반쯤 닫힌(half-open) 연결, 죽은 keep-alive 연결에 전송([[keep-alive-timeout-ordering]]), 중간 장비가 상태를 잃은 NAT/방화벽 |

실제 사례에서 이 구분이 결정적이었다. 30일치 502를 시간대별로 늘어놓으니 **배포 시간대에 몰린 뭉치는 전부 수십 ms**(죽어가는 타깃이 즉시 거부), **평상시에 산발하는 단발은 전부 1초대**(유휴 keep-alive 레이스)였다. 소요 시간 하나로 "502가 두 종류였고 원인도 두 개"라는 결론까지 갈 수 있었다.

## 디버깅에 써먹는 법

- 에러 응답의 **latency 분포를 먼저 본다.** 즉시/1초대/수 초대 군집이 갈리면 원인이 하나가 아니라는 강한 신호다.
- **1초·2초·4초 같은 "예쁜" 숫자**가 반복되면 애플리케이션이 아니라 전송 계층(TCP 재전송, 커널 타이머)을 의심한다. 앱 코드의 지연은 이렇게 깔끔한 계단을 만들지 않는다.
- 다만 이 추론은 패킷 캡처 없이는 정황이다. 1초 = RTO라는 해석이 그럴듯해도, 확정하려면 로드밸런서 액세스 로그나 tcpdump가 필요하다. 정황과 확정을 구분해서 기록해두면 나중에 결론이 뒤집혀도 어디까지 유효한지 알 수 있다.
