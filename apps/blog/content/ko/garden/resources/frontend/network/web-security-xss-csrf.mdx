프론트엔드 보안 사고의 양대 산맥인 XSS와 CSRF는 각각 무엇을 노리고, 브라우저와 우리는 무엇으로 막는가. 둘 다 "신뢰"를 악용하지만, 무너뜨리는 신뢰의 종류가 정반대다.

> 한 줄 요약: **XSS는 "내 페이지가 남의 코드를 믿어버리는 것"이고, CSRF는 "내 서버가 남이 위조한 요청을 믿어버리는 것"이다.**

## 두 공격은 무엇이 다른가

먼저 큰 그림부터 잡는다. 둘 다 "신뢰의 경계"가 뚫리는 사건이지만, 뚫리는 위치가 다르다.

```
XSS:  공격자 코드 ──실행──▶ [내 페이지 안] ──▶ 쿠키·토큰·DOM 다 장악
                              (브라우저가 "이건 우리 사이트 코드"라고 믿음)

CSRF: 공격자 사이트 ──요청──▶ [내 서버] ──▶ 쿠키 자동 첨부돼서 인증된 척
                              (서버가 "이건 로그인한 사용자 요청"이라고 믿음)
```

XSS는 **코드 실행** 권한을 빼앗는다. 한번 성공하면 그 페이지에서 할 수 있는 모든 걸 공격자가 한다. CSRF는 코드를 실행하지 못한다. 단지 사용자 이름으로 **요청 한 방**을 위조해서 보낼 뿐이다. 이 차이가 방어 전략을 가른다.

## XSS: 내 사이트에서 남의 스크립트가 실행된다

XSS(Cross-Site Scripting)는 공격자가 심어둔 스크립트가 **피해자의 브라우저에서, 그 사이트의 권한으로** 실행되는 것이다. 핵심은 "그 사이트의 권한으로"다. 브라우저는 같은 출처(origin)의 스크립트를 한 식구로 믿기 때문에, 일단 내 페이지 안에서 도는 코드는 쿠키도 읽고 DOM도 고치고 fetch도 보낼 수 있다.

### 왜 생기나 — 데이터가 코드로 둔갑하는 순간

근본 원인은 하나다. **데이터로 들어온 문자열이 코드로 해석되는 경계가 무너지는 것.** 사용자가 입력한 `"<script>..."`는 그냥 글자여야 하는데, 그게 HTML 파서를 만나 실행 가능한 스크립트가 돼버린다.

세 갈래로 나뉘는데, 갈리는 기준은 "악성 문자열이 어느 경로로 들어와 어디서 실행되느냐"다.

| 유형      | 어디로 들어오나        | 누가 당하나           | 서버를 거치나 |
| --------- | ---------------------- | --------------------- | ------------- |
| Reflected | URL 파라미터에 실려서  | 그 링크를 클릭한 사람 | 거침          |
| Stored    | DB에 저장돼서          | 그 페이지를 본 모두   | 거침          |
| DOM-based | URL/입력 → 프론트 코드 | 그 코드를 실행한 사람 | 안 거침       |

Reflected는 검색 결과 페이지가 검색어를 그대로 다시 뿌릴 때처럼 "요청에 실린 값이 즉시 응답에 반사"되는 경우다. Stored가 가장 위험하다. 한번 댓글로 심어두면 그 글을 본 **모든** 방문자에게 발사된다. DOM-based는 서버 응답은 멀쩡한데 프론트 JS가 `location.hash` 같은 값을 받아 직접 DOM에 꽂으면서 터진다. 그래서 서버 측 방어만으로는 못 막는다.

### innerHTML이 위험한 이유

`innerHTML`은 받은 문자열을 **HTML로 파싱**한다. 즉 "데이터"를 "코드"로 승격시키는 통로다.

```js
// URL이 ...#<img src=x onerror=alert(1)> 이면 location.hash는 "#<img...>",
// slice(1)로 맨 앞 #을 떼어 name = "<img src=x onerror=alert(1)>"
const name = location.hash.slice(1);

el.innerHTML = name; // 위험: img 태그가 만들어지고 onerror가 실행된다
el.textContent = name; // 안전: 그냥 글자로만 들어간다, 태그로 안 읽힌다
```

`textContent`는 무슨 문자열이 와도 "이건 글자다"라고 못박는다. 같은 입력인데 결과가 갈리는 이유는, `innerHTML`은 파서를 통과시키고 `textContent`는 통과시키지 않기 때문이다. 직접 따라가 보면 감이 온다. `#<img src=x onerror=alert(1)>`를 받았을 때, 첫 줄은 깨진 이미지를 만들며 `onerror`를 실행하고, 둘째 줄은 화면에 `<img ...>`라는 글자를 그대로 보여준다.

### 무엇을 노리나

내 페이지 안에서 코드가 돌면 가져갈 수 있는 건 사실상 전부다.

- 쿠키·세션·토큰 탈취 → `document.cookie`를 외부로 전송 (단, httpOnly 쿠키는 못 읽는다 — 뒤에서)
- 키로깅 → 입력 이벤트를 가로채 비밀번호를 수집
- 피싱 UI → 진짜 페이지 위에 가짜 로그인 폼을 덮어씌움

### React가 막아주는 것과 남는 빈틈

React가 XSS에 강한 이유는, JSX의 `{값}` 자리에 들어오는 모든 값을 **기본으로 이스케이프**하기 때문이다. `<`는 `&lt;`로 바뀌어 태그가 아니라 글자로 그려진다. 즉 데이터를 데이터로 묶어두는 게 기본값이다.

```jsx
// 안전: comment가 "<script>..."여도 글자로 그려진다
<div>{comment}</div>

// 위험: 이름부터 "위험하게"라고 경고하는 API
<div dangerouslySetInnerHTML={{ __html: comment }} />
```

`dangerouslySetInnerHTML`이라는 길고 무서운 이름은 **의도된 마찰**이다. "이건 이스케이프를 끄는 행위이고 위험하다"를 매 사용처에서 의식하게 만든다. 이런 API를 쓸 땐 `DOMPurify` 같은 라이브러리로 sanitize한 뒤 넣어야 한다.

이스케이프가 막지 못하는 또 다른 빈틈은 **속성 컨텍스트**, 특히 URL이 들어가는 자리다. 텍스트를 이스케이프한다고 URL의 "의미"까지 검증되지는 않기 때문이다.

```jsx
// userProvidedUrl이 어떤 스킴이든 그대로 href에 들어간다
<a href={userProvidedUrl}>링크</a>
```

React 19부터는 `href`/`src`에 `javascript:` URL이 들어오면 React가 에러를 던져 막는다(과거 버전은 콘솔 경고만 했다). 하지만 이건 `javascript:` 스킴이라는 한 갈래만 닫은 것이고, 속성 컨텍스트 전반은 여전히 직접 챙겨야 한다. 예를 들어 `data:` URL로 시작하는 페이지나 사용자가 넣은 외부 도메인으로의 오픈 리다이렉트는 React가 걸러주지 않는다. 이게 "이스케이프는 컨텍스트별로 달라야 한다"는 원칙의 실례다. HTML 본문, 속성값, URL, JS 문자열, CSS는 각각 위험한 문자가 다르다. URL을 받을 땐 `http`/`https` 스킴인지 먼저 검증해야 한다.

### 방어는 한 겹이 아니라 여러 겹

XSS는 단일 방어로 못 막는다. 막혔을 때 피해를 줄이는 계층까지 쌓는다.

| 계층            | 무엇을 하나                          | 무엇을 노린 방어        |
| --------------- | ------------------------------------ | ----------------------- |
| 출력 이스케이프 | 데이터를 코드로 승격 못 시키게       | 침투 자체를 차단        |
| CSP             | 인라인 스크립트·외부 스크립트를 차단 | 침투해도 실행을 차단    |
| httpOnly 쿠키   | JS가 쿠키를 못 읽게                  | 실행돼도 탈취 피해 축소 |

CSP(Content Security Policy)는 응답 헤더로 "이 출처의 스크립트만 허용, 인라인 `<script>`는 금지"를 선언한다. 그러면 공격자가 본문에 스크립트를 심는 데 성공해도 브라우저가 실행을 거부한다. httpOnly 쿠키는 마지막 안전망이다. 코드 실행까지 허용됐어도 `document.cookie`로 세션을 못 빼가게 한다.

## CSRF: 의도하지 않은 요청이 인증된 채로 나간다

CSRF(Cross-Site Request Forgery)는 사용자가 **자기도 모르게** 보낸 요청이, 이미 로그인된 상태라는 이유로 서버에서 정상 처리되는 공격이다.

### 왜 생기나 — 쿠키는 출처를 안 가리고 자동 전송된다

핵심 약점은 브라우저의 오래된 습관이다. **쿠키는 그 도메인으로 가는 요청이라면 누가 시켰든 자동으로 따라붙는다.** 내가 친 요청이든, 악성 사이트의 숨겨진 폼이 친 요청이든, 목적지가 `bank.com`이면 `bank.com`의 세션 쿠키가 자동으로 실린다.

```html
<!-- evil.com에 심긴 폼. 페이지 열리는 순간 자동 제출된다 -->
<form action="https://bank.com/transfer" method="POST">
  <input type="hidden" name="to" value="attacker" />
  <input type="hidden" name="amount" value="1000000" />
</form>
<script>
  document.forms[0].submit();
</script>
```

피해자가 `bank.com`에 로그인된 상태로 `evil.com`을 열기만 하면, 이 폼이 `bank.com`으로 POST를 쏘고 브라우저는 친절하게 세션 쿠키를 붙여준다. 서버 입장에선 "로그인한 사용자가 보낸 정상 송금"으로 보인다.

### XSS와의 본질적 차이

| 항목          | XSS                   | CSRF                       |
| ------------- | --------------------- | -------------------------- |
| 공격자가 얻음 | 코드 실행 (거의 전권) | 요청 위조 한 방            |
| 응답을 읽나   | 읽는다                | 못 읽는다 (동일 출처 정책) |
| 악용하는 신뢰 | 페이지가 코드를 믿음  | 서버가 쿠키를 믿음         |
| 필요 조건     | 입력이 코드로 해석됨  | 피해자가 인증된 세션 보유  |

가장 중요한 차이는 **CSRF는 응답을 읽지 못한다**는 점이다. 동일 출처 정책 때문에 `evil.com`의 스크립트는 `bank.com`이 보낸 응답 본문을 못 본다. 그래서 CSRF는 "조회"가 아니라 "상태를 바꾸는 요청"(송금, 비밀번호 변경, 삭제)을 노린다. 결과를 못 봐도 일을 저지를 수는 있기 때문이다.

### 방어 — 출처를 증명하게 만든다

CSRF 방어의 공통 아이디어는 "이 요청이 **정말 우리 사이트에서 출발했는지**" 증명을 요구하는 것이다. 악성 사이트는 그 증명을 만들 수 없기 때문에 막힌다.

- **SameSite 쿠키**: 쿠키에 `SameSite=Lax`/`Strict`를 붙이면, 다른 출처에서 출발한 요청에 쿠키가 자동으로 붙는 걸 제한한다. 즉 자동 전송이라는 약점 자체를 좁힌다(`Lax`가 남기는 예외는 아래에서 다룬다).
- **CSRF 토큰**: 서버가 발급한 예측 불가능한 토큰을 폼/헤더에 동봉하게 한다. 악성 사이트는 이 토큰 값을 모르므로 위조 요청을 완성하지 못한다.
- **Origin/Referer 검증**: 요청 헤더의 출처가 우리 도메인인지 서버가 확인한다.

### SameSite Lax가 바꾼 판도, 그래도 남는 구멍

요즘 브라우저는 `SameSite` 미지정 쿠키를 사실상 `Lax`로 취급한다. 이 기본값 변경이 위 송금 폼 같은 **교차 출처 POST**를 기본으로 막아버렸다. CSRF의 고전적 공격 표면이 크게 줄어든 결정적 사건이다.

다만 `Lax`는 완전하지 않다. **top-level GET 내비게이션**(사용자가 링크를 눌러 페이지를 직접 이동하는 것)에는 여전히 쿠키를 붙인다. 그래서 만약 서버가 GET 요청으로 상태를 바꾸도록 만들어 뒀다면 — 예를 들어 `GET /logout`이나 `GET /delete?id=1` — 공격자가 `<img src="https://bank.com/delete?id=1">` 한 줄로 그 부수효과를 일으킬 수 있다.

```html
<!-- Lax 쿠키도 top-level GET엔 붙으므로, GET이 상태를 바꾸면 이거에 당한다 -->
<img src="https://bank.com/delete?id=1" />
```

여기서 "GET 같은 안전한 메서드(safe method)에는 부수효과를 두지 말라"는 HTTP 원칙이 단순한 권고가 아니라 **보안적 근거**를 가짐을 알 수 있다. GET을 진짜로 읽기 전용으로 유지하면, `Lax`가 남긴 이 구멍으로 들어올 일이 없다. HTTP 메서드의 의미는 [[http-versions]]에서도 다룬다.

## 토큰 저장 위치 논쟁 재방문: localStorage vs httpOnly 쿠키

인증 토큰을 어디 둘지는 결국 "어느 공격에 노출면을 줄이느냐"의 선택이다. 두 선택지는 정확히 반대의 약점을 가진다.

| 항목           | localStorage            | httpOnly 쿠키        |
| -------------- | ----------------------- | -------------------- |
| XSS에 노출     | 높음 (JS가 직접 읽음)   | 낮음 (JS가 못 읽음)  |
| CSRF에 노출    | 낮음 (자동 전송 안 됨)  | 높음 (자동 전송됨)   |
| 요청에 싣는 법 | 코드가 직접 헤더에 첨부 | 브라우저가 자동 첨부 |

`localStorage`는 자동 전송이 없으니 CSRF에서 자유롭지만, XSS가 한번 터지면 토큰이 그대로 읽혀 나간다. `httpOnly` 쿠키는 JS가 못 읽으니 XSS 탈취에 강하지만, 자동 전송되므로 CSRF 대비책(SameSite, CSRF 토큰)을 반드시 함께 둬야 한다.

그래서 "무엇이 더 안전한가"라는 질문 자체가 약간 틀렸다. **각 저장 위치가 어느 공격에 강하고 약한지를 알고, 약한 쪽을 다른 계층으로 보완하는 것**이 정답에 가깝다. 토큰과 저장소의 트레이드오프는 [[browser-storage]]에서 더 깊게 다룬다.

## 흔한 오해

- **오해**: "React를 쓰면 XSS는 신경 안 써도 된다." → **실제**: 기본 이스케이프는 강력하지만 `dangerouslySetInnerHTML`, 속성·URL 컨텍스트(스킴 검증 안 된 외부 URL 등), DOM-based 경로는 여전히 열려 있다. React 19가 `javascript:` 스킴을 막아준 건 그중 한 갈래일 뿐이다.
- **오해**: "입력값만 검증하면 XSS는 끝이다." → **실제**: 핵심은 입력 필터링보다 **출력 시점의 컨텍스트별 이스케이프**다. 같은 데이터도 HTML 본문, 속성, URL에서 위험한 문자가 다르다.
- **오해**: "SameSite=Lax면 CSRF는 완전히 끝났다." → **실제**: 교차 출처 POST는 막지만 top-level GET엔 쿠키가 붙는다. GET이 상태를 바꾸면 여전히 당한다.
- **오해**: "CSRF로도 내 데이터를 읽어간다." → **실제**: CSRF는 응답을 못 읽는다(동일 출처 정책). 상태를 바꾸는 요청을 위조할 뿐, 조회 결과를 가져가진 못한다.

- `el.innerHTML = x`와 `el.textContent = x`는 같은 입력에 대해 왜 결과가 갈리나?
- Reflected, Stored, DOM-based XSS는 무엇을 기준으로 나뉘고, 왜 DOM-based는 서버 측 방어로 못 막나?
- React의 기본 이스케이프가 막아주지 못하는 XSS 빈틈 두 가지를 들 수 있나?
- CSRF가 응답 본문을 읽지 못하는 이유는 무엇이고, 그 제약이 공격 대상(읽기 vs 상태 변경)을 어떻게 정하나?
- `SameSite=Lax`가 막는 요청과 못 막는 요청은 무엇이고, "GET에 부수효과를 두지 말라"가 왜 보안 원칙이 되나?
- 인증 토큰을 localStorage에 두는 것과 httpOnly 쿠키에 두는 것은 각각 어느 공격에 강하고 약한가?
