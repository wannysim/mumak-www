같은 파일을 두 번 받지 않으려고 브라우저와 서버는 어떤 약속을 해뒀는가. 한 번 받은 응답을 언제 재사용해도 되는지, 언제 다시 물어봐야 하는지를 정하는 규칙이 HTTP 캐싱이다.

> 한 줄 요약: **가장 빠른 요청은 보내지 않는 요청이다. 캐싱은 "쓸 수 있나(신선한가)"를 먼저 묻고, 그게 만료되면 "아직 같나(검증)"를 본문 없이 묻는 두 단계 약속이다.**

## 캐싱이 던지는 두 가지 질문

네트워크 왕복은 비싸다. 같은 `app.js`를 페이지를 옮길 때마다 다시 받으면 느리고, 데이터도 낭비된다. 그래서 브라우저는 한 번 받은 응답을 어딘가(메모리·디스크)에 보관해 두고 재사용하려 한다. 이때 던지는 질문은 둘뿐이다.

1. **쓸 수 있나(신선한가)?** — 보관해 둔 응답이 아직 유효하면, 네트워크에 아예 나가지 않고 그대로 쓴다.
2. **아직 같나(검증)?** — 유효 기간이 지났으면, 서버에 "내가 가진 게 아직 최신이냐"만 물어본다. 같으면 본문은 다시 안 받는다.

**왜 두 단계인가?** 1번만 있으면 "언제까지 믿어도 되나"를 정확히 못 정한다. 너무 짧으면 캐시가 쓸모없고, 너무 길면 바뀐 내용을 못 본다. 2번이 있어서 "일단 짧게 믿되, 만료되면 싸게 확인"이라는 절충이 가능하다.

```
요청 ──▶ 캐시에 있나?
          │ 없음 ───────────────▶ 서버에서 전체 받기 (200)
          │ 있음 ──▶ 신선한가?
                     │ 예 ───────▶ 캐시 그대로 사용 (네트워크 X)
                     │ 아니오 ───▶ 서버에 검증 요청
                                    │ 같음 ──▶ 304, 캐시 재사용
                                    │ 다름 ──▶ 200, 새 본문 받기
```

## 신선도(freshness): 네트워크에 아예 안 나가는 구간

응답이 "신선하다"는 건 유효 기간 안에 있다는 뜻이다. 이 기간을 정하는 게 `Cache-Control`의 `max-age`다.

```http
Cache-Control: max-age=3600
```

이 응답을 받은 시점부터 **3600초(1시간) 동안**은 브라우저가 서버에 묻지 않고 캐시를 그대로 쓴다. DevTools 네트워크 탭에서 `(memory cache)` 또는 `(disk cache)`로 찍히는 게 이 구간이다. 요청 자체가 나가지 않으니 가장 빠르다.

- **메모리 캐시**: 탭이 살아 있는 동안 RAM에 보관. 같은 탭에서 뒤로 가기·재방문 시 즉시.
- **디스크 캐시**: 디스크에 보관. 탭을 닫았다 다시 열어도 살아남는다.

**왜 두 곳인가?** 메모리는 빠르지만 휘발성이고 용량이 작다. 디스크는 느리지만 영속적이다. 브라우저가 응답의 크기·재사용 빈도를 보고 알아서 배치한다.

`Expires` 헤더(절대 시각)도 같은 일을 하지만, 클라이언트 시계가 틀어지면 어긋난다. 그래서 상대 시간인 `max-age`가 우선이고 권장된다.

## 만료 후 검증(revalidation): 본문 없이 헤더만

`max-age`가 지나면 캐시는 "stale(상한)" 상태가 된다. 버리는 게 아니라, 서버에 **"내가 가진 게 아직 유효하냐"**만 물어본다. 이걸 조건부 요청(conditional request)이라고 한다.

서버는 응답을 줄 때 그 응답의 "지문"을 함께 준다.

```http
HTTP/1.1 200 OK
ETag: "v3-abc123"
Last-Modified: Wed, 04 Jun 2026 10:00:00 GMT
Cache-Control: max-age=60
```

브라우저는 만료 후 다음 요청에 그 지문을 되돌려 보낸다.

```http
GET /data.json HTTP/1.1
If-None-Match: "v3-abc123"
If-Modified-Since: Wed, 04 Jun 2026 10:00:00 GMT
```

서버가 보기에 내용이 그대로면, **본문 없이** 짧은 응답만 보낸다.

```http
HTTP/1.1 304 Not Modified
ETag: "v3-abc123"
```

`304`는 본문이 비어 있다. 헤더만 오가니까 전체를 다시 받는 것보다 훨씬 싸다. 브라우저는 이걸 받고 "아, 내 캐시가 아직 맞구나" 하고 보관 중인 본문을 그대로 쓴다. 내용이 바뀌었으면 서버는 `200`과 새 본문을 보낸다.

| 검증 헤더 (서버→클라) | 조건부 요청 헤더 (클라→서버) | 기준      |
| --------------------- | ---------------------------- | --------- |
| ETag                  | If-None-Match                | 내용 지문 |
| Last-Modified         | If-Modified-Since            | 수정 시각 |

**왜 ETag가 Last-Modified보다 정확한가?** 수정 시각은 초 단위라 1초 안에 두 번 바뀌면 구분 못 하고, 내용은 그대로인데 파일을 다시 저장만 해도 시각이 바뀐다. ETag는 내용 자체에서 뽑은 지문이라 "내용이 같으면 같은 값"을 보장한다.

## no-cache vs no-store: 이름이 반대 같은 함정

가장 자주 헷갈리는 지점이다. 이름만 보면 둘 다 "캐시 금지"처럼 들리지만 다르다.

| 지시어    | 저장하나?  | 재사용 전에 검증하나? | 한 줄 의미                        |
| --------- | ---------- | --------------------- | --------------------------------- |
| no-cache  | 저장함     | 매번 검증함           | "캐시하되 매번 확인"              |
| no-store  | 저장 안 함 | 해당 없음             | "아예 남기지 마"                  |
| max-age=0 | 저장함     | 즉시 stale, 보통 검증 | 검증 강제는 `must-revalidate`까지 |

`no-cache`는 캐시를 **하긴 한다.** 다만 쓰기 전에 매번 서버에 검증(`304`인지)을 묻는다. 그래서 "항상 최신을 보장하되, 안 바뀌었으면 본문은 안 받는다"가 된다.

`no-store`는 디스크·메모리 어디에도 **저장 자체를 금지**한다. 은행 잔액, 결제 정보처럼 캐시에 남으면 안 되는 민감 응답에 쓴다.

`max-age=0`은 "받자마자 stale"이라 다음 사용 때 보통 검증을 거치지만, `must-revalidate`가 없으면 캐시가 상황에 따라 stale 응답을 그대로 쓸 여지가 남는다. `no-cache`처럼 "쓰기 전 검증"을 확실히 강제하려면 `max-age=0, must-revalidate`로 둔다.

```http
Cache-Control: no-cache          # 캐시 O, 매번 검증
Cache-Control: no-store          # 캐시 X
```

**왜 이렇게 헷갈리게 지었나?** `no-cache`는 "신선도를 믿고 그냥 캐시에서 꺼내 쓰는 것(use cached copy without checking)을 하지 마라"는 뜻으로 봐야 한다. 즉 "검증 없이 쓰지 마라"이지 "저장하지 마라"가 아니다. 이 한 끗 차이가 사고의 단골 원인이다.

## private vs public: 누구의 캐시인가

응답이 거치는 캐시는 브라우저만이 아니다. 사이 중간에 CDN·프록시 같은 **공유 캐시**가 끼어 있을 수 있다.

```
브라우저 ──── CDN/프록시 ──── 원본 서버
         (공유 캐시)
```

- `private`: 브라우저(개인) 캐시에만 저장. 중간 공유 캐시는 보관 금지.
- `public`: 중간 공유 캐시도 보관 가능.

**왜 이 구분이 사고로 이어지나?** 사용자별로 다른 개인화 응답(예: "안녕하세요, 윤하님" 헤더가 박힌 HTML)에 실수로 `public`을 붙이면, CDN이 그 응답을 통째로 캐시했다가 **다른 사용자에게 그대로 내준다.** 한 사람의 로그인 화면이 다른 사람에게 보이는 식의 정보 유출이다. 인증·개인화가 섞인 응답은 `private`(또는 `no-store`)이 안전하다.

```http
Cache-Control: private, max-age=0, must-revalidate   # 개인화 응답
Cache-Control: public, max-age=31536000, immutable   # 공용 정적 자산
```

## Vary: 같은 URL인데 응답이 여러 개일 때

캐시는 보통 URL을 열쇠(key)로 응답을 보관한다. 그런데 같은 URL이라도 **요청 헤더에 따라 응답이 달라지는** 경우가 있다.

```http
Vary: Accept-Encoding, Accept-Language
```

`Vary`는 "이 헤더들이 다르면 다른 응답으로 취급하라"는 지시다.

- `Accept-Encoding`: 어떤 클라이언트는 gzip 압축본을, 어떤 클라이언트는 비압축본을 받는다. 이걸 구분 안 하면, gzip을 못 푸는 클라이언트에 압축본이 잘못 전달될 수 있다.
- `Accept-Language`: 같은 `/home`이라도 한국어·영어 응답이 다르다. 언어 협상 결과를 캐시 키에 포함시켜야 섞이지 않는다.

**왜 필요한가?** `Vary` 없이 캐시하면 "처음 받은 한 가지 응답"이 모두에게 나간다. 영어 사용자가 먼저 받아 캐시되면, 한국어 사용자가 영어 페이지를 보게 되는 식이다.

## stale-while-revalidate: 일단 보여주고 뒤에서 갱신

만료된 캐시를 검증하는 동안 사용자를 기다리게 하면 화면이 멈칫한다. 이걸 없애는 게 `stale-while-revalidate`다.

```http
Cache-Control: max-age=60, stale-while-revalidate=600
```

해석하면 이렇다.

- 0~60초: 신선함. 캐시 그대로.
- 60~660초: 만료됐지만, **일단 상한 캐시를 즉시 보여주고** 백그라운드에서 조용히 새 응답을 받아 캐시를 갱신한다. 사용자는 기다리지 않는다.
- 660초 이후: 너무 오래됐으니 정상적으로 새로 받는다.

**왜 이 패턴이 중요한가?** 체감 속도와 최신성을 동시에 잡는다. "낡았을 수도 있지만 즉시 보이는 화면"이 "정확하지만 기다려야 하는 화면"보다 대개 낫기 때문이다. 이 사고방식이 그대로 데이터 페칭 라이브러리 이름이 됐다. SWR과 React Query가 쓰는 "stale 데이터를 먼저 보여주고 뒤에서 다시 검증" 전략이 바로 이 헤더에서 따온 것이다. 클라이언트 측 캐시는 [[browser-storage]] 노트와도 이어진다.

## 프론트엔드 배포의 정석 패턴

여기까지가 도구라면, 실제 배포에서 이걸 어떻게 조합하느냐가 핵심이다. 정답에 가까운 조합이 있다.

```http
# 해시 박힌 정적 자산: app.3f9a2c.js, main.7b2e10.css
Cache-Control: public, max-age=31536000, immutable

# 진입점: index.html
Cache-Control: no-cache
```

핵심은 **파일 종류에 따라 정반대 전략**을 쓴다는 것이다.

- **해시 박힌 자산은 영원히 캐시한다.** 빌드 도구는 내용이 바뀌면 파일명의 해시도 바꾼다(`app.3f9a2c.js` → `app.8d1f04.js`). 즉 **내용이 바뀌면 URL이 바뀐다.** 그러면 같은 URL의 캐시가 낡을 일이 없으니 1년(`31536000초`)이고 `immutable`(만료 전엔 검증조차 하지 마라)이고 안전하다.
- **index.html은 항상 검증한다.** 이 파일은 URL이 고정(`/index.html`)인데 내용은 배포마다 바뀐다. `<script src="app.8d1f04.js">`처럼 **새 해시를 가리키도록** 갱신돼야 한다. 그래서 `no-cache`로 매번 검증해 항상 최신 진입점을 받는다.

```
index.html (no-cache, 매번 검증)
   └─▶ <script src="/app.8d1f04.js">  ← 배포 때 해시가 바뀜
            │
            ▼
   app.8d1f04.js (immutable, 1년 캐시)  ← URL이 곧 버전
```

**이 조합이 "배포했는데 옛날 화면이 보여요"를 막는 원리:** 진입점만 항상 신선하면, 그 안의 `<script>` 태그가 늘 최신 해시를 가리킨다. 새 해시 URL은 캐시에 없으니 새로 받고, 안 바뀐 자산은 기존 해시 그대로라 캐시를 재사용한다. 결과적으로 바뀐 것만 정확히 새로 받는다. 반대로 `index.html`까지 길게 캐시하면, 브라우저가 옛 HTML을 붙들고 사라진 옛 해시 파일을 계속 가리켜 화면이 갱신되지 않는다.

## 캐시 버스팅의 역사와 한계

해시 파일명이 표준이 되기 전에는 **쿼리스트링**으로 캐시를 무효화했다.

```html
<script src="/app.js?v=20260605"></script>
```

`?v=...` 값을 바꾸면 URL이 달라 보이니 새로 받는다는 발상이다. 동작은 하지만 한계가 있다.

- 일부 중간 프록시는 쿼리스트링이 붙은 응답을 캐시하지 않거나, 반대로 쿼리를 무시하고 같은 것으로 취급하기도 했다.
- 버전을 손으로 올리는 실수가 잦았다.
- 내용은 그대로인데 버전만 바꾸면 불필요하게 다시 받는다.

그래서 지금은 **내용 해시를 파일명에 박는 방식**이 표준이다. 내용이 같으면 해시가 같아 캐시가 유지되고, 내용이 바뀌어야만 URL이 바뀐다. 캐시 무효화가 빌드 도구에서 자동으로, 정확하게 일어난다. HTTP 버전별 연결 재사용·멀티플렉싱 차이는 [[http-versions]] 노트에서, 요청부터 화면까지의 전체 흐름은 [[url-to-pixels]] 노트에서 다룬다.

## 흔한 오해

- **오해**: "no-cache는 캐시를 안 한다." → **실제**: 캐시는 한다. 다만 쓰기 전에 매번 서버에 검증한다. 저장 금지는 `no-store`다.
- **오해**: "304 응답에도 본문이 들어 있다." → **실제**: `304 Not Modified`는 본문이 비어 있다. 헤더만 오가서 싸다. 본문은 기존 캐시를 재사용한다.
- **오해**: "max-age만 길게 주면 캐싱 끝이다." → **실제**: URL이 고정된 파일(index.html 등)을 길게 캐시하면 배포 후 옛 화면이 박힌다. 고정 URL은 검증 위주, 해시 URL만 길게 캐시해야 한다.
- **오해**: "public이 그냥 더 적극적으로 캐시하는 좋은 옵션이다." → **실제**: 개인화·인증 응답에 `public`을 붙이면 CDN이 한 사람의 응답을 다른 사람에게 내줄 수 있다. 누구의 캐시에 둘지의 문제다.

## 스스로 점검하기

- "신선도"와 "검증"은 각각 어떤 질문에 답하며, 왜 두 단계로 나뉘어 있는가?
- `max-age` 구간에서는 왜 네트워크 요청이 아예 나가지 않는가?
- `304 Not Modified`가 전체 응답을 다시 받는 것보다 싼 이유는 무엇인가?
