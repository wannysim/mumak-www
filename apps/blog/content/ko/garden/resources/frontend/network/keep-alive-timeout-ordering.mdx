로드밸런서 뒤에 Node 서버를 두면, 아무도 설정을 건드리지 않아도 간헐 502가 생길 수 있다. Node의 keep-alive 기본값(5초)과 ALB idle timeout 기본값(60초)이 **서로 반대 방향으로 어긋나 있기 때문**이다. 실제 프로덕션에서 이 조합이 만든 산발적 502를 추적하면서 정리한 노트다.

> 한 줄 요약: **유휴 keep-alive 연결은 "재사용을 결정하는 쪽(앞)"이 아니라 "받는 쪽(뒤)"이 먼저 끊으면 안 된다. 뒤에 선 서버의 idle timeout을 앞 홉보다 항상 길게 — Node라면 `keepAliveTimeout = ALB idle + 5초`, 그리고 `headersTimeout`은 그보다 1초 더.**

## keep-alive는 왜 존재하나

HTTP 요청 하나에는 보이지 않는 준비 비용이 붙는다. TCP 3-way handshake, 그 위에 TLS 협상까지. 요청마다 이걸 반복하면 왕복 지연이 몇 배로 든다.

- **keep-alive 없음** — 한 마디 할 때마다 전화를 걸고, 말하고, 끊는다.
- **keep-alive 있음** — 한 번 걸어놓고 통화를 유지하며 여러 마디를 주고받는다.

그래서 로드밸런서 ↔ 백엔드 사이에는 **연결 풀**이 유지되고, 어떤 사용자의 요청이든 미리 열려 있는 연결에 실려 나간다.

## 문제: 유휴 연결을 언제 끊을지 양쪽이 각자 정한다

"아무 말 없이 통화만 유지 중"인 연결은 자원을 잡아먹으니 언젠가 끊어야 한다. 그런데 이 타이머가 **양쪽에 하나씩** 있다.

| 주체           | 설정                           | 기본값   |
| -------------- | ------------------------------ | -------- |
| Node HTTP 서버 | `server.keepAliveTimeout`      | **5초**  |
| AWS ALB        | `idle_timeout.timeout_seconds` | **60초** |

유휴 연결의 실제 수명은 `min(앞, 뒤)`으로 정해진다. 문제는 수명이 아니라 **누가 먼저 끊느냐**다.

## 왜 "뒤"가 먼저 끊으면 사고가 나는가

연결을 **재사용할지 결정하는 쪽은 앞(ALB)** 이다. 뒤(서버)가 먼저 끊으면, 그 사실이 앞에 전파되기까지의 짧은 틈이 생긴다. 그 틈에 ALB가 죽은 연결에 새 요청을 실으면:

```
서버: 유휴 5초 경과 → 연결 끊음 (FIN)
ALB:  아직 모름 → 그 연결에 요청을 실어 보냄
      → 받을 사람이 없음 → 실패 확정 → 502 생성
```

이 502의 성질이 고약하다.

- **서버는 요청을 받은 적이 없다.** 서버 로그·APM 어디에도 흔적이 없다. "로그에 없는 502"는 이 패턴의 시그니처다.
- **ALB는 이미 보낸 요청을 재시도하지 않는다.** POST는 두 번 실행되면 위험할 수 있어(비멱등) 그냥 502로 반환한다.
- **확률적이다.** "직전 요청 후 5초 이상 놀았던 연결"에 하필 내 요청이 실릴 때만 터진다. 재현이 안 되고, 재시도하면 성공한다.
- 실패까지 **~1초**가 걸리는 경우가 많다. 죽은 연결에 보낸 패킷은 응답이 없고, TCP가 재전송을 시도하는 초기 타임아웃이 1초라서다([[tcp-retransmission-timeout]]).

반대로 **앞이 먼저 끊으면 아무 일도 없다.** ALB는 자기가 끊은 연결을 재사용 후보에서 제거하니까, 죽은 연결에 요청이 실릴 일 자체가 없다.

## 규칙: 타임아웃 피라미드

그래서 원칙은 하나로 수렴한다. **체인의 뒤로 갈수록 idle timeout이 길어져야 한다.**

```
CDN(예: CloudFront)  <  ALB(60초)  <  Node 서버(65초)
        앞                 중간            뒤
```

각 홉에서 "내 뒤에 있는 놈이 나보다 오래 기다린다"가 보장되면, 유휴 연결은 항상 앞에서부터 정리되고 레이스는 구조적으로 사라진다. AWS 공식 권고도 "타깃의 keep-alive timeout을 ALB idle timeout보다 크게"다.

Node에서의 표준 설정:

```ts
const server = app.listen(port);
server.keepAliveTimeout = 65_000; // ALB idle(60초) + 5초 여유
server.headersTimeout = 66_000; // 규칙: keepAliveTimeout보다 항상 크게
```

## headersTimeout은 왜 같이 올리나

Node는 keep-alive 대기 중 도착한 요청의 **헤더 수신 시간**을 `headersTimeout`(기본 60초)으로 잰다. `keepAliveTimeout`만 올리고 이걸 안 올리면 `keepAlive(65s) > headers(60s)` 역전이 생기고, 같은 부류의 조기 절단이 다른 경로로 재발한다. **항상 한 쌍으로** 올린다.

## "너무 길면 문제 아닌가"라는 걱정에 대해

값을 65초든 185초든 크게 잡아도 실질 비용이 거의 없다. **유휴 연결의 실제 수명은 `min(앞, 뒤)` = 앞(ALB) 값이 지배**하기 때문이다. 서버 쪽 값은 "내가 먼저 끊지는 않겠다"는 안전핀이지, 실제로 그 시간만큼 연결을 유지하겠다는 뜻이 아니다.

- 서버에 연결하는 주체가 로드밸런서뿐이라면(보안 그룹으로 제한), 유휴 소켓 수는 LB의 커넥션 풀 크기로 바운드된다 — 태스크당 수십 개, fd와 수 KB 수준.
- ALB는 요청 단위로 타깃을 고르므로 긴 연결이 로드밸런싱을 쏠리게 하지도 않는다.
- 유일한 주의점: 같은 ALB를 **인그레스 그룹**으로 공유하는 경우, 그룹 멤버 하나가 건 `idle_timeout` 속성이 ALB 전체에 적용된다. "우리 매니페스트엔 없으니 60초"라고 단정하지 말고 실효 값을 실측한 뒤 그보다 크게 잡을 것.

## 적정값 계산법 같은 건 없다

트래픽·유저 수로 계산하는 공식은 없다. 이건 용량 튜닝 노브가 아니라 **순서 제약(ordering constraint)** 이다.

1. 앞 홉의 실효 idle timeout을 실측한다 (`aws elbv2 describe-load-balancer-attributes`).
2. 뒤 홉 = 그 값 + 5초.
3. `headersTimeout` = 그 값 + 1초.
4. 끝. 순서만 맞으면 절대값은 중요하지 않다.
