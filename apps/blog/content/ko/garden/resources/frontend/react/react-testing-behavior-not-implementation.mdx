컴포넌트 내부를 통째로 갈아엎었는데 테스트가 전부 통과한다면, 그건 운일까 설계일까? 그리고 어떤 코드베이스는 왜 리팩터링할 때마다 테스트가 우수수 깨질까?

> 한 줄 요약: **테스트는 사용자가 관찰할 수 있는 "동작"을 고정하고 "구현"은 풀어줘야 한다. 그래야 리팩터링의 안전망이 되고, 구현에 묶이면 도리어 리팩터링의 족쇄가 된다.**

## 내부를 갈아엎어도 테스트가 안 깨진 이유

실제로 겪은 일을 일반화해 보자. 진행바(페이지 이동을 알려주는 상단 바), 폴링 훅(주기적으로 서버를 다시 묻는 훅), 캔버스 위젯 세 가지의 내부 구조를 대대적으로 바꿨다. 상태를 어떻게 쪼갰는지, effect(렌더 후 부수효과를 실행하는 React 장치)를 몇 개로 배치했는지를 전부 새로 짰다. 그런데 단위 테스트 738개와 E2E(브라우저에서 실제 사용자처럼 클릭하며 검증하는 테스트) 128개가 한 개도 깨지지 않고 통과했다.

이게 운이 아닌 이유는 단순하다. 그 테스트들은 "내부를 어떻게 만들었는가"를 보고 있지 않았기 때문이다. 그들은 "내부 링크를 누르면 진행바가 보이고, 이동이 끝나면 사라진다" 같은 **밖에서 보이는 사실**만 검사하고 있었다. 내부 구조는 검사 대상이 아니었으니, 내부를 아무리 갈아엎어도 그 사실만 그대로면 테스트는 침묵했다.

> 왜 이렇게 설계했나? 테스트의 목적은 "코드를 안 바꿨음"을 증명하는 게 아니라 "사용자가 보는 결과가 안 바뀌었음"을 증명하는 것이다. 리팩터링은 정의상 "동작은 유지한 채 내부만 바꾸는 일"이다. 그러니 동작만 고정한 테스트는 리팩터링과 충돌하지 않고, 구현까지 고정한 테스트는 리팩터링과 정면충돌한다.

## 구현에 묶인 테스트의 냄새

내가 만든 테스트가 안전망인지 족쇄인지 구분하려면 아래 냄새를 점검하면 된다.

| 냄새                        | 무엇을 검사하나                    | 왜 문제인가                            |
| --------------------------- | ---------------------------------- | -------------------------------------- |
| 내부 함수 호출 스파이       | "이 함수가 불렸는가"               | 같은 결과를 다른 함수로 내도 깨진다    |
| 컴포넌트 state 값 직접 검사 | "내부 상태가 정확히 이 모양인가"   | 상태 구조만 바꿔도 깨진다              |
| `.class`·`nth-child` 셀렉터 | "DOM 구조가 정확히 이 모양인가"    | 마크업만 다듬어도 깨진다               |
| 화면 전체 스냅샷 남발       | "렌더 결과가 글자 하나까지 같은가" | 사소한 변경마다 거대한 diff가 쏟아진다 |

이런 테스트의 공통점은 전부 **"코드를 바꾸지 않았는가"를 검사한다**는 것이다. 그러면 다음 악순환이 돈다.

```
구현 결합 테스트
  │ 리팩터마다 깨진다
  ▼
고치는 비용 > 테스트가 주는 가치
  │
  ▼
"또 빨개졌네" 하고 무시하기 시작
  │
  ▼
빨간 테스트가 일상이 됨 → 진짜 회귀도 묻힘
  │
  ▼
안전망이 사라진다
```

내부 함수가 불렸는지를 스파이로 확인하는 테스트는, 같은 일을 다른 함수로 해내는 순간 깨진다. 사용자는 결과가 같으니 아무것도 달라진 게 없는데 테스트만 비명을 지른다. 이런 거짓 경보가 쌓이면 사람은 테스트를 신뢰하지 않게 되고, 결국 진짜 버그가 섞여 들어와도 알아채지 못한다.

## 동작을 고정하는 테스트의 모양

Testing Library의 안내 원칙은 한 문장으로 요약된다. **"사용자가 찾는 방식으로 찾아라."** 사용자는 `div.list-item:nth-child(2)`로 버튼을 찾지 않는다. "확인이라고 적힌 버튼"을 찾는다. 그래서 셀렉터에 우선순위가 있다.

```
getByRole        ← 1순위: 역할 + 접근 가능한 이름 (사용자·보조기술이 보는 방식)
getByLabelText   ← 2순위: 폼 요소를 라벨로
getByText        ← 3순위: 화면에 보이는 텍스트로
getByTestId      ← 최후의 수단: 위로 안 잡힐 때만
```

이 순서를 지키면 접근성 검증을 **덤으로** 얻는다. `getByRole('button', { name: '저장' })`이 통과한다는 건, 스크린리더 사용자도 그 버튼을 "저장 버튼"으로 인식한다는 뜻이기 때문이다. 구조 결합 셀렉터는 이 이점을 통째로 버린다.

검증 대상은 DOM 모양이 아니라 **시나리오**여야 한다. 진행바라면 "내부 링크를 클릭하면 진행바가 나타나고, 라우트가 바뀌면 사라진다". 훅이라면 "이 입력을 주면 이 반환값·이 상태 전이가 나온다"는 입력-출력 계약이다.

```tsx
// 나쁜 예: 내부 상태와 호출을 들여다본다
it('handleClick이 setLoading(true)를 부른다', () => {
  const setLoading = jest.fn();
  // 내부 구현을 알아야만 쓸 수 있는 테스트 → 내부 바꾸면 깨짐
  // 사용자는 setLoading이 불렸는지 따위 모른다
});

// 좋은 예: 사용자가 보는 동작만 검사한다
it('내부 링크를 누르면 진행바가 나타난다', async () => {
  render(<App />);
  await userEvent.click(screen.getByRole('link', { name: '소개' }));
  expect(screen.getByRole('progressbar')).toBeVisible();
});
```

두 번째 예는 진행바가 불리는 함수가 무엇이든, 상태를 boolean으로 쥐든 객체로 쥐든 상관하지 않는다. 오직 "링크를 누르면 진행바가 보인다"는 사용자 사실만 고정한다. 그래서 내부를 갈아엎어도 살아남는다.

> 왜 `getByTestId`가 최후의 수단인가? `data-testid`는 사용자도 보조기술도 보지 못하는, 오직 테스트만을 위한 표식이다. 이걸 1순위로 쓰면 "사용자가 찾는 방식으로 찾는다"는 원칙이 무너지고, 접근성 검증이라는 공짜 보너스도 사라진다. 진짜로 역할·텍스트로 잡히지 않는 요소에만 escape hatch로 남겨 둔다.

## 그럼 테스트는 언제 고쳐야 하나

"동작 테스트는 절대 안 고친다"가 아니다. 리팩터링이 **계약 자체**를 바꾸면 테스트를 고치는 게 정당하다. 여기서 계약이란 "사용자나 호출자가 의존하는 약속"을 말한다.

예를 들어 어떤 훅이 값이 바뀔 때마다 그 값을 이벤트 payload로 직접 넘겨주다가, 구독자에게는 "바뀌었다"는 신호만 주고 실제 값은 스토어에서 다시 읽어 가는 방식으로 바뀌었다고 하자. 이건 단순 내부 변경이 아니라 **mock(가짜 의존성) 경계가 이동한** 것이다. 테스트가 가짜로 흉내 내야 할 지점이 달라졌으니 테스트도 따라 바뀌어야 한다.

판단 기준은 딱 하나다.

> **"사용자 관점의 동작이 바뀌었는가?"** — 동작은 그대로인데 테스트가 깨졌다면 그건 테스트가 잘못된 것(구현에 묶였던 것)이다. 동작 자체가 바뀌었거나 계약이 이동했다면 테스트 갱신은 정당한 작업이다.

## 도구는 가설, 테스트는 판결

정적 분석기(코드를 실행하지 않고 훑어 문제를 찾는 도구)나 린터의 경고는 **출발점이지 판결이 아니다**. 한 진단 도구가 경고 80건을 쏟아냈는데, 그중 약 1/3이 프레임워크 제약을 모르는 오탐이었다. 가령 OG 이미지(소셜 공유 미리보기 이미지) 렌더러는 인라인 스타일만 지원하는데, 룰은 "인라인 스타일을 쓰지 마라"고 일률적으로 지적하는 식이었다. 룰을 곧이곧대로 따랐다면 멀쩡한 코드를 망가뜨렸을 것이다.

그래서 운용 순서는 이렇게 둔다.

```
[도구] 경고를 던진다 = 가설 제시
  │
  ▼
[사람] 룰 문서를 읽고 코드 맥락으로 판정한다
  │  (프레임워크 제약·의도된 예외인지 확인)
  ▼
[테스트] 수정 후 동작 테스트가 전부 통과 = 최종 판결
```

도구의 경고는 "여기 의심스럽다"는 가설일 뿐이고, 적용 여부의 최종 근거는 "고친 뒤에도 동작 테스트가 전부 통과하는가"다. 도구 자체는 CI(자동 검증 파이프라인)에 걸어 **새 경고의 유입을 차단**하고, 기존에 쌓인 빚은 한 번에 다 갚으려 하지 말고 점진적으로 상환하는 운용이 현실적이다.

## 흔한 오해

- **오해**: 커버리지가 높으면 안전하다. → **실제**: 구현에 묶인 테스트로 채운 커버리지는 리팩터마다 깨지면서도 정작 버그는 못 잡는다. 커버리지는 "얼마나 검사했나"의 양일 뿐, "올바른 것을 검사했나"의 질을 보장하지 않는다.
- **오해**: 스냅샷 테스트는 많을수록 좋다. → **실제**: 스냅샷은 "무엇이 왜 중요한지"를 말해 주지 않는다. 의미를 모르는 채 diff 소음만 늘어나고, 사람은 결국 변경분을 읽지 않고 통째로 갱신해 버린다.
- **오해**: 테스트는 한 번 쓰면 고치면 안 된다. → **실제**: 동작이나 계약이 바뀌면 테스트 갱신은 당연한 작업이다. 손대면 안 되는 건 "동작이 같은데도 깨지는" 구현 결합 테스트뿐이다.
- **오해**: E2E는 느려서 가치가 낮다. → **실제**: E2E는 내부를 전혀 모르는 최종 사용자 관점에서 검증하므로 리팩터 내성이 가장 강하다. 느린 건 사실이라 개수를 가려 써야 하지만, 가치가 낮은 건 아니다.

## 스스로 점검하기

- 내가 마지막에 쓴 테스트는 "코드를 안 바꿨는가"를 검사하는가, "동작이 안 바뀌었는가"를 검사하는가?
- 컴포넌트 내부 상태 구조를 바꿨을 때 그 테스트가 깨진다면, 그건 좋은 신호인가 나쁜 신호인가?
- 셀렉터 우선순위(getByRole > getByLabelText > getByText > getByTestId)가 왜 접근성 검증을 덤으로 주는지 설명할 수 있는가?
- 테스트를 고치는 게 정당한 경우와 정당하지 않은 경우를 "계약"이라는 단어로 구분할 수 있는가?
- 린터 경고를 그대로 따르면 안 되는 상황의 예를 하나 들 수 있는가? 적용 여부의 최종 근거는 무엇인가?
- 커버리지 90%인데 리팩터마다 테스트가 깨진다면, 어디서부터 의심해야 하는가?
