React 16에서 React 팀은 잘 굴러가던 재조정기(reconciler)를 통째로 다시 썼다. 멀쩡한 걸 왜 갈아엎었을까. 이 노트는 그 동기와 Fiber라는 자료구조가 푼 문제를 따라간다.

> 한 줄 요약: **Fiber는 "한 번 시작하면 끝까지 가는 재귀"를 "언제든 멈췄다 재개할 수 있는 루프"로 바꾼 자료구조다. 이 한 가지 변화가 동시성 기능 전부를 가능하게 했다.**

## 왜 멀쩡한 재조정기를 다시 썼나

React 15까지의 재조정기(흔히 "스택 재조정기"라 부른다)는 가상 DOM 트리를 **재귀**로 순회했다. 부모를 처리하면서 자식을 호출하고, 그 자식이 또 자식을 호출하고... 함수 호출 스택이 쌓이는 구조다.

재귀의 문제는 단순하다. **한 번 시작하면 끝까지 간다.** 트리가 1만 개 노드짜리라면, 그걸 다 처리할 때까지 자바스크립트 엔진은 다른 일을 못 한다. 브라우저의 메인 스레드는 하나뿐인데, React가 그 스레드를 통째로 붙잡고 놓아주지 않는 것이다.

```
스택 재조정기 (재귀)
─────────────────────────────────────────────►  메인 스레드
[========= React가 트리 전체 처리 (16ms 초과) =========]
        ↑ 이 사이 클릭/입력/애니메이션 전부 무시됨
```

결과는 이렇다.

- 큰 트리를 업데이트하는 동안 메인 스레드 독점
- 그 사이 들어온 사용자 입력은 처리되지 못하고 대기
- 애니메이션 프레임을 놓쳐서 화면이 뚝뚝 끊긴다(프레임 드랍)

즉 스택 재조정기는 "**중단할 수 없다**"는 게 본질적 한계였다. 이걸 풀려면 작업을 잘게 쪼개고 중간에 멈출 수 있어야 했고, 그러려면 자료구조부터 바꿔야 했다.

## 16.6ms라는 예산

왜 하필 "중단 가능"이 그렇게 중요할까. 화면 주사율이 60Hz인 디스플레이는 1초에 60번 화면을 갱신한다. 즉 한 프레임에 주어진 시간은 `1000ms / 60 ≈ 16.6ms`다.

이 16.6ms 안에 브라우저는 자바스크립트 실행, 스타일 계산, 레이아웃, 페인트를 다 끝내야 한다. 자세한 후반 단계는 [[browser-rendering-pipeline]]에서 다룬다. 자바스크립트가 이 예산을 넘겨 메인 스레드를 붙잡으면, 브라우저는 그 프레임을 그릴 기회를 놓친다. 사람 눈에는 "버벅임"으로 보인다.

여기서 [[js-event-loop]] 관점이 필요하다. 메인 스레드는 한 번에 한 가지 작업만 한다. 클릭 핸들러, 렌더링, 타이머 콜백이 전부 같은 큐에서 차례를 기다린다. React가 긴 렌더링으로 스레드를 점유하면, 그 뒤에 줄 선 클릭 이벤트는 React가 끝날 때까지 실행되지 못한다.

그래서 React가 원한 건 이거다. **"렌더링 작업을 잘게 쪼개고, 짧은 시간 조각(React 스케줄러는 기본 약 5ms)을 다 쓸 때마다 브라우저에게 '급한 일 있으면 먼저 하세요'라고 양보한다."** 16.6ms를 통째로 React가 쓰는 게 아니라, 그보다 훨씬 짧게 끊어서 한 프레임 안에서도 브라우저가 끼어들 틈을 남긴다. 이게 가능하려면 재귀를 버려야 했다.

## Fiber 노드 = 작업 단위이자 연결 리스트

재귀를 멈췄다 재개하려면, 현재 어디까지 했는지를 **데이터로** 들고 있어야 한다. 함수 호출 스택은 멈추면 사라지지만, 객체로 들고 있는 정보는 안 사라진다. 그래서 React는 컴포넌트마다 **Fiber 노드**라는 자바스크립트 객체를 하나씩 만든다.

Fiber 노드 하나는 두 가지 역할을 한다.

1. **하나의 작업 단위(unit of work)** — "이 컴포넌트를 처리한다"는 할 일 하나
2. **트리를 표현하는 연결 리스트의 노드** — 트리 구조를 자식/형제/부모 포인터로 들고 있다

핵심은 트리를 표현하는 방식이다. 부모-자식 관계를 배열이 아니라 **세 개의 포인터**로 표현한다.

```
        ┌─────────┐
        │  App    │
        └─────────┘
          │ child
          ▼
        ┌─────────┐  sibling   ┌─────────┐
        │ Header  │──────────► │  Main   │
        └─────────┘            └─────────┘
          ▲ return               │ child
          │                      ▼
       (부모로 복귀)          ┌─────────┐
                             │  List   │
                             └─────────┘
```

| 포인터    | 가리키는 곳            |
| --------- | ---------------------- |
| `child`   | 첫 번째 자식 fiber     |
| `sibling` | 다음 형제 fiber        |
| `return`  | 부모 fiber (복귀 지점) |

이 세 포인터 덕분에 트리 순회를 **재귀 대신 while 루프**로 표현할 수 있다.

```js
// 개념 코드: 재귀가 아니라 루프다
let next = root;
while (next !== null) {
  next = performUnitOfWork(next); // fiber 하나 처리하고 다음 fiber 반환
  if (shouldYield()) break; // 시간 조각(약 5ms) 다 썼으면 여기서 멈춤
}
// break로 빠져나와도 next에 "다음 할 일"이 남아 있다 → 나중에 재개
```

루프는 매 반복마다 `shouldYield()`로 "시간 다 됐는지" 확인하고, 다 됐으면 빠져나온다. 이때 `next` 변수에 "다음에 처리할 fiber"가 그대로 남아 있으므로, 브라우저에게 양보했다가 다시 이 루프로 돌아와 이어서 처리하면 된다. **재귀로는 절대 못 하던 "멈췄다 재개"가 이렇게 가능해진다.**

## 두 단계로 나눈 이유: 렌더 단계와 커밋 단계

작업을 중간에 멈추려면, 멈춰도 안전한 구간과 안전하지 않은 구간을 갈라야 한다. DOM을 절반만 바꿔놓고 멈추면 화면이 깨지니까. 그래서 React는 한 번의 업데이트를 두 단계로 쪼갰다.

```
┌────────────── 렌더 단계 ──────────────┐  ┌──── 커밋 단계 ────┐
  무엇이 바뀌었는지 fiber 트리에서 계산      계산 결과를 DOM에 한 번에 반영
  - 중단 가능 / 재시작 가능 / 폐기 가능       - 동기, 중단 불가
  - 화면에 아직 아무것도 안 바뀜              - effect 실행
└───────────────────────────────────────┘  └──────────────────┘
```

**렌더 단계**는 "무엇이 바뀌었는가"를 fiber 트리 위에서 계산하기만 한다. 화면에는 아직 아무 변화도 없다. 그래서 중간에 멈춰도, 더 급한 업데이트가 들어와 지금 작업을 통째로 버리고 다시 시작해도 사용자는 모른다.

바로 이 점 때문에 **렌더 단계에서 실행되는 코드(컴포넌트 함수 본문)는 부수효과가 없어야 한다.** React가 같은 컴포넌트를 두 번 호출하거나, 계산하다 버리고 다시 호출할 수 있기 때문이다. StrictMode가 개발 모드에서 컴포넌트를 **일부러 두 번 호출**하는 이유가 여기 있다. 두 번 불러도 결과가 같은지, 즉 부수효과에 의존하지 않는지를 미리 잡아내려는 것이다.

**커밋 단계**는 렌더 단계가 계산한 결과를 실제 DOM에 **한 번에, 동기적으로** 반영한다. 이 단계는 중단되지 않는다. DOM을 절반만 바꾼 어정쩡한 상태를 사용자에게 절대 보여주지 않기 위해서다. `useLayoutEffect`나 ref 부착도 이 단계에서 일어난다.

## 더블 버퍼링: current와 workInProgress

렌더 단계에서 새 트리를 계산하는 동안, 화면에는 이전 트리가 멀쩡히 보여야 한다. 그래서 React는 fiber 트리를 항상 **두 벌** 유지한다. 게임 그래픽의 더블 버퍼링과 같은 아이디어다.

| 트리             | 역할                              |
| ---------------- | --------------------------------- |
| `current`        | 지금 화면에 그려져 있는 트리      |
| `workInProgress` | 렌더 단계에서 새로 계산 중인 트리 |

두 트리의 짝이 되는 fiber는 서로를 `alternate` 포인터로 가리킨다. 작업은 전부 `workInProgress`에서 일어나므로, 중간에 멈추거나 버려도 `current`(=화면)는 안전하다. 계산이 끝나면 커밋 단계에서 포인터만 바꿔 `workInProgress`를 새로운 `current`로 만든다. **이 "포인터 교체"가 곧 화면 갱신이다.** 매번 트리를 새로 할당하지 않고 두 벌을 번갈아 재활용하니 메모리 압박도 줄어든다.

## 우선순위: lanes

작업을 쪼갤 수 있게 되자, 자연스럽게 다음 질문이 따라온다. "쪼갠 조각들 중 뭘 먼저 할까?" 모든 업데이트가 똑같이 급한 건 아니다.

- 버튼 클릭에 대한 시각적 응답 → **아주 급함** (사람이 즉시 알아챔)
- 검색어 입력에 따른 결과 목록 갱신 → 덜 급함 (조금 늦어도 됨)
- 화면 밖(off-screen) 콘텐츠 준비 → 가장 안 급함

React는 이런 우선순위를 **lanes**라는 개념으로 표현한다. 각 업데이트에 "차선(lane)"을 배정하고, 급한 차선의 작업을 먼저 처리한다. 비트마스크로 구현되어 여러 우선순위를 효율적으로 묶고 비교한다.

핵심은 이거다. 급한 업데이트가 들어오면, 진행 중이던 덜 급한 렌더 작업을 **중단하고**(렌더 단계라 안전하다) 급한 것부터 처리한 뒤, 덜 급한 작업을 다시 시작한다. 중단 가능한 fiber 구조가 없으면 애초에 불가능한 전략이다.

## 이 기반이 열어준 것들

Fiber라는 "중단 가능한 작업 단위 + 우선순위" 토대 위에서 우리가 쓰는 동시성 기능들이 나왔다. 전부 "덜 급한 작업을 미루거나 끊을 수 있다"는 같은 능력의 다른 얼굴이다.

- **자동 배칭(automatic batching)** — 여러 state 변경을 한 번의 렌더로 묶는다. 자세한 메커니즘은 [[react-state-batching-and-rerender]]에서 다룬다.
- **`startTransition`** — "이 업데이트는 급하지 않다"고 직접 표시해 낮은 lane으로 보낸다.
- **`useDeferredValue`** — 값의 갱신을 한 박자 늦춰, 급한 입력 응답을 막지 않게 한다.
- **`Suspense`** — 자식이 준비될 때까지 렌더를 "보류"하고 폴백을 보여준다. 렌더 단계를 멈췄다 재개할 수 있어야 성립한다.

## 비유: 두 요리사

스택 재조정기는 **주문 하나를 처음부터 끝까지 다 만들어야만 손을 떼는 요리사**다. 10인분 코스를 조리하는 30분 동안 새 손님이 와서 물을 달라 해도 거들떠보지 않는다.

Fiber 재조정기는 **틈틈이 주변을 살피는 요리사**다. 한 가지 작업(fiber 하나)을 끝낼 때마다 고개를 들어 "급한 일 없나?" 확인하고(`shouldYield`), 손님이 손을 들었으면(클릭/입력) 하던 걸 잠시 멈추고 응대한 뒤 다시 조리로 돌아온다. 음식이 늦게 나올 수는 있어도, 손님은 "무시당하는 느낌"을 받지 않는다. React가 16에서 사려 한 건 바로 이 **반응성**이다.

## 흔한 오해

- **오해: Fiber는 가상 DOM을 대체한 것이다.**
  실제: Fiber는 가상 DOM을 없앤 게 아니라, 그것을 다루는 **재조정 방식**을 재귀에서 중단 가능한 루프로 바꾼 것이다. 가상 DOM과 재조정의 기본 개념은 [[react-virtual-dom-and-reconciliation]]에 따로 있다.

- **오해: Fiber 도입만으로 앱이 자동으로 빨라진다.**
  실제: Fiber는 총 작업량을 줄이지 않는다. 같은 양의 일을 **쪼개서 양보**할 뿐이다. 빨라지는 게 아니라 **끊김이 줄어 반응성이 좋아지는** 것이다. 오히려 쪼개는 오버헤드 때문에 단일 작업의 총 시간은 약간 늘 수도 있다.

- **오해: 렌더 단계도 동기라서 중간에 멈출 수 없다.**
  실제: 멈출 수 있는 건 렌더 단계뿐이다. 멈출 수 없는(동기) 단계는 DOM을 반영하는 **커밋 단계**다. 둘을 반대로 기억하기 쉽다.

- **오해: StrictMode의 이중 호출은 버그이거나 성능 낭비다.**
  실제: 개발 모드에서만 일부러 두 번 호출해, 렌더 단계 코드가 부수효과에 의존하지 않는지를 검출하려는 의도적 장치다. 프로덕션 빌드에서는 한 번만 호출된다.

## 스스로 점검하기

- 스택 재조정기의 "재귀"가 왜 사용자 입력 무반응으로 이어졌는지 설명할 수 있는가?
- 16.6ms라는 숫자는 어디서 나왔고, [[js-event-loop]]의 단일 스레드와 어떻게 엮이는가?
- Fiber 노드의 `child` / `sibling` / `return` 세 포인터가 "멈췄다 재개"를 어떻게 가능하게 하는가?
- 렌더 단계와 커밋 단계 중 어느 쪽이 중단 가능하며, 그 차이가 왜 안전성과 직결되는가?
- StrictMode가 컴포넌트를 두 번 호출하는 것과 "렌더 단계는 부수효과가 없어야 한다"는 규칙은 어떻게 연결되는가?
- `current`와 `workInProgress` 두 트리를 굳이 유지하는 이유는 무엇인가?
