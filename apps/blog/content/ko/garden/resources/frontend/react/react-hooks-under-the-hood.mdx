`useState`는 함수가 끝나도 값을 기억한다. 함수 컴포넌트는 매 렌더마다 처음부터 다시 실행되는데, 그 값은 대체 어디에 저장되고 React는 수많은 훅 중에 어느 게 어느 값인지 어떻게 구별하는가.

> 한 줄 요약: **훅은 이름이 아니라 "호출 순서"로 구별된다. 그 순서가 매 렌더 동일해야 하므로 조건문 안에서 쓰면 안 된다.**

## 함수는 끝나는데 상태는 왜 남는가

함수 컴포넌트는 말 그대로 함수다. 렌더링이란 React가 그 함수를 호출하는 일이고, 호출이 끝나면 함수 안의 지역 변수는 전부 사라진다. 그런데 `count`는 다음 렌더에서도 멀쩡히 살아 있다.

```jsx
function Counter() {
  const [count, setCount] = useState(0); // 매 렌더마다 다시 실행되는 줄
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

핵심은 **값이 컴포넌트 함수 안에 저장되는 게 아니라는 것**이다. 함수는 매번 비워지고 다시 채워지는 일회용 양식지일 뿐이다. 실제 데이터는 React 바깥의 다른 곳에 보관되고, 렌더링 때마다 그 곳에서 "이 컴포넌트의 첫 번째 상태"를 꺼내 양식지에 다시 적어 넣는다.

그 "다른 곳"이 바로 fiber 노드다.

## 상태의 진짜 위치: fiber 노드의 훅 리스트

React는 각 컴포넌트 인스턴스마다 fiber라는 내부 객체를 하나씩 갖고 있다. 상태는 컴포넌트 함수가 아니라 이 fiber에 매달린 **연결 리스트(linked list)**에 저장된다. fiber 구조 자체는 [[react-fiber-architecture]]에서 더 다루고, 여기서는 "훅이 어디 사는가"만 본다.

```
Counter의 fiber
  └─ memoizedState ─▶ [hook0] ─▶ [hook1] ─▶ [hook2] ─▶ null
                       useState   useEffect  useRef
```

훅을 호출할 때마다 React는 이 리스트에서 노드를 하나씩 순서대로 가져온다. `useState`를 처음 호출하면 `hook0`, 그다음 훅 호출은 `hook1`, 이런 식이다. 양식지(함수)는 매번 새로 그려지지만, 칸에 채울 값은 이 리스트에서 순서대로 읽어 온다.

여기서 결정적인 사실이 하나 나온다. **React는 훅에 이름을 붙이지 않는다.** `useState`를 `count`라는 이름으로 받았든 `total`로 받았든 React는 모른다. React가 아는 건 오직 "이번 렌더에서 몇 번째로 호출된 훅인가"뿐이다.

## 왜 이름이 아니라 순서인가

이름으로 매칭하려면 React가 변수명을 들여다봐야 하는데, 함수 호출 결과를 어떤 변수에 담을지는 순전히 사용자 코드의 일이라 React 입장에서 접근할 방법이 없다. 그래서 가장 단순하고 빠른 방법을 택했다. **호출 순서를 인덱스로 쓴다.**

이 설계의 대가가 바로 훅 규칙이다. 순서로 매칭하니까, 매 렌더의 호출 순서가 한 치도 어긋나면 안 된다. "훅은 항상 컴포넌트 최상위에서, 같은 순서로 호출하라"는 규칙은 미관이나 컨벤션이 아니라 **이 인덱스 매칭이 깨지지 않게 하는 필수 조건**이다.

## 조건문 안에 넣으면 무너지는 과정

말로만 들으면 와닿지 않으니 직접 시뮬레이션해 본다.

```jsx
function Form({ isLoggedIn }) {
  if (isLoggedIn) {
    const [name, setName] = useState(''); // 조건부 훅 (금지)
  }
  const [email, setEmail] = useState('');
  const [theme, setTheme] = useState('light');
  // ...
}
```

`isLoggedIn`이 처음엔 `true`, 다음 렌더에 `false`가 됐다고 하자. React는 인덱스로만 매칭하므로 이렇게 어긋난다.

| 호출 순서 | 1번째 렌더 (`true`) | 2번째 렌더 (`false`) |
| --------- | ------------------- | -------------------- |
| index 0   | name 상태           | email 상태           |
| index 1   | email 상태          | theme 상태           |
| index 2   | theme 상태          | (없음)               |

2번째 렌더에서 `email`을 호출했는데 React는 index 0을 돌려주고, 그 자리엔 1번째 렌더 때 `name`이 차지하던 칸이 있다. `email`이라는 이름으로 받았지만 안에 든 값은 옛 `name`이다. 모든 상태가 한 칸씩 밀린다. 그래서 React는 아예 `Rendered fewer hooks than expected` 같은 에러를 던지며 막는다. 순서가 곧 정체성이라, 순서가 흔들리는 순간 어느 값이 누구 것인지 알 수 없게 되는 것이다.

이래서 조건은 훅 바깥에 둬야 한다. 훅은 항상 부르고, 조건은 훅이 돌려준 값으로 처리한다.

## 미니 구현: useState를 30줄로 흉내 내기

멘탈 모델을 굳히는 가장 빠른 길은 직접 만들어 보는 것이다. 배열 하나와 인덱스 하나면 `useState`의 뼈대가 나온다.

```js
let hooks = []; // fiber의 훅 리스트 역할
let cursor = 0; // 이번 렌더에서 몇 번째 훅인지

function useState(initial) {
  const i = cursor; // 이 훅이 쓸 칸을 순서로 확정
  hooks[i] = hooks[i] ?? initial; // 첫 렌더면 초기값, 아니면 기존 값 유지
  const setState = next => {
    hooks[i] = next; // 닫아둔 i 덕분에 자기 칸만 갱신
    render(); // 다시 그리기 트리거
  };
  cursor++; // 다음 훅을 위해 커서 전진
  return [hooks[i], setState];
}

function render() {
  cursor = 0; // 매 렌더 시작 시 커서를 0으로 리셋
  App(); // 컴포넌트 함수 다시 실행
}
```

`render`가 매번 `cursor`를 0으로 되돌리고 컴포넌트를 다시 실행한다는 점이 핵심이다. 훅이 같은 순서로 호출되기만 하면 `cursor`가 같은 칸을 정확히 다시 가리킨다. 조건문으로 호출을 건너뛰면 그 순간부터 `cursor`가 틀어지고, 위 표처럼 칸이 어긋난다. `setState` 안에서 `i`가 살아 있는 이유는 클로저 덕분인데, 이건 바로 다음 주제로 이어진다.

## 매 렌더는 새로운 클로저

컴포넌트 함수가 다시 실행될 때마다 그 안의 `props`, `state`, 이벤트 핸들러는 **그 렌더 시점의 값을 가둔 새로운 클로저**로 만들어진다. 즉 각 렌더는 자기만의 `count`를 본다. 1번 렌더의 핸들러는 영원히 1번 렌더의 `count`를, 2번 렌더의 핸들러는 2번 렌더의 `count`를 본다. 클로저 개념 자체는 [[js-closure-and-scope]]에서 더 깊이 다룬다.

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  // 이 함수는 매 렌더마다 새로 만들어지고, 만들어진 시점의 count를 가둔다
  const handleClick = () => console.log(count);
  return <button onClick={handleClick}>{count}</button>;
}
```

이게 React의 의도다. UI = f(state)라는 모델에서, 각 렌더는 특정 state에 대응하는 화면의 스냅샷이고 그 화면의 핸들러도 같은 스냅샷을 봐야 일관적이다. 문제는 이 스냅샷이 의도치 않게 "오래 살아남을" 때 생긴다.

## stale closure: 옛 state를 붙드는 버그

`setInterval`이나 한 번만 등록하는 이벤트 리스너 안에서, 첫 렌더의 클로저가 그대로 굳어 옛 state를 계속 보는 버그를 stale closure라고 한다.

```jsx
function Timer() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1); // 이 count는 영원히 0 (첫 렌더의 스냅샷)
    }, 1000);
    return () => clearInterval(id);
  }, []); // 빈 배열: effect는 첫 렌더 때 딱 한 번만 실행
  return <p>{count}</p>;
}
```

빈 의존성 배열 때문에 effect는 첫 렌더에서 한 번만 돈다. 그 안의 콜백은 첫 렌더의 클로저라 `count`가 영원히 0이다. 매초 `setCount(0 + 1)`을 부르니 화면은 0에서 1로 한 번 갔다가 멈춘다.

해결책은 두 가지다.

```jsx
// 1) 함수형 업데이트: 클로저의 count 대신 React가 쥔 최신 값을 받는다
setCount(prev => prev + 1);

// 2) ref로 최신 값을 들고 다닌다 (effect 재실행 없이)
const countRef = useRef(0);
countRef.current = count; // 매 렌더 최신값 동기화
// 콜백 안에서 countRef.current를 읽으면 항상 최신
```

함수형 업데이트는 클로저에 갇힌 값을 아예 참조하지 않고, "이전 값에서 1을 더해 달라"는 명령만 React에 넘긴다. 그래서 클로저가 낡았어도 결과는 항상 맞는다. 이 갱신이 모여 어떻게 리렌더로 이어지는지는 [[react-state-batching-and-rerender]]에서 다룬다.

## useRef는 왜 리렌더를 일으키지 않는가

`useRef`는 매 렌더 **같은 객체를 계속 돌려준다**. `{ current: ... }`라는 상자 하나를 fiber에 한 번 만들어 두고, 이후 렌더에서는 그 동일한 상자의 참조를 그대로 반환한다.

```jsx
const ref = useRef(0);
ref.current = 5; // 상자 내용물만 바꿈, 상자 자체는 그대로
```

`current`를 바꿔도 React는 그 변경을 추적하지 않는다. 상태가 아니라 그냥 가변 상자이기 때문이다. 그래서 리렌더 없이 값을 들고 다니기에 적합하다. 반대로 `setState`는 호출될 때마다 React에게 "새 값이니 다시 그려라"라고 알린다.

리렌더를 일으킬지 말지를 가르는 비교 기준도 알아둘 만하다. `useEffect`의 의존성 배열은 이전 값과 새 값을 **`Object.is`로 비교**한다. 원시값은 값으로 같으면 같다고 보지만, 객체나 배열은 **참조가 다르면 다른 것으로 본다**. 그래서 매 렌더 새로 만든 객체를 의존성에 넣으면 effect가 매번 다시 돈다. 이 함정을 피하는 메모이제이션 전략은 [[react-memoization-strategy]]로 이어진다.

## 흔한 오해

**오해: 상태는 컴포넌트 함수 안에 저장된다.**
실제: 함수는 매 렌더 비워진다. 상태는 fiber 노드의 훅 리스트에 산다. 함수는 그걸 꺼내 쓰는 양식지일 뿐이다.

**오해: React는 변수 이름으로 훅을 구별한다.**
실제: 이름은 전혀 보지 않는다. 오직 호출 순서(인덱스)로만 매칭한다. 그래서 순서가 흔들리면 안 된다.

**오해: 조건부 훅 금지는 그냥 lint가 잡는 스타일 규칙이다.**
실제: 인덱스 매칭이 깨지면 상태가 한 칸씩 밀려 다른 훅의 값을 받는다. 동작이 실제로 망가지는 근본 제약이다.

**오해: stale closure는 React 버그다.**
실제: 매 렌더가 자기 스냅샷을 본다는 정상 동작의 부작용이다. 함수형 업데이트나 ref로 의도적으로 최신값을 가져와야 한다.

## 스스로 점검하기

- 함수 컴포넌트가 매 렌더 다시 실행되는데도 `useState` 값이 유지되는 이유는 무엇인가
- React가 훅을 구별하는 유일한 기준은 무엇이고, 그래서 어떤 규칙이 강제되는가
- 조건문 안에서 훅을 호출하면 1번째와 2번째 렌더 사이에서 정확히 무엇이 어긋나는가
- 배열과 인덱스만으로 `useState`를 흉내 낼 때 `cursor`를 매 렌더 0으로 리셋해야 하는 이유는 무엇인가
- `setInterval` 안에서 `count`가 0에 멈추는 stale closure는 왜 생기고, 두 가지 해결책은 각각 무엇을 다르게 하는가
- `useRef`가 리렌더를 일으키지 않는 이유와, `useEffect` 의존성 배열이 객체를 매번 다르다고 보는 이유는 무엇인가
