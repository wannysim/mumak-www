"빠른 사이트"라는 말은 사람마다 다르게 느낀다. Core Web Vitals는 그 모호한 체감을 숫자 세 개로 못박은 시도다. 이 노트는 그 세 숫자가 각각 무엇을 잡아내고, 왜 그렇게 설계됐는지를 정리한다.

> 한 줄 요약: **로딩(LCP)·반응(INP)·안정성(CLS) 세 가지 질문으로 "빠름"을 쪼갰고, 각 숫자는 렌더링 파이프라인의 특정 단계가 사용자에게 새어 나온 흔적이다.**

## 왜 숫자가 필요했나

"이 사이트 빠르네"는 합의가 안 된다. 누군가는 첫 글자가 뜨는 순간을 빠르다고 하고, 누군가는 버튼이 눌리는 순간을 본다. 체감은 주관적이라 개선의 목표가 될 수 없다.

그래서 오래전부터 지표를 썼는데, 문제는 **옛 지표가 사용자 경험과 어긋났다**는 점이다. 대표적인 게 `load` 이벤트다.

```js
window.addEventListener('load', () => {
  // 모든 리소스(이미지·스크립트·CSS)가 다 받아진 시점
  console.log('load 완료');
});
```

`load`는 "마지막 리소스까지 다 받은 시점"이다. 그런데 사용자는 마지막 트래킹 픽셀이 도착하는지 신경 쓰지 않는다. 화면 위쪽 콘텐츠는 이미 다 보이는데 `load`는 한참 뒤에 찍히기도 하고, 반대로 `load`는 끝났는데 메인 이미지가 아직 안 뜨기도 한다. 측정값과 체감이 따로 논 것이다.

Core Web Vitals의 발상은 단순하다. **사용자가 실제로 느끼는 질문을 먼저 정하고, 그 질문에 답하는 순간을 측정하자.** 질문은 셋이다.

| 질문              | 지표 | 좋음 기준  |
| ----------------- | ---- | ---------- |
| 로딩이 빠른가     | LCP  | 2.5초 이하 |
| 반응이 빠른가     | INP  | 200ms 이하 |
| 화면이 안정적인가 | CLS  | 0.1 이하   |

## LCP — 로딩이 빠른가

LCP(Largest Contentful Paint)는 **뷰포트 안에서 가장 큰 콘텐츠 요소가 그려진 시점**이다. 첫 픽셀(FCP)이 아니라 "가장 큰 것"을 보는 이유가 핵심이다. 사용자가 "페이지가 떴다"고 느끼는 건 보통 메인 이미지나 헤드라인이 보일 때지, 작은 로고 하나 떴을 때가 아니다. 큰 요소 = 페이지의 주제일 확률이 높다.

LCP 요소가 될 수 있는 것은 정해져 있다.

- `<img>`, `<image>`(SVG 내부)
- `background-image`를 가진 블록
- `<video>`의 포스터 이미지
- 텍스트 블록(가장 큰 텍스트 묶음)

왜 느려지는지를 따라가 보면 결국 **그 큰 요소가 화면에 닿기까지의 경로**가 전부다.

```
서버 응답(TTFB) → HTML 파싱 → LCP 리소스 발견 → 다운로드 → 디코드 → 페인트
```

이 경로의 어느 칸이든 늦으면 LCP가 밀린다. 서버 응답이 느리면(TTFB) 출발선부터 늦고, LCP 이미지가 페이지 한참 아래에서 `<img>`로 늦게 발견되면 다운로드도 늦게 시작된다. 폰트도 한몫한다. 텍스트가 LCP 요소인데 웹폰트가 늦게 오면, 그 텍스트는 폰트가 도착할 때까지 안 그려지거나(invisible) 나중에 다시 그려진다.

그래서 LCP 개선의 큰 방향은 **리소스 우선순위**다. LCP 이미지에 `fetchpriority="high"`를 주고, `<link rel="preload">`로 먼저 가져오게 하고, 게으른 로딩(`loading="lazy"`)을 LCP 요소에는 절대 걸지 않는 식이다. 스크립트와 리소스가 서로 우선순위를 다투는 구조는 [[browser-script-loading]]에서 더 깊게 다룬다.

## INP — 반응이 빠른가

INP(Interaction to Next Paint)는 **사용자 입력이 들어온 뒤 다음 프레임이 그려지기까지 걸린 시간**이다. 클릭·탭·키 입력을 했는데 화면이 멈칫하는 그 답답함을 숫자로 잡는다.

```
입력 발생 → 이벤트 핸들러 실행 → 렌더링 작업 → 다음 페인트
└──────────────── 이 전체 구간이 INP ────────────────┘
```

범인은 거의 항상 **긴 JS 태스크**다. 브라우저의 메인 스레드는 한 번에 하나의 태스크만 돌린다. 클릭 이벤트 핸들러가 50ms짜리 무거운 계산을 돌고 있으면, 그동안 화면을 다시 그릴 틈이 없다. 이 한 스레드를 누가 점유하느냐의 문제라 [[js-event-loop]]를 알면 INP가 한결 또렷해진다.

```js
button.addEventListener('click', () => {
  // 메인 스레드를 100ms 점유 → 그동안 화면 멈춤 → INP 악화
  const result = heavySyncWork();
  render(result);
});
```

### 왜 FID를 버리고 INP로 갔나

원래 이 자리에는 FID(First Input Delay)가 있었다. FID는 **첫 입력**이 핸들러에 들어가기까지의 지연만 쟀다. 두 가지 한계가 있었다.

- **첫 입력만** 본다. 페이지 로드 직후 한 번만 측정하니, 그 뒤로 앱을 쓰는 내내 버벅여도 FID는 멀쩡하게 나왔다.
- **지연만** 보고 처리·페인트는 안 본다. 핸들러가 빨리 시작만 하면, 그 안에서 아무리 오래 걸려도 FID는 좋게 나왔다.

INP는 이 둘을 메운다. 페이지 생애 동안 **모든 상호작용**을 보고(사실상 가장 느린 쪽), 입력부터 **다음 페인트까지** 전체를 잰다. "첫인상"이 아니라 "내내 반응하는가"로 질문이 바뀐 셈이다.

INP 개선의 큰 방향은 **태스크 쪼개기**다. 긴 작업을 잘게 나눠 중간에 브라우저가 페인트할 틈을 주는 것이다.

```js
button.addEventListener('click', async () => {
  render(firstChunk); // 급한 것 먼저 그리고
  await scheduler.yield(); // 메인 스레드를 잠깐 양보
  render(restChunk); // 나머지는 다음 틈에
});
```

## CLS — 화면이 안정적인가

CLS(Cumulative Layout Shift)는 **예고 없이 일어난 레이아웃 점프의 누적량**이다. 글을 읽으려는데 위에서 배너가 끼어들며 본문이 아래로 밀리거나, 누르려던 버튼이 광고 때문에 갑자기 이동해 엉뚱한 걸 누른 경험. 그 짜증을 점수화한다.

CLS는 시간이 아니라 **비율 점수**다. 대략 "이동한 영역이 화면에서 차지하는 비율 × 이동한 거리 비율"을 누적한다. 그래서 단위가 없고 0.1 같은 소수다.

흔한 원인 셋은 전부 **공간을 미리 잡아두지 않은 것**이다.

```html
<!-- 나쁨: 크기가 없어 이미지가 도착하면 그 자리가 갑자기 벌어진다 -->
<img src="hero.jpg" />

<!-- 좋음: width/height(또는 aspect-ratio)로 자리를 먼저 예약 -->
<img src="hero.jpg" width="800" height="450" />
```

- **이미지 크기 미지정**: 로드 전엔 높이 0이다가 도착 순간 본문을 밀어낸다.
- **동적 삽입 배너·광고**: 이미 그려진 콘텐츠 위에 끼어들면 아래가 통째로 내려간다.
- **웹폰트 스왑**: 대체 폰트로 그렸다가 진짜 폰트로 바뀔 때 글자 폭이 달라지며 줄이 재배치된다.

개선의 큰 방향은 한마디로 **공간 예약**이다. 이미지·임베드에는 치수나 `aspect-ratio`를 주고, 광고 슬롯은 최소 높이를 미리 확보하고, 폰트는 `size-adjust`로 대체 폰트와 폭을 맞춘다. 단, 사용자 입력 직후 500ms 안의 이동은 "사용자가 유발한 것"으로 보고 CLS에서 제외한다. 메뉴를 펼쳐 콘텐츠가 밀리는 건 의도된 이동이기 때문이다.

## 세 지표는 파이프라인의 어디서 나오나

세 숫자는 따로 노는 게 아니라 [[browser-rendering-pipeline]]의 서로 다른 구간이 사용자에게 새어 나온 흔적이다.

```
요청 → [응답·파싱·리소스] → [Layout·Paint] → 화면 → [입력 → 다음 Paint]
          └── LCP ──┘            └─ CLS ─┘              └──── INP ────┘
          (얼마나 빨리 그렸나)  (그린 게 흔들렸나)   (다시 그리는 게 빠른가)
```

- **LCP**는 첫 페인트까지의 경로(응답·다운로드·디코드·페인트) 길이를 잰다.
- **CLS**는 일단 그려진 뒤 Layout이 의도치 않게 다시 일어난 양을 잰다.
- **INP**는 입력 후 다음 Paint까지, 즉 메인 스레드가 얼마나 빨리 풀려 다시 그리는지를 잰다.

그래서 개선 도구도 다르다. LCP는 리소스 우선순위, CLS는 레이아웃 안정성, INP는 메인 스레드 점유 시간으로 접근한다.

## lab과 field, 왜 숫자가 다른가

같은 페이지인데 Lighthouse는 LCP가 1.8초로 나오고 실제 데이터는 4초로 나오는 일이 흔하다. 둘은 **측정 환경 자체가 다르기 때문**이다.

| 구분      | lab(실험실)              | field(현장)              |
| --------- | ------------------------ | ------------------------ |
| 대표 도구 | Lighthouse               | CrUX(실사용자 데이터)    |
| 환경      | 통제된 1회 실행          | 실제 사용자들의 누적     |
| 기기·망   | 고정된 가상 조건         | 제각각(저가폰·느린 3G도) |
| INP       | 측정 불가(상호작용 없음) | 측정 가능                |
| 대푯값    | 단일 측정                | 75 퍼센타일              |

lab은 깨끗한 통제 환경에서 한 번 돌린다. 재현 가능하고 디버깅에 좋지만, 내 빠른 노트북 기준이라 현실보다 낙관적이다. field는 진짜 사용자들이 다양한 기기로 쓴 결과를 모은 것이라 현실을 반영하지만, 내가 통제할 수 없고 노이즈가 많다.

field에서 **75 퍼센타일**을 쓰는 게 의미심장하다. 평균이 아니라 "느린 쪽 4명 중 1명"을 기준선으로 잡는다는 뜻이다. 평균은 소수의 빠른 사용자가 끌어올려 가리기 쉽다. 4분의 3의 사용자가 겪는 경험을 보장하자는 게 75 퍼센타일의 뜻이고, 그래서 lab 단일 수치보다 항상 박하게 나온다. 둘이 다른 건 버그가 아니라 설계다. lab으로 원인을 찾고 field로 진짜 효과를 확인하는 식으로 역할을 나눈다.

## 흔한 오해

**오해: LCP는 페이지에서 가장 먼저 그려진 요소다.**
실제로는 가장 **큰** 콘텐츠 요소다. 첫 페인트는 FCP라는 별도 지표이고, LCP는 보통 그보다 뒤다. 작은 로고가 먼저 떠도 LCP는 메인 이미지가 뜨는 순간에 찍힌다.

**오해: INP는 첫 클릭만 측정한다.**
그건 옛 지표 FID다. INP는 페이지를 쓰는 내내 일어난 상호작용을 보고 사실상 가장 느렸던 반응을 대표값으로 삼는다. 그래서 로드는 빨라도 사용 중 버벅이면 INP가 나쁘게 나온다.

**오해: CLS는 모든 레이아웃 이동을 벌점으로 잡는다.**
사용자 입력 직후 짧은 시간(약 500ms) 안의 이동은 "의도된 것"으로 보고 제외한다. 버튼을 눌러 아코디언이 펼쳐지는 건 점수에 안 잡힌다. 예고 없는 이동만 문제다.

**오해: Lighthouse 점수가 좋으면 Core Web Vitals를 통과한 거다.**
Lighthouse는 lab이라 INP를 아예 측정하지 못하고, 내 기기 기준이라 낙관적이다. 검색·평가에 실제로 쓰이는 건 field(CrUX) 75 퍼센타일이다. lab 통과는 출발점일 뿐 보장이 아니다.

## 스스로 점검하기

- `load` 이벤트 같은 옛 지표가 사용자 경험과 어긋났던 이유를 한 문장으로 설명할 수 있는가?
- LCP가 "가장 먼저"가 아니라 "가장 큰" 요소를 보는 이유는 무엇인가?
- FID에서 INP로 교체된 두 가지 배경(첫 입력만 봄, 지연만 봄)을 말할 수 있는가?
- 긴 JS 태스크가 왜 INP를 악화시키는지를 메인 스레드 관점에서 설명할 수 있는가?
- CLS가 시간이 아니라 비율 점수인 이유, 그리고 입력 직후 이동을 제외하는 이유는?
- 같은 페이지인데 lab과 field 수치가 다르게 나오는 이유와, field가 75 퍼센타일을 쓰는 의도는?
