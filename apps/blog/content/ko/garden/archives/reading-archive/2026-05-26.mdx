## Source

- [AI를 사용해 더 나은 코드를 더 천천히 작성하기](https://news.hada.io/topic?id=29870)
- 원문: [Using AI to write better code more slowly](https://nolanlawson.com/2026/05/25/using-ai-to-write-better-code-more-slowly/)

## 한줄 요약

이 글은 AI 코딩을 _더 많이, 더 빨리_ 만드는 장치가 아니라, PR을 깊게 검토하고 실패 모드와 버그를 집요하게 찾아내며 코드베이스를 더 건강하게 만드는 도구로 재해석한다.

## 핵심 포인트

- 흔히 말하는 "AI 코딩"은 저품질 코드를 빠르게 대량 생산하는 쪽에만 갇혀 있다.
- 하지만 LLM은 코드 생성만이 아니라 *검토, 탐색, 반례 찾기, 실패 모드 분석*에도 강하다.
- Mythos류 실험이 보여주듯, 모델은 코드베이스에서 버그 후보를 많이 찾아낸다.
- 진짜 어려움은 버그를 찾는 게 아니라, *무엇이 우선인지*와 *정말 버그인지*를 판단하는 일이다.
- 그래서 여러 모델을 병렬로 돌리고, 결과를 합쳐 오탐을 줄이는 방식이 유효하다.
- 중요한 건 속도보다 *정확도, 검증, 학습*이다.

## 더 깊은 분석

### 1) 이 글이 뒤집는 질문

보통 AI 코딩의 질문은 "얼마나 빨리 코드를 뽑아낼 수 있나"에 가깝다. 그런데 이 글은 질문 자체를 바꾼다.

- 더 빨리 만들 수 있나? → 물론 가능
- 더 좋은 결정을 하게 만들 수 있나? → 그게 더 중요
- PR을 더 깊이 이해하게 만들 수 있나? → 오히려 이게 핵심

즉, AI의 가치를 *산출량*이 아니라 _판단력_ 쪽으로 옮겨 놓는다.

### 2) LLM의 진짜 강점은 탐색이다

저자는 LLM이 버그를 "생성"하는 도구가 아니라, 버그를 "발견"하고 "의심"하게 만드는 도구라고 본다.

- 코드 전체를 훑으며 이상한 가정을 집어낸다.
- PR에서 빠진 엣지 케이스를 찾는다.
- 지금 당장 수정할 가치가 있는 항목을 고른다.
- 반대로, 고칠 가치가 낮은 문제는 과감히 넘긴다.

이건 AI를 autocomplete가 아니라 *리뷰 엔진*으로 쓰는 방식이다.

### 3) 왜 여러 모델을 같이 쓰는가

핵심은 ensemble이다.

- Claude sub-agent
- Codex
- Cursor Bugbot

이렇게 서로 다른 모델을 돌리면, 한 모델의 편향이나 환각을 다른 모델이 견제한다. 저자는 이 조합이 오탐을 줄이고, 리뷰 결과를 훨씬 신뢰할 수 있게 만든다고 말한다.

내가 보기엔 이게 제일 중요한 지점이다. AI가 똑똑해서가 아니라, *여러 관점이 겹치면서 인간 검토 비용을 줄여준다*는 점이 실용적이다.

### 4) 속도가 아니라 품질을 최적화한다

이 방식은 전형적인 "vibe coding"과 반대다.

- 대충 크게 만들고 나중에 고치는 방식이 아니다.
- 초안 생성 후 검증을 생략하는 방식도 아니다.
- 오히려 PR을 더 천천히 읽고, 더 오래 멈추고, 더 많이 의심한다.

그래서 결과적으로 velocity는 꼭 오르지 않을 수 있다. 저자도 오히려 기존 버그를 발견하고, 유닛 테스트를 추가하고, 구조를 이해하는 쪽으로 시간이 더 가는 경우가 많다고 말한다. 그런데도 이 방식이 만족스러운 이유는, *문제를 더 잘 이해하게 되기 때문*이다.

### 5) 학습 도구로서의 AI

이 글이 흥미로운 이유는, AI가 단지 일을 끝내는 도구가 아니라 *코드베이스를 배우는 도구*가 될 수 있다고 보여주기 때문이다.

- 실패 모드를 물어본다.
- PR이 어디서 깨질지 묻는다.
- Mermaid 다이어그램 같은 문서로 구조를 시각화한다.
- `/grill-me` 같은 방식으로 내가 이해하지 못한 부분을 끝까지 캐묻는다.

이건 코드를 빨리 쓰기보다, 코드를 *정확하게 이해하는 습관*에 더 가깝다.

## 왜 중요한가

AI를 잘 쓰는 방식은 꼭 "생산성을 폭발시키는 것"만이 아니다. 이 글은 AI를 *검증, 리뷰, 학습, 코드베이스 정리*에 쓰는 더 느린 방식이 충분히 강력하다는 걸 보여준다.

특히 지금처럼 나는 daily, 블로그, 지식 아카이브를 계속 쌓고 있어서, "일단 많이 만들기"보다 "무엇이 진짜로 남길 가치가 있는지 가려내는 것"이 더 중요하다.

## 후속 메모

- 큰 PR을 빨리 내는 것보다, 작게 나누고 검증을 붙이는 쪽이 더 맞을 수 있다.
- AI에게 먼저 "이 PR이 어떻게 실패할 수 있는지"를 묻게 해보자.
- 여러 모델의 결과를 비교하면 오탐과 편향을 줄이는 데 도움이 된다.
- daily 작성에도 생성보다 선별과 검토의 비중을 더 키우면 좋다.

## CodeGraph

### Source

- [CodeGraph - AI 코딩 에이전트를 위한 코드 지식 그래프](https://news.hada.io/topic?id=29873)
- 원문: [colbymchenry/codegraph](https://github.com/colbymchenry/codegraph)

### 한줄 요약

에이전트가 grep/glob/Read를 반복하기 전에, 사전 인덱싱된 코드 지식 그래프에서 심볼 관계와 영향 범위를 바로 가져오게 해주는 로컬 MCP 인프라.

### 핵심 포인트

- CodeGraph는 코드베이스를 미리 인덱싱해 두고, 에이전트가 바로 질의할 수 있게 만든다.
- 심볼 관계, 호출 그래프, 코드 구조를 그래프 형태로 저장해서 탐색 비용을 줄인다.
- README 기준으로 평균 약 35% 저렴하고, 토큰 57–59% 절감, 시간 46–49% 단축, 도구 호출 70% 안팎 절감 효과를 주장한다.
- `Smart Context Building`으로 진입점, 관련 심볼, 스니펫을 한 번에 돌려준다.
- `Impact Analysis`로 변경 영향 범위를 미리 추적할 수 있다.
- SQLite만 쓰는 100% 로컬 구조라 외부 API 키나 서비스 없이 동작한다.
- MCP로 Claude Code, Cursor, Codex, opencode, Hermes Agent 같은 에이전트에 바로 붙는다.

### 더 깊은 분석

#### 1) 이 도구가 겨냥하는 문제

대부분의 에이전트는 코드를 이해할 때 먼저 파일을 훑고, 찾고, 다시 읽는다. 작은 레포에서는 그 비용이 크지 않지만, 파일 수가 많아지면 탐색 그 자체가 토큰과 시간을 잡아먹는다. CodeGraph는 이 탐색 단계를 미리 계산해 둔 인덱스로 치환하려는 시도다.

즉, 이건 "더 똑똑한 모델"보다 *더 좋은 컨텍스트 공급 방식*에 가깝다.

#### 2) 왜 유효할 수 있는가

에이전트 작업에서 가장 비싼 건 종종 답이 아니라 *답을 찾는 과정*이다. CodeGraph는 이 과정을 줄이려 한다.

- 먼저 어떤 심볼이 중심인지 찾고
- 그 심볼과 연결된 호출자/피호출자를 보고
- 필요한 파일만 제한적으로 읽는다

이 흐름이 성립하면, LLM이 문맥을 만드는 데 쓰는 낭비를 꽤 줄일 수 있다.

#### 3) 하지만 한계도 있다

나는 이 도구가 모든 코드베이스에 만능이라고 보진 않는다.

- 그래프가 정확하려면 인덱싱 품질이 좋아야 한다.
- 동적인 패턴, 리플렉션, 런타임 생성 코드는 그래프만으로 다 안 잡힐 수 있다.
- 작은 레포에서는 이미 grep/read가 충분히 싸서 이득이 작을 수 있다.
- 에이전트가 여전히 무분별하게 파일을 읽으면, CodeGraph는 오히려 부가 오버헤드가 된다.

그래서 이건 "파일 읽기를 대체하는 도구"라기보다, *읽기 전에 방향을 잘 잡아주는 도구*로 보는 게 맞다.

#### 4) 내 관심사와 연결되는 지점

최근 내가 관심 있는 건 결국 같은 축이다.

- 더 빨리 생성하는가
- 더 잘 검증하는가
- 더 적은 컨텍스트로도 정확히 이해하는가

CodeGraph는 그중에서도 "정확하게 이해하는 데 필요한 첫걸음"을 줄여준다. 특히 큰 모노레포나 오래된 코드베이스에서는 꽤 매력적이다.

### 왜 중요한가

AI 에이전트가 커질수록, 모델 자체보다 *컨텍스트 인프라*가 경쟁력이 될 가능성이 크다. CodeGraph는 그 방향을 보여주는 예시다. "무엇을 읽을지"를 미리 구조화해 두면, 에이전트는 더 적은 호출로 더 나은 판단을 할 수 있다.

### 후속 메모

- 큰 레포에서 특히 유효할 가능성이 크다.
- 에이전트가 직접 그래프를 질의하도록 프롬프트/설정이 맞아야 효과가 난다.
- 우리 저장소처럼 문서와 코드가 함께 있는 구조와도 궁합이 좋을 수 있다.
