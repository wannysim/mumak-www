# karaoke

좋아하는 노래를 재생목록에 모아 연습하는 모바일 노래방 웹앱. YouTube 영상을 재생하면서
타임스탬프 가사를 한 줄씩 하이라이트하고, 줄마다 원문 · 한글 발음 · 한국어 번역을 토글해서 볼 수 있다.

기본 재생목록에는 Vaundy 9곡과 Fujii Kaze 대표곡 10곡의 공식 YouTube Music 원곡 오디오가 들어 있다.

## 사용법

- 헤더 좌우 화살표: 이전/다음 곡 (마지막 다음은 첫 곡으로 순환)
- 헤더 가운데 제목 탭: 현재 재생목록의 곡 목록. 뒤로 가면 재생목록을 만들거나 바꿀 수 있고,
  각 목록의 + 버튼에서 YouTube 주소와 원어·한국어 제목을 직접 등록한다
- 플레이어 줄: 재생/일시정지 · 경과 시간 · 탐색 슬라이더 · 전체 길이 · 반복 버튼
- 반복 버튼: 반복 없음 → 전체 반복(곡이 끝나면 다음 곡 자동재생, 마지막 다음은 첫 곡)
  → 한 곡 반복. 선택은 localStorage에 남는다
- 표시 토글: JP / PRON / KO on·off (localStorage 저장, 최소 하나는 유지)
- READ: 일본어를 한 단계 절제하고 발음·해석을 키우는 리딩 모드 (최초 기본값 ON, localStorage 저장)
- 테마 버튼: 다크 ↔ 라이트. 최초 접속에만 기기 설정을 씨앗으로 쓰고, 한 번 고르면 그 선택을 지킨다
  (그래서 "시스템" 상태가 따로 없다 — 아이콘은 항상 현재 테마를 가리킨다)
- 가사 줄 탭: 그 구간으로 시크 + 재생 + 화면 중앙 정렬
- 가사 불러오기: 빈 화면에서는 현재 곡의 JSON 한 개를 파일명과 무관하게 저장하고, 보관함에서는 전체 백업을 복원한다
- 백업 내보내기: 이 기기의 전체 가사 라이브러리를 재가져오기 가능한 JSON 한 개로 저장
- 종이·연필 버튼(가사 편집): AI용 정리 요청을 복사하거나 일본어·발음·번역을 줄별로 고친 뒤,
  노래를 왕복 재생하며 시작 시점을 찍어 이 기기에 바로 저장

가사를 손으로 스크롤하면 자동 스크롤이 3초간 양보한다. 그 사이에도 줄을 직접 탭하면
명시적 의사표시로 보고 즉시 중앙 정렬을 되살린다.

## YouTube 플레이어 제약

플레이어 위에는 아무것도 덮지 않는다. [Required Minimum Functionality](https://developers.google.com/youtube/terms/required-minimum-functionality)가
"플레이어 앞에 오버레이·프레임 등 시각 요소를 두지 말 것"과 최소 200x200 뷰포트를 요구한다.

그래서 영상을 숨기고 자체 플레이어 UI만 남기는 건 하지 않는다. 기술적으로는 iframe을
1px로 줄이거나 화면 밖으로 밀면(display:none은 재생이 끊긴다) 되지만 위 조항에 걸린다.
16:9를 유지하면서 높이 200px을 지키려면 폰 화면에서는 사실상 전체 폭이라, 줄여서 얻는
공간도 거의 없다.

대신 약관 안에서 할 수 있는 건 다 한다 — 컨트롤 바는 공식 파라미터(`controls=0`)로 끄고,
재생·탐색·반복은 플레이어 아래 자체 컨트롤 줄이 담당한다. 정지 상태에서 YouTube 제목·공유·
로고가 보이는 것은 이 제약의 결과이지 버그가 아니다.

`e2e/home.spec.ts`의 "unobstructed" 테스트가 `elementFromPoint`로 플레이어 위에 다른
요소가 올라오지 않았는지 확인한다. 오버레이를 다시 얹으면 그 테스트가 잡는다.

## 로컬 가사

앱과 배포물에는 가사 원문·발음·번역이 들어 있지 않다. 앱은 `/lyrics`나 외부 가사 API를
호출하지 않으며, 사용자가 직접 고른 파일만 브라우저 IndexedDB에 저장한다. 형식:

```json
[{ "time": 12.3, "jp": "歌の練習", "pron": "우타노 렌슈", "ko": "노래 연습" }]
```

빈 가사 화면에서는 파일 이름과 무관하게 현재 곡에 저장한다. 보관함에서 곡별 파일을
직접 복원할 때는 `src/songs/`에 등록된 `<slug>.json`으로 맞추거나
`{ "slug": "<slug>", "lyrics": [...] }` 형식으로 slug를 명시한다.
기존 곡을 바꾸기 전에는 확인을 받으며, 여러 파일은 하나의 IndexedDB transaction으로
저장되어 중간 상태를 남기지 않는다. Web Locks를 지원하는 최신 브라우저에서는 여러 탭의
확인과 저장도 직렬화한다. `이 앱에 대해 → 내 가사 → 백업 내보내기`에서 전체 라이브러리를
한 파일로 보관할 수 있고, 그 파일은 같은 가져오기 버튼으로 복원한다.

자세한 형식과 사용법은 **[docs/LYRICS.md](docs/LYRICS.md)** 에 정리했다.
`public/lyrics`나 `dist/lyrics`에 파일이 생기면 확장자와 관계없이 빌드 검사가 실패한다.
다른 경로의 JSON·LRC·자막·텍스트 데이터 파일도 라이선스 고지를 제외하고 차단한다.

### 저장 구조

- `localStorage`: 표시 설정, 현재 곡, 재생목록처럼 작은 상태. 키는 `src/lib/client-storage.ts`의
  버전 없는 `karaoke:*` 이름을 사용한다. 기존 `-v1`·`-v2` 키는 시작할 때 한 번 옮긴 뒤 제거한다.
- `IndexedDB`: 용량이 커질 수 있는 가사 본문. DB `version`은 저장소 구조 변경에만 사용하고,
  레코드·백업의 `schemaVersion`은 각 JSON 형식의 호환성을 뜻한다.
- `CacheStorage`: 오프라인 앱 셸. 서비스워커의 `RELEASE`는 사용자 데이터 버전과 무관한 캐시
  교체 번호다.

```bash
pnpm --filter karaoke check:no-lyrics
```

E2E는 실제 저작물을 쓰지 않는다. `e2e/mobile.spec.ts`가 synthetic JSON을 파일 입력으로
불러와 실제 import → IndexedDB → 새로고침 복원 경로를 검증한다.

## QR 기기 간 전송 (MK3)

재생목록과 가사를 서버 없이 옮긴다. 보내는 기기가 QR을 애니메이션으로 돌리고, 받는 기기가 카메라로 읽는다.

### 파운틴 코드

이전 형식(MK2)은 데이터를 512B 청크로 나눠 `MK2:{id}:{i}:{n}:{...}`처럼 **인덱스 주소**를 붙이고
2 fps로 순환했다. 받는 쪽이 모든 인덱스를 하나도 빠짐없이 봐야 해서 쿠폰 수집가 문제가 생긴다
(N=100이면 기대 프레임이 약 5.2N).

MK3은 파운틴 코드다. 각 심볼은 여러 블록의 XOR이고, 받는 쪽은 GF(2) 소거로 랭크를 채운다.
서로 다른 심볼 K개면 무엇이든 복원되므로 **놓친 프레임이 공짜**다. 구조는
`src/lib/share/`의 `codec.ts`(base45·CRC-32·deflate-raw) → `fountain.ts`(오브젝트 헤더·마스크 PRNG·
GF(2) 디코더) → `frames.ts`(와이어 포맷·프로파일·수집기) 순서로 쌓여 있다.

와이어 포맷은 `MK3:{CODE}{ID}:{K}:{N}:{base45(symbol || crc32)}`이고 헤더는 26자로 고정이다.
프레임마다 CRC-32 4바이트를 싣는다. 손상된 심볼 하나가 XOR 소거를 오염시키면 전송 전체를 처음부터
다시 해야 하므로, 0.15%의 오버헤드로 그것을 막는다.

### 사전 인코딩 풀

자바스크립트로는 표시 속도만큼 QR을 실시간 인코딩할 수 없다. 데스크톱 Node 벤치에서 한 장이
V25-L 12.1 ms · V30-L 16.8 ms · V40-L 29.0 ms이고, 폰은 그보다 3배에서 5배 느리다.
초당 30장에서 60장을 실시간으로 만드는 것은 불가능하다.

그래서 무한 스트림을 포기하고 유한한 심볼 풀
(`poolSize = K + max(8, ceil(K/4))`, 25% 여유, 짝수면 +1 — 아래 레인 패리티 참조)을
**먼저 다 굽고** 순서대로 순환한다. 굽는 일은
`qr-encoder.worker.ts`에서 워커 최대 3개가 나눠 하고, 표시 루프는 구운 비트셋을 캔버스에 blit할
뿐이라 공짜다. 파운틴 코드라서 유한 풀이 문제가 되지 않는다 — 받는 쪽이 표시 프레임의 비율 f를
잡으면 한 바퀴에 f·poolSize개의 서로 다른 심볼이 모이고, 못 주운 것은 다음 바퀴에 줍는다.

blit은 정수 배율만 쓰고 보간을 끈다. 비정수 배율은 모듈 폭을 2px/3px로 들쭉날쭉하게 만들어
디코드를 깨뜨린다. 백킹 스토어를 정수로 맞춘 뒤 CSS 박스도 같은 값으로 못 박는다 — 안 그러면
컴포지터가 다시 비정수 배율로 늘려 방금 맞춘 격자를 무너뜨린다.

### 속도 프로파일

네 가지를 제공하고 기본값은 `fast`다. **"이론"과 "실측"을 같은 칸에 섞지 않는다.** "이론"은
`targetSymbolsPerSecond × blockBytes` 계산값이고 UI의 프로파일 라디오가 보여 주는 값이다.
"실측"은 `e2e/qr-transfer.spec.ts`의 광학 루프백에서 첫 스캔부터 완료까지 잰 실효 처리량이며
전송 화면에만 나온다.

측정 조건: macOS·Chromium, 합성 가사 20곡, `--repeat-each=3 --workers=1`, **엔진별 3회**.
아래는 중앙값이고 괄호가 3회의 최소~최대다.

| id    | 라벨   | QR    | 레인 | blockBytes | 표시             | 이론       | 실측 · 기본 엔진(BarcodeDetector 있음) | 실측 · jsQR 워커 강제 |
| ----- | ------ | ----- | ---- | ---------- | ---------------- | ---------- | -------------------------------------- | --------------------- |
| safe  | 안정   | V16-M | 1    | 416        | 10장/s           | 4.1 KB/s   | 4.2 (4.2~4.2)                          | 4.2 (4.2~4.2)         |
| fast  | 빠르게 | V25-L | 1    | 1214       | 20장/s           | 23.7 KB/s  | 24.1 (24.0~24.2)                       | 23.0 (21.7~23.3)      |
| turbo | 고속   | V30-L | 1    | 1658       | 30장/s           | 48.6 KB/s  | 43.9 (39.2~46.9)                       | 23.0 (20.9~25.0)      |
| max   | 최대   | V40-L | 2    | 2842       | 60장/s (장당 30) | 166.5 KB/s | 64.8 (55.1~70.0)                       | 11.3 (11.1~15.3)      |

**`max`의 실측 조건에는 "보내는 화면이 2장을 함께 보여 준다"가 들어 있다. 폰은 그 조건을 못 맞춘다.**
루프백은 합성 캔버스에 2장을 나란히 그리지만, 실기기에서는 V40 두 장이 폰 드로어 높이에 함께 들어가지
않아 한 장만 보이고 합산 60장이 30장으로 떨어진다(2026-08-01 확인). 즉 위 `max` 행은 태블릿·데스크톱
화면을 전제한 값이고, 폰에서 보낼 때의 실질 상한은 `turbo` 행이다. 파운틴 코드라 한 레인만 읽혀도
전송은 완주하므로(풀 크기를 홀수로 강제한 이유) 고장은 아니지만, 폰에서 `max`를 골라도 빨라지지 않는다.

**측정은 반드시 직렬로 한다.** Playwright 워커를 병렬로 두면 루프백 캔버스와 디코더 워커가 CPU를
서로 뺏어 같은 커밋에서 처리량이 최대 2배까지 흔들린다(`max` 기본 엔진에서 48~72 KB/s를 봤다).
`--workers=1` 없이 잰 숫자는 이 표에 넣지 않는다.

**빠른 두 프로파일은 네이티브 디코더가 있을 때만 빠르다. 이것을 UI에서 숨기지 않는다.**
jsQR 경로에서 `turbo`는 23.0 KB/s로 `fast`(23.0)와 **같고**, `max`는 11.3 KB/s로 `fast`의 절반이다.
그래서 옵션 설명은 실측이 지지하는 만큼만 말한다 — turbo는 "느립니다"가 아니라 "빠르지 않습니다"다.
병목은 디스플레이가 아니라 디코더다. 표시는 어느 엔진에서나 목표치를 그대로 내보내지만(실측 표시
10.0 · 20.0 · 30.1 · 60.6장/s) 받는 쪽이 따라오는 장수는 기본 엔진에서 10.4 · 20.4 · 27.9 · 34.9장/s,
jsQR 워커에서 10.5 · 19.3 · 18.6 · 7.2장/s다. 삭제가 아니라 표기가 답이다.

`max`의 기본 엔진 실측 64.8 KB/s는 이론 166.5의 **39%**(3회 범위 33~42%)다. 초당 60장을 그대로
띄우지만 디코더가 34.9장밖에 못 받는다. 버린 조각(CRC·포맷 실패)은 30회 실행 전부에서 0이었다.
사전 인코딩 중앙값은 safe 풀 43장 0.22초, fast 75장 0.84초, turbo 47장 0.82초,
max 45스텝(QR 90장) 0.84초다.

측정 창은 "첫 진행률 렌더"부터라 실제 시작보다 조금 늦게 열린다. 그래서 실측치가 이론값에
붙거나 살짝 넘을 수 있다 — 이론값을 넘겼다는 뜻이 아니라 경과 시간이 과소 측정된 것이다.
기하 테스트 두 개(가로 2레인·한쪽 레인)는 번들이 작아(K가 한 자리) 측정 창에 통계 렌더가
한두 번밖에 안 들어간다. **그 둘은 완주 여부를 보는 테스트이지 처리량 수치가 아니다.**

**루프백 캔버스는 폰 카메라가 아니다.** 초점·흔들림·기울기·조명·롤링셔터·화면 반사가 전부 빠져
있으므로 위 실측치는 실제 광학 전송의 상한이다. 엔진 선택은 `qr-scanner` 내부 휴리스틱이라
"BarcodeDetector가 있으면 그것"이 아니다(arm macOS 13+에서는 일부러 피한다). 그래서 측정 로그는
엔진 이름을 추측하지 않고 `BarcodeDetector` 존재 여부만 적는다. `QR_LOOPBACK_FORCE_JSQR=1`을 주면
리눅스 CI와 같은 jsQR 워커 경로를 로컬에서 재현할 수 있다.

`prefers-reduced-motion: reduce`인 기기에서는 기본값이 `safe`로 내려가고, 초당 20회를 넘는
`turbo`·`max`는 **선택 자체가 막힌다**(disabled + 이유 표시). 라디오의 `disabled`만으로는 부족하다 —
그것은 렌더 시점 스냅샷이라, 고른 뒤에 설정을 켠 사용자에게는 '비활성인데 체크된' 항목이 남는다.
그래서 `createQr`이 시작 직전에 같은 판정(`isBlockedByReducedMotion`)을 다시 돌려 `safe`로 클램프한다.
판정이 한 곳에 있어야 라디오와 클램프가 갈라지지 않는다. 고대비 흑백 면이 초당 수십 회 바뀌는 것은
WCAG 2.3.1(3회/초 초과 섬광) 관점에서 실재하는 위험이라, 보내는 화면과 받는 화면 양쪽에 갱신 속도를
미리 적는다. 2레인일 때 캔버스 폭 클램프(`max-w-80`)는 푼다 — 185모듈짜리 V40 두 장을 320 CSS px에
밀어 넣으면 모듈당 1.7px이 되어, "큰 화면이 필요하다"고 안내하면서 정작 쓸 수 없는 함정이 된다.
클램프를 푼 대가로 2레인 캔버스 두 장이 폰 드로어 높이를 넘길 수 있으므로 보내는 화면은
`justify-center`가 아니라 `justify-center-safe`로 정렬한다 — 보통은 가운데지만, 넘칠 때 시작 모서리를
스크롤 밖으로 밀어내지 않는다(그러면 레인 1로 되돌아갈 방법이 없다).

**그리고 이 절충은 폰에서 이기지 못했다.** 클램프를 풀고 정렬을 고쳐도 V40 두 장이 폰 화면에 함께
들어가지 않아, 실기기에서는 한 장만 보인다(2026-08-01 확인). 리뷰가 "2레인 좁은 뷰포트" 케이스로
정확히 지적했는데 당시 "비용이 문제보다 크다"며 스킵했고, 그 판단이 틀렸다. `max`를 지우지 않고
남겨둔 것은 태블릿·데스크톱에서 유효하고 폰에서도 전송이 완주하기 때문이지만, UI 문구와 위 표가
그 한계를 말하도록 고쳤다. 되살릴 때 필요한 것: **좁은 뷰포트에서 두 레인이 실제로 동시에 보이는지
검증하는 e2e**, 그리고 폰에서 2레인을 성립시킬 레이아웃(가로 모드 전제, 또는 폭에 맞춘 축소 후
카메라 해상도 요구 재측정). 측정 없이 레이아웃만 바꾸지 말 것 — `MAX_SCAN_SIDE` 주석이 비정수
축소가 디코드를 깨뜨린다고 기록하고 있다.

### 2레인을 송·수신 기하 합의 없이 읽는 법

프레임은 레인 기하를 싣지 않는다(레인은 표시 문제일 뿐이다). 예전 초안은 카메라 프레임의 종횡비로
분할축을 골랐는데, 보내는 쪽은 **항상 세로로 쌓는데** 카메라가 가로 프레임을 주면 두 영역이 각각 두
코드를 반씩 물어 어느 쪽도 디코드되지 않았고, 한 번 그 상태에 들어가면 빠져나올 길이 없었다.
축을 맞추는 게 아니라 없애는 것이 답이다.

- **엔진이 `BarcodeDetector`면 `detect(video)`를 직접 부른다.** 그 API는 프레임 안의 모든 코드를
  배열로 준다 — `QrScanner.scanImage()`가 그중 하나만 쓸 뿐이다. 이 경로에서는 분할도 축도 없다.
- **jsQR 워커는 결과가 하나뿐이라 영역을 나눈다.** latch하지 않고 라운드마다 스케줄을 회전시킨다:
  phase 0 전체 프레임 → phase 1 위/아래 절반 → phase 2 좌/우 절반. 상태도 정체 감지도 복구 로직도
  없이 세 배치가 3라운드(30fps에서 0.1초)마다 모두 덮인다. 전체 프레임 위상이 있어서 **카메라가 한쪽
  레인만 담은 경우**도 잡힌다.
- 레인 수는 수집기의 `profileCode`에서 매 라운드 새로 읽는다(`M`이면 2). **아직 MK3 프레임을 하나도
  못 받았으면 `null`("모른다")이고, 그동안에도 회전 스케줄을 함께 돌린다.** 회전을 끄는 조건은
  `lanes === 1`로 확인된 것 하나뿐이다. 이 "모른다"를 별도의 부트스트랩 불리언으로 들고 있으면
  안 된다 — 그 플래그는 "무언가 디코드됐다"로 꺼지는데, MK3가 아닌 QR 한 장이 시야에 들어오는 것만으로
  `profileCode`가 여전히 `null`인 채 회전이 영구히 멈춘다(단조 latch). 그러면 2레인 송신은 전체 프레임
  위상에서만 운이 좋기를 기다리게 되고, 되돌아올 길이 없다. 모른다는 상태를 레인 수 **값**으로
  표현하면 그 문 자체가 사라진다. `scan-loop.test.ts`의
  "keeps rotating after a foreign QR decodes while the lane count is still unknown"가 이걸 고정한다.
- 영역마다 엔진과 캔버스를 따로 둔다. 워커 하나에 두 스캔을 동시에 던지면 응답이 엇갈리고 캔버스를
  공유하면 픽셀이 겹친다. 회전 스케줄의 최대 영역 수가 2라 엔진도 2개를 넘지 않는다.

**풀 크기 불변식은 `gcd(lanes, poolSize) === 1`이다.** 레인들은 하나의 `cursor`를 나눠 쓰며 한 칸씩
올라가므로 레인 하나가 밟는 풀 인덱스의 보폭이 정확히 `lanes`가 된다. 최대 레인이 2인 지금은 그
불변식이 "`poolSize`는 홀수"와 같은 말이고, `poolSizeFor`가 짝수면 +1을 해서 그것을 강제한다.
짝수로 두면 레인 0은 짝수 인덱스, 레인 1은 홀수 인덱스에 영원히 고정되어 **한쪽 레인만 보이는 수신은**
최대 `poolSize/2`개까지만 모으고 랭크 K에 **도달하지 못한다**(K=38·poolSize=48이면 24에서 정체).
풀은 커지기만 하므로 용량 주장이 후퇴하지 않는다. 레인이 3개가 되면 "홀수"로는 부족하니 그때
`gcd` 조건으로 돌아올 것.

e2e가 이 셋을 각각 잡는다: 가로 카메라 프레임 + 세로 2레인(`max`가 완주하는가 — 기하 합의가
되돌아오면 여기서 0장), 한쪽 레인만 보이는 수신(랭크 K에 도달하는가 — 풀 패리티가 되돌아오면
여기서 무한 정체), 그리고 네 프로파일의 완주와 처리량 기록. 전부 `QR_LOOPBACK_FORCE_JSQR=1`에서도
통과해야 한다. 그 변수는 `turbo.json`의 `test:e2e` 태스크에서 **`passThroughEnv`가 아니라 `env`에**
있어야 한다 — `passThroughEnv`는 태스크 해시에서 제외되므로, 거기 두면 변수를 켜도 turbo가 이전
BarcodeDetector 실행 결과를 그대로 재생해 두 엔진이 똑같은 green을 찍는다. `env`에 있으면 변수를
뒤집을 때마다 캐시 항목이 갈라진다(`"engine":"platform default"` / `"jsqr-worker (forced)"` 두 개).

### `turbo`·`max`를 되살리며 닫은 것

이 두 프로파일은 한 번 리뷰 blocker 때문에 표에서 삭제됐다가 되살아났다. 참조 수준의 속도가
이 기능의 목적이라 **기능을 줄이는 것은 blocker를 닫는 방법이 아니었고**, blocker 자체는 전부
실재했다. 각각을 어디서 어떻게 닫았는지는 위 절들에 본문으로 들어가 있고, 여기 목록은 색인이다.

| 무엇이 깨졌었나                                                                    | 어떻게 닫았나                                                                                                                                                   |
| ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 수신이 카메라 종횡비로 분할축을 골라, 가로 프레임 + 세로 2레인에서 영구히 0장      | 축 선택을 없애고 라운드마다 회전(전체 → 위/아래 → 좌/우). `BarcodeDetector`는 `detect()`로 멀티 디코드                                                          |
| 부트스트랩 불리언이 "무언가 디코드됨"으로 꺼져, 낯선 QR 한 장이 회전을 영구히 정지 | 플래그 삭제. `getLaneCount`가 `1 \| 2 \| null`을 돌려주고 회전은 `!== 1`일 때 돈다                                                                              |
| 짝수 풀에서 레인 패리티가 고정돼, 한쪽 레인만 보이는 수신이 랭크 K에 영원히 미달   | `poolSizeFor`가 `gcd(lanes, poolSize) === 1`(지금은 홀수)을 강제                                                                                                |
| 2레인 캔버스가 `max-w-80`에 눌려 모듈당 1.7px — 쓸 수 있는 척하는 함정             | 2레인에서 클램프 해제 + `justify-center-safe`. 섬광 위험은 프로파일 선택 단계에서 막는다. **폰에서는 이것으로도 부족했다 — 위 "폰은 그 조건을 못 맞춘다" 참조** |
| 보내는 화면이 표시 상한을 `실측`이라고 표기 (받는 쪽 실제 처리량의 최대 14배)      | 보내는 화면은 `표시`, `실측`은 받는 화면의 랭크 기반 수치 전용                                                                                                  |
| `QR_LOOPBACK_FORCE_JSQR`가 `passThroughEnv`라 jsQR 검증이 캐시 재생으로 통과       | `test:e2e`의 `env`로 이동 — 엔진마다 캐시 항목이 갈라진다                                                                                                       |
| 모션 줄이기 판정이 렌더 스냅샷이라 `createQr`이 초당 60장을 그대로 시작            | `isBlockedByReducedMotion` 한 곳으로 모으고 시작 직전에 재판정                                                                                                  |

### 버전 호환

MK3만 받는다. `MK1|`·`MK2:`로 시작하는 프레임에는
"보내는 기기의 앱이 오래된 버전입니다…"를 안내한다. 인덱스 주소 기반과 랭크 기반은 디코더가 아예
달라서 호환을 유지하면 죽은 경로만 남는다. 버전이 섞인 기기 사이는 **공유 파일(JSON)** 경로가
다리 역할을 한다 — 받는 화면의 "카메라 대신 공유 파일 불러오기"와 보내는 화면의 "공유 파일 저장",
"기기로 바로 공유"가 그것이다.

### qrcode.react → qrcode-generator

`qrcode.react`는 React 컴포넌트로만 그릴 수 있어 워커에서 못 돌고, 데이터가 넘치면 **QR 버전을
조용히 올린다**. 스트림 도중 버전이 바뀌면 받는 쪽 모듈 크기 가정이 깨진다.
`qrcode-generator`(MIT, 의존성 0, TS 타입 포함, DOM 참조 0)는 `qrcode(typeNumber, ec)`에 버전을
명시하면 용량 초과 시 **throw**하므로 그 위험이 구조적으로 사라지고, 워커에서 그대로 돈다.
`src/__tests__/share-frames.test.ts`가 각 프로파일의 실제 프레임에 3자만 덧붙여도 라이브러리가
던지는 것을 확인한다.

## PWA

`public/manifest.webmanifest` + `public/sw.js`. 서비스워커는 프로덕션 빌드에서만 등록된다
(`src/register-sw.ts`) — dev에서 등록하면 캐시가 HMR을 가로챈다.

빌드 때 해시가 붙은 JS/CSS와 manifest·icons 목록을 서비스워커에 주입해 프리캐시한다.
분할된 일본어 폰트 100여 개를 전부 받지는 않고, 첫 화면에서 브라우저가 실제로 사용한
폰트 조각만 서비스워커에 전달해 캐시한다. 문서는 network-first, `/assets`·`/icons`는
cache-first다. 외부 오리진(YouTube)은 캐시하지 않는다. 사용자가 불러온 가사는
서비스워커를 거치지 않고 IndexedDB에만 남는다.

셸과 프리캐시 파일의 콘텐츠 해시로 build ID를 만들기 때문에 배포마다 새 캐시에 완전한 셸을 먼저 만든 뒤
activate에서 이전 karaoke 캐시를 지운다. 설치가 중간에 실패해도 활성 캐시는 건드리지 않는다.
캐시 전략 자체를 바꾸면 `sw.js`의 `RELEASE`를 올린다. `v3-local-first`가 활성화되면 예전
`karaoke-lyrics-*`와 전체 폰트가 들어 있던 구 캐시도 함께 지운다.

아이콘은 `scripts/`가 아니라 일회성으로 Chromium 렌더링해 `public/icons/`에 넣어 두었다.

## 폰트

Pretendard Variable(OFL-1.1) 원본은 2MB인데 대부분이 실사용되지 않는 확장 한글 음절이다.
KS X 1001 완성형 2350자 + 라틴만 남겨 449KB로 줄이고, 수정본의 예약명을
`Mumak Sans Variable`로 바꿨다 (`mumak-sans-variable.woff2`). 범위 밖 희귀 음절은
시스템 폰트로 글자 단위 폴백되므로 깨지지 않는다. 원 저작권 고지와 라이선스 전문은
[`public/licenses/pretendard-ofl.txt`](public/licenses/pretendard-ofl.txt)에 있다.

일본어 제목과 가사는 `@fontsource-variable/noto-serif-jp`의 Noto Serif JP Variable을 쓴다.
Fontsource가 제공하는 `unicode-range` 분할 파일 중 화면의 글자에 필요한 조각만 브라우저가
받으므로, 전체 일본어 글리프 파일을 첫 화면에서 한꺼번에 내려받지 않는다. 패키지에 포함된
Google Inc. 저작권 고지와 OFL 전문은
[`public/licenses/noto-serif-jp-ofl.txt`](public/licenses/noto-serif-jp-ofl.txt)에 있다.

```bash
pip install fonttools brotli
python3 scripts/subset-font.py <원본.woff2> src/assets/fonts/mumak-sans-variable.woff2
```
