# Stickerbook 스파이크 측정과 운영

기준일: 2026-11-13. 이 문서 전체가 엔지니어링 제안이며 확정이 아니다. 스파이크 목록과 범위는 [tech-research.md](./tech-research.md) 9장, 결정 시점 G0–G5는 [open-decisions.md](./open-decisions.md)를 따른다. 이 문서에서 "N장"은 tech-research.md의 장이다.

준비도 리뷰에서 통과 기준과 예산 수치가 스파이크 뒤로 미뤄져 있어 결과에 기준을 맞출 위험이 있다는 지적이 나왔다. 그래서 착수 전에 측정 항목, 측정 방법, 후보 임계값을 적어 둔다. "후보"는 사용자가 게이트에서 확정할 값이고, "(제안)"은 엔지니어링이 정할 수 있는 규칙이다.

## 측정 항목과 후보 임계값

### 기준을 잡는 원칙

- **참조 실측을 그대로 목표로 쓴다.** 출처는 [plan.md](./plan.md) 참고 자료다.
  - ryo.lu(2026-11-12 데스크톱 Chromium 측정): 앞면 CSS 7KB, 서브셋 woff2 2개 각 18KB, 이미지 0개, JS 전송 323KB.
  - georgehatton.com(2026-11-13 Wayback 스냅샷 관찰): 폰트 파일 1개 약 68KB. 사진 해상도 단계(343/686/960/1334/1920px)와 20×13 흐린 미리보기는 차용 후보라 G0에서 채택하면 목표로 쓴다.
- 모션 값(ryo.lu 전환 0.65s, georgehatton 400·750·1000ms)은 성능 목표가 아니라 G3 사용자 디자인 결정의 후보다(S3-8).
- **참조보다 느슨한 상한을 엔지니어링이 걸지 않는다.** 측정 결과 참조를 지킬 수 없으면 측정값과 선택지를 사용자에게 올린다.
- **참조 수치가 없는 항목**(프레임 시간 p95, 텍스처 메모리 상한 등)은 업계 관례를 출처와 함께 후보로 두고 사용자가 정한다. 참조 사이트를 같은 기기·같은 네트워크에서 함께 재서 그 값을 후보로 쓸 수도 있다. ryo.lu의 클릭 반응과 LCP는 아직 재지 않았다.
- **확정 시점:** S1 후보는 G1, S2는 G2, S3는 G3에서 확정한다. S4–S6은 선택지를 토글로 두고 시작할 수 있고, 각 스파이크 판정 전에 확정한다. G5(공개 전)에는 0장 매트릭스 전체로 다시 잰다. 결과를 본 뒤에는 임계값을 바꾸지 않는다. 바꾸면 날짜·이전 값·이유를 아래 "스파이크 결과"에 남긴다.
- **성능 수치는 실기기에서만 잰다.** headless CI의 WebGL은 소프트웨어 렌더링일 수 있다(0장). CI는 결정적인 항목(순수 TS 단위 테스트, 빌드 산출물 크기)만 맡는다(제안).
- 모든 스파이크 통과 기준에 7장 요소별 대응표의 해당 행을 넣는다. 아래 각 표의 마지막 행이 그것이다.

### 공통 측정 방법

| 대상               | 방법                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 구간 시간          | `performance.mark`와 `performance.measure`를 쓴다. 이름은 `sb:<스파이크>:<사건>`으로 통일한다(예: `sb:s3:click`, `sb:s3:first-frame`, 제안).                                                                                                                                                                                                                                                                  |
| 프레임 시간        | 애니메이션 중 rAF 콜백 timestamp의 간격을 잰다. 주사율 간격은 이 간격의 중앙값이다. p50·p95·최대와 표본 수 n을 남긴다. 간격이 주사율 간격의 1.5배를 넘으면 누락 프레임으로 센다(제안). 프레임당 JS 시간은 콜백 안 `performance.now()` 차이로 잰다. Chromium에서는 Long Animation Frames API를 보조로 본다.                                                                                                    |
| 입력부터 첫 프레임 | 입력 이벤트의 `event.timeStamp`부터 변화가 처음 그려진 프레임의 rAF timestamp까지 잰다. rAF timestamp는 프레임 시작 시점이라 실제 표시는 조금 더 늦다. Event Timing API(`PerformanceEventTiming.duration`)를 보조로 쓴다. Safari는 26.2부터 지원한다([web.dev](https://web.dev/blog/lcp-and-inp-are-now-baseline-newly-available), 2025-12-17).                                                               |
| 전송량             | 실기기에서 `PerformanceResourceTiming.transferSize`로 잰다. 교차 출처 리소스는 `Timing-Allow-Origin` 헤더가 있어야 값이 나온다. 빌드 산출물은 br과 gzip 크기를 함께 적는다.                                                                                                                                                                                                                                   |
| 화면 비교          | 데스크톱은 Playwright 스크린샷(`deviceScaleFactor` 1·2·3), 실기기는 OS 스크린샷(기기 픽셀)을 쓴다. 차이는 pixelmatch 같은 도구로 픽셀 차이 비율을 기록한다. 판정은 사용자가 100%와 400% 확대 crop을 나란히 보고 한다. 움직이는 구간은 화면 녹화(iOS 화면 기록, Android `adb shell screenrecord`)에서 프레임을 뽑는다.                                                                                         |
| 텍스처 메모리      | 한 면 = CSS 폭 × CSS 높이 × DPR² × 4바이트. 상주 합계 = 한 면 × 미리 래스터할 면 수 N이고, 밉맵을 쓰면 4/3을 곱한다. foreignObject 중간 2D 캔버스(래스터 1건당 같은 크기)와 WebGL 그리기 버퍼(캔버스 기기 픽셀 × 4바이트, 깊이·MSAA 별도, 추정)는 따로 더한다.                                                                                                                                                |
| 하드 상한 기록     | `gl.getParameter(gl.MAX_TEXTURE_SIZE)`를 기록한다. iOS Safari의 캔버스 상한은 면적 16,777,216px, 메모리 합계 384MB(iOS 15)로 보고됐다([면적](https://pqina.nl/blog/canvas-area-exceeds-the-maximum-limit/), [메모리](https://pqina.nl/blog/total-canvas-memory-use-exceeds-the-maximum-limit/), 둘 다 2022). 현재 iOS의 값은 미확인이다. 중간 캔버스는 업로드 직후 1×1로 줄여 해제한다(같은 글의 우회, 제안). |

계산 예(가정): 세로 폰에서 한 쪽이 화면 전체(390×844 CSS, DPR 3)라는 최대 가정이면 한 면은 1170×2532×4, 약 11.85MB다. 양방향으로 즉시 넘기려면 현재 펼침 2면에 다음 펼침 2면, 이전 펼침 2면이 더 필요하다. N=6이라 약 71MB이고 밉맵을 쓰면 약 95MB다. 앞으로만 즉시 넘기면 N=4, 약 47MB다. 판형은 G0에서 정해지므로 S1에서 실제 값으로 다시 계산한다.

### 재래스터 트리거 시나리오 (S1은 쉬는 중, S2는 넘김 중)

감지 방법과 다시 그리는 동안의 규칙은 tech-research.md 1장 "재래스터 규칙과 대체 경로"를 따른다. 여기서는 재현과 측정만 적는다.

| 트리거              | 재현 방법                                                                                                              |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| DPR 변경            | 데스크톱 브라우저 확대·축소, 배율이 다른 모니터로 창 이동                                                              |
| 회전                | 세로와 가로 전환                                                                                                       |
| Fold 접기·펴기      | Galaxy Fold 접힘과 펼침 전환                                                                                           |
| 모바일 주소창       | iOS Safari·Chrome Android에서 스크롤해 주소창을 보이고 숨김                                                            |
| 사진·폰트 로드 완료 | 폰트 준비 전 래스터가 일어나지 않는지 확인한다. 흐린 미리보기를 채택하면 느린 네트워크에서 미리보기가 원본으로 바뀔 때 |

각 트리거에서 잴 것은 다음과 같다.

- API별 감지 여부
- 트리거부터 선명한 상태로 돌아오기까지 걸린 ms
- 그동안 보인 화면(늘린 옛 텍스처, 빈 면, 깜빡임)
- 다시 래스터한 면 수와 누락 프레임 수
- 넘김 중이었다면 포인터 추종과 진행도가 유지되는지

후보 기준:

- (제안) 쉬는 중 빈 면과 깜빡임 0회, 넘김 중 보이는 텍스처 교체 0회. 1장 규칙이 지켜지는지 검사한다.
- 선명 복귀 시간: 키·메뉴로 하는 브라우저 확대(DPR 변경)는 입력 응답이라 후보 100ms를 쓴다(RAIL Response, [web.dev](https://web.dev/articles/rail)). RAIL은 드래그·스크롤에 이 목표를 적용하지 않으므로 회전, Fold, 주소창, 모니터 이동에는 참조 수치가 없다. 이 크기 트리거는 1장의 디바운스(150ms, 제안값)에 래스터 시간을 더한 측정값을 사용자에게 올린다. G1에서 확정한다.

### E2E (제안)

저장소 사실:

- `packages/playwright-config/src/create-playwright-config.ts`: CI는 Desktop Chrome, Desktop Firefox, Desktop Safari 세 프로젝트, 로컬은 chromium 하나다. launch 옵션, 터치(`hasTouch`) 프로젝트, 스크린샷 설정이 없다. 팩토리 주석은 필요하면 호출부에서 spread로 덮어쓰라고 적는다.
- CI E2E 잡은 ubuntu-latest 위 `mcr.microsoft.com/playwright:v1.63.0-noble` 컨테이너에서 돈다(`.github/workflows/e2e.yml`). 저장소 E2E에 `toHaveScreenshot` 사용처가 없다.
- 설치된 playwright-core 1.63.0의 Chromium 실행 코드(`server/chromium/chromium.ts` 부분)는 기본 인자에 `--enable-unsafe-swiftshader`를 넣는다. CI처럼 headless로 돌 때 실행 바이너리는 Chrome Headless Shell 153(`chromium-headless-shell`)이고, headed는 Chrome for Testing 153이다. Chromium 문서(`docs/gpu/swiftshader.md`)는 SwiftShader 자동 폴백이 deprecated이고 WebGL 컨텍스트 생성이 실패하게 바뀌며, 이 플래그로 opt-in한다고 적는다. 그래서 CI chromium은 소프트웨어 WebGL을 받을 것으로 본다(추정, 컨테이너에서 실행 확인 안 함). Firefox와 WebKit의 컨테이너 WebGL 여부는 미확인이다.
- `apps/blog/e2e/graph.spec.ts`는 캔버스나 미지원 안내 중 하나가 보일 때까지 기다린 뒤 캔버스 유무로 분기한다. "캔버스가 있으면 범례가 있고 없으면 범례도 없다"는 양방향 불변식을 검사하고, 캔버스가 필요한 테스트는 `test.skip`한다.

제안:

1. 설정 변경은 `apps/stickerbook/playwright.config.ts`에서 spread로 한다. 공용 패키지를 고치면 모든 E2E 앱이 영향을 받는다.
2. 앱 루트에 `data-render-path`(webgl 또는 fallback)를 둬서 렌더 경로를 관찰 가능하게 한다. 캔버스 유무로는 포스터 단계와 구분되지 않는다.
3. chromium 프로젝트에 "webgl 경로여야 한다"를 단언하는 테스트를 하나 둔다. CI가 대체 경로만 검사하고 녹색이 되는 일을 막는다. 실패하면 stickerbook 설정에 launch 인자를 명시한다. Firefox와 WebKit은 blog처럼 분기하고 어느 경로였는지 test annotation으로 남긴다.
4. 대체 경로는 `page.addInitScript`로 `getContext('webgl2')`가 null을 돌려주게 해서 강제한다. 같은 상호작용 시나리오를 두 경로에서 돌린다. 운영 코드에 강제 플래그를 두지 않는다.
5. 컨텍스트 손실은 chromium의 webgl 경로에서 `page.evaluate`로 `WEBGL_lose_context`를 불러 일으킨다. 현재 쪽, 포커스, 복구 뒤 `data-render-path`를 단언한다.
6. 상호작용 단언은 공통 DOM 오버레이의 역할과 상태로 한다. 현재 쪽 번호, 숨은 쪽의 `inert`, 레코드의 펼침 상태처럼 보조 기술이 읽는 값을 그대로 쓴다. 접근성 대응표의 행마다 E2E 단언을 하나 이상 둔다. 넘김이 끝나기를 쪽 번호 변화로 기다리고 `waitForTimeout`을 쓰지 않는다.
7. 드래그는 쉬는 상태 오버레이의 boundingBox로 좌표를 얻어 `page.mouse`로 여러 단계 움직인다. 모델이 고정 timestep이라 프레임 속도와 무관하게 같은 결과를 기대한다.

시각 회귀:

- 기준 이미지는 CI와 같은 Linux 컨테이너 이미지에서만 만든다. macOS 로컬에서 만들지 않는다. Playwright는 기준 이미지 이름에 프로젝트와 플랫폼(예: chromium-linux)을 붙이고, 렌더링이 OS와 헤드리스 여부에 따라 달라진다고 경고한다(Playwright 문서 Visual comparisons).
- 갱신은 같은 이미지에서 `--update-snapshots`로 한다. 로컬 docker와 수동 실행 워크플로 중 하나를 고른다.
- 로컬 실행에서는 `ignoreSnapshots`를 CI가 아닐 때 켠다.
- 범위는 chromium webgl 경로의 쉬는 상태(닫힌 책 앞면, 펼침면, 부록 쪽)다. 넘김 중 프레임은 찍지 않는다. Firefox와 WebKit은 WebGL 여부가 확인될 때까지 찍지 않는다.
- SwiftShader 결과는 실제 GPU와 다르다. 기준 이미지는 회귀 감지용이며 선명도 판단을 대신하지 않는다. 선명도는 실기기에서 사용자가 본다.
- 도입은 G4로 한다. G0 시각 방향과 S1 결론 전에는 기준 이미지가 계속 바뀐다.

터치:

- stickerbook 설정에만 CI 전용 `chromium-touch` 프로젝트(`devices['Pixel 7']`)를 더한다. Playwright 터치 문서의 예제가 이 기기 설정을 쓴다.
- Playwright에는 내장 터치 드래그가 없다. 문서는 `dispatchEvent`로 TouchEvent를 직접 보내라고 안내하고, 이렇게 보낸 이벤트는 `isTrusted`가 false라고 적는다. 그래서 이 프로젝트는 탭 넘김, 책 영역의 `touch-action: none`, 조작 영역 크기 확인에 쓴다. 드래그 감각은 실기기에서 본다.
- Chromium CDP `Input.dispatchTouchEvent`로 신뢰된 터치를 보낼 수 있는지는 미검증이다.
- WebKit 모바일 에뮬레이션은 iOS Safari가 아니므로(0장) 더하지 않는다.

### three와 @types/three 버전 (제안)

저장소와 레지스트리 사실:

- stickerbook `package.json`에는 three가 없다. `apps/blog/package.json`은 `"three": "^0.186.1"`이고 `pnpm-lock.yaml`에는 three@0.186.1 하나만 있으며 @types/three는 없다.
- npm 레지스트리(2026-11-13 조회): three latest는 0.187.0(2026-10-30)이다. three 패키지에는 타입 선언 필드가 없다. @types/three 0.187.0이 같은 날 나왔다.
- npm semver에서 `^0.187.0`은 0.187.x만 허용한다.
- @react-three/fiber 9.8.2의 peer는 react와 react-dom `>=19 <19.4`, three `>=0.156`이다. 앱은 react `^19.3.1`이고 lock은 19.3.1, npm latest도 19.3.1이라 지금은 맞는다.

제안:

- three와 @types/three를 정확한 버전 `0.187.0`으로 함께 고정하고, 올릴 때는 한 PR에서 같이 올린다. three는 r 번호마다 API가 바뀔 수 있고 @types/three 버전은 three r 번호를 따라간다. 정확 고정이면 둘의 짝을 package.json에서 바로 읽는다.
- blog의 0.186.1에 맞추지 않는다. blog는 react-force-graph-3d 계열과 `three/webgpu` 스텁(`apps/blog/next.config.mjs`) 때문에 올릴 때 따로 확인할 것이 있다. 비용은 pnpm 저장소에 three 사본이 둘 생기는 것이고, 앱 번들은 서로 독립이다.
- @types/three는 devDependencies에 둔다. 0.187.0은 fflate, meshoptimizer, @tweenjs/tween.js, @dimforge/rapier3d-compat를 의존성으로 끌어와 설치는 늘지만 번들에는 들어가지 않는다.
- 버전을 올리면 해당 스파이크의 실기기 확인을 다시 한다.
- R3F는 재미 트랙이라 기본 경로에 넣지 않는다. 넣는다면 그때 peer를 다시 본다. 저장소 react를 19.4로 올리면 9.8.x peer 범위를 벗어난다. 저장소에 `.npmrc`가 없고 `pnpm-workspace.yaml`에 peer 엄격 설정이 없어 경고로만 나올 것으로 본다(추정).
