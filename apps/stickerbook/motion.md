# 같은 페이지를 유지하는 책 넘김

2026-10-27. 사용자는 클릭·드래그 시작 시 글자가 줄고 해상도가 낮아지는 현상을 다시 지적했다. 펼친 책은 항상 좌우 두 페이지이며, 넘기는 오른쪽 장의 뒷면은 다음 펼침의 왼쪽 페이지라는 모델도 명확히 했다.

## 원인과 판단

정지 화면은 HTML/CSS, 움직이는 종이는 수동 Canvas 2D 그림을 WebGL에 올린 별도 표현이었다. CSS의 EXIF는 `clamp(10px, 2.5cqw, 12px)`인데 Canvas는 논리 폭 480에서 항상 12px로 그렸다. 폭 350에 그리면 8.75px이 되어 CSS의 최소 10px과 다르다. 텍스처도 고정 960×1240, WebGL DPR은 최대 2여서 화면 밀도에 따른 차이가 생겼다.

지난 수정은 진행률 0에서 원래 DOM을 유지하고 전환을 짧게 연결했다. 누른 채 가만히 있을 때의 픽셀 일치는 확인했으나, 움직이기 시작했을 때 표현 자체가 바뀌는 원인은 해결하지 못했다.

| Before                      | After                                               | 이유                                                         |
| --------------------------- | --------------------------------------------------- | ------------------------------------------------------------ |
| HTML → 수동 Canvas → WebGL  | 같은 AlbumPage HTML/CSS 유지                        | 글자·사진·스티커·테이프를 두 방식으로 그리지 않는다.         |
| 고정 크기 텍스처와 DPR 제한 | 실제 페이지 너비의 HTML을 clip-path로 잘라 배치     | 브라우저의 폰트 렌더링과 CSS 최소 글자 크기를 계속 사용한다. |
| 페이지 전체를 텍스처로 변형 | 평평한 앞·뒷면은 크기 1, 좁은 접힘만 12개 띠로 변형 | 종이의 말림 때문에 눌리는 구간과 전체 글자 축소를 구별한다.  |
| 작은 화면은 한 페이지       | 모든 화면에서 좌우 펼침                             | 02쪽의 뒷면이 03쪽인 물리적 연결을 유지한다.                 |
| 완성 높이로 compact 판정    | 실제 가용 높이로 판정                               | 세로 휴대폰에서 작아진 펼침의 스티커·EXIF가 사라지지 않는다. |

텍스처 해상도 증가와 HTML 캡처도 검토했다. 전자는 글자 규칙의 차이가 남고, 후자는 비트맵 전환과 캡처 준비가 남아 선택하지 않았다. [Three.js의 Canvas 텍스처 설명](https://threejs.org/manual/pages/canvas-textures.html)과 [MDN clip-path](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/clip-path)를 참고했다.

## 종이와 입력

- `01–02`에서 앞으로 넘기면 02쪽 앞면 / 03쪽 뒷면이 한 장이다. 01쪽은 그대로, 아래에는 04쪽이 기다리며 최종 펼침은 `03–04`다. 역방향은 03쪽 앞면 / 02쪽 뒷면을 뒤집는다.
- 모든 페이지 사본은 실제 한쪽 페이지와 같은 CSS 너비다. 사본은 `inert`·`aria-hidden`이고, 읽기와 조작은 원래 두 페이지가 담당한다. 전환 중 원래 페이지는 조작을 잠시 막는다.
- 잡은 높이·수직 당김에 따라 접는 선의 방향이 달라진다. 이 선을 기준으로 원통 말림을 근사한다. 위·아래 모서리부터 접을 수 있지만 종이 전체의 탄성·중앙만 찌그러지는 변형을 푸는 물리 시뮬레이션은 아니다.
- 평평한 뒷면은 반사된 종이 좌표와 뒷면의 읽기 방향을 합성해 글자가 거울상이 되지 않게 한다. 접힘 띠에만 음영을 넣는다. 띠 경계의 미세한 틈은 0.3px 겹침으로 줄이고 명암은 띠 사이에 이어지는 그라데이션을 사용한다.
- 한쪽 페이지 너비 두 배의 이동이 전체 뒤집기에 대응한다. 진행률 0.25 초과 또는 0.06 초과와 수평 속도 0.45px/ms 초과면 완주한다. 수직 이동만으로는 완료하지 않는다.
- 놓은 뒤 160–280ms ease-out으로 완주/복귀한다. 별도 렌더러 준비나 준비 후 교체는 없다. 키보드·reduced-motion·아주 낮은 compact 구획은 즉시 전환한다.
- 회전·레이아웃 변경·Escape·pointer cancel로 취소한다. 스티커 상태, 44px 터치 영역, 사진 확대와 포커스 복귀는 유지한다.

## 검증과 한계

- 타입·lint·format·단위 41개·coverage·빌드·앱 범위 Knip 통과. 기존 WebGL 수명/텍스처 테스트는 제거하고 DOM 면 연결과 기하학 테스트로 교체했다.
- Chromium·Firefox·WebKit E2E 29 passed / 4 skipped. skip은 실제 구획·터치 타이밍을 쓰는 Chromium CDP 전용 2개 시나리오의 나머지 브라우저 실행이다.
- 진행률 0.015·0.3·0.65·0.96·1에서 정방향·역방향, DPR 1 데스크톱과 DPR 3 모바일의 글자 크기·사진 프레임 너비·뒷면의 크기/방향을 자동 검사한다. WebGL을 막아도 같은 렌더러가 동작한다.
- 별도 Chromium 스크린샷 비교: 1440px/DPR 2, 390px/DPR 3, 320px/DPR 3에서 움직이기 시작한 진행률 0.015의 아직 접히지 않은 EXIF 영역은 이동 전과 픽셀 차이 0이었다. 전체 착지 화면은 모서리 표시와 그림자/변형 경계의 안티앨리어싱 차이가 있어 픽셀 동일성을 주장하지 않는다.
- 독립 verifier가 390×844 DPR 2, 진행률 0.418에서 원본과 각 조각의 EXIF 10px·사진 프레임 141px 일치, 순방향/역방향 연결, 거울상 없음을 확인했다. 곡면 띠 경계의 사진 변형은 여전히 기하학적 근사다.
- 작은 320px 펼침의 페이지별 스티커 2–3개·44px 터치 영역·중심점 클릭 가능, 확대/포커스·스티커 상태·취소·회전·힌지 회피를 검사했다. JPG 6개 SHA 해시는 수정 전과 같다.

브라우저는 변형된 HTML을 내부적으로 합성하므로 회전·기울임 구간의 안티앨리어싱까지 모든 환경에서 동일하다고 보장하지 않는다. 이번 교체는 앱이 별도 저해상도 비트맵을 만드는 경로와 다른 폰트 규칙을 제거한다. 실물 폴더블·iPhone Duo·저사양 기기 프레임 성능은 별도 확인이 필요하다. JPG 사진은 변경하지 않는다.
