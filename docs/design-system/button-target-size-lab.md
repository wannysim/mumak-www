# 버튼 타깃 크기 비교

2026-10-20. PR #636의 admin 로그인 C loading 적용이 develop에 병합된 `360995ed`에서 시작했다. Storybook 비교 후 사용자가 실제 모바일에서 C를 선택했다(D-016). 이 최초 실습은 제품 크기 변경·공유 API 구현·단계 1 전체 완료를 포함하지 않았다. 이후 D-018에서 공유 IconButton과 Blog 헤더·GraphToolbar를 이전했다. 현재 범위는 [적용 현황](./support-matrix.md#7-인터랙션-적용-현황)을 따른다.

[Storybook 비교](http://127.0.0.1:6006/?path=/story/learning-button-target-size--compare&globals=locale:ko;theme:light). 실행은 `pnpm --filter blog storybook`. 시작 화면의 일곱 번째 링크로도 연다.

## 사용자 문제와 비교 조건

버튼의 보이는 표면과 실제 클릭·터치 영역은 다를 수 있다. 작은 아이콘 버튼을 누르기 쉬워지려면 표면을 키워야 하는지, 보이지 않는 영역만 넓혀도 되는지 관찰한다. 실습에서 정답이나 제품 기본값을 먼저 선택하지 않는다.

| 안            | 보이는 표면 | 실제 타깃 | 구성                                                      |
| ------------- | ----------- | --------- | --------------------------------------------------------- |
| A 현재 크기   | 32×32       | 32×32     | 실제 공유 Button의 outline / icon                         |
| B 함께 확대   | 44×44       | 44×44     | 실제 Button의 크기만 실습에서 확대                        |
| C 영역만 확대 | 32×32       | 44×44     | 실제 Button의 투명한 타깃 안에 outline 스타일의 32px 표면 |

단위는 CSS px다. 아이콘은 모두 16×16, 중심 간격은 52px로 고정하고 데스크톱에서는 세 안의 버튼 행 높이도 맞춘다. 현재 A는 전체 제품의 모든 버튼 크기를 대표하지 않고 `size="icon"`의 기준이다. C의 안쪽은 비상호작용 span이며 독립 버튼이나 중첩 타깃이 아니다. 포커스는 세 안 모두 실제 버튼 경계에 표시한다.

- 이전·저장·다음 세 버튼은 마지막 실행 이름과 총 실행 횟수만 갱신한다. 데이터 저장이나 페이지 이동은 없다.
- 중심 위치를 고정해 A/C의 같은 위치에서 타깃 크기를 비교하고 B/C의 같은 타깃 크기에서 표면 크기를 비교한다. 자연스러운 전체 레이아웃 밀도를 판단하는 실험은 아니다.
- A의 타깃 사이 간격은 20px, B/C는 8px다. C도 44px 레이아웃 공간을 확보하므로 보이지 않는 영역이 이웃 타깃을 덮지 않는다. 제품에 적용할 때는 실제 배치의 공간 비용을 다시 봐야 한다.
- 영역 표시를 켜면 실제 버튼 안쪽에 점선과 반투명 표면을 겹친다. 표시는 pointer 이벤트를 받지 않으며 타깃 크기·실행 동작을 바꾸지 않는다.
- C의 Dark 기본·hover 표면도 A/B의 outline 색과 맞춘다. 투명한 바깥 영역은 hover 중에도 채우지 않는다.
- Light/Dark, ko/en은 기존 전역 메뉴를 사용한다. 테마 변경은 실행 횟수·영역 표시를 유지한다.

## 관찰 순서

1. 영역 표시를 끄고 가운데 저장, 좌우 버튼을 번갈아 누른다. 정확히 겨냥해야 하는 느낌과 이웃 버튼을 누를 우려를 비교한다.
2. 영역을 켠 뒤 가장자리를 누른다. C가 보이는 표면 밖에서 반응하는 것이 예상과 일치하는지 확인한다.
3. Tab·Shift+Tab으로 이동하고 Space·Enter로 실행한다. 포커스가 실제 타깃을 둘러싸는지 본다.
4. Light/Dark와 좁은 화면을 비교한다. 실제 터치 기기에서 확인한 판단은 마우스·에뮬레이션 관찰과 구분한다.
5. 사용자가 선호와 이유를 말한 뒤 누락·비용·되돌릴 조건을 검토한다. 그 전에는 결정 로그에 채택을 기록하거나 공유 Button을 바꾸지 않는다.

## 기준과 한계

[WCAG 2.2 SC 2.5.8 (AA)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)은 24×24 CSS px 최소 타깃 크기와 간격·인라인 등의 예외를 다룬다. [SC 2.5.5 (AAA)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)는 44×44 CSS px 강화 기준이다. 44px가 모든 버튼의 AA 의무라는 뜻은 아니다. 기준의 크기와 실제 조작 편의성을 구분한다.

실습은 성공한 실행만 센다. 실패한 시도나 사용자의 의도를 추정하지 않으므로 오탭률·정확도 점수·후보 순위를 계산하지 않는다. 자동 터치는 이벤트 전달을 검증하며 실제 손가락 면적·떨림·기기별 편의성을 대신하지 않는다. 경계 밖 터치는 브라우저의 보정 동작에도 영향을 받을 수 있다.

## 검증 범위

`stories/button-target-size.spec.ts`는 실제 DOM 크기·아이콘 크기·중심 간격·비중첩, 같은 위치에서의 A 미실행과 B/C 실행, 영역 표시 후 경계·간격 클릭, 네이티브 키보드·포커스, 테마 전환 상태 유지, C의 투명 영역 터치, Light/Dark의 표면색 일치, ko/en × Light/Dark 320px 화면과 axe를 검사한다.

첫 검사에서 Light 안내 문구의 `text-muted-foreground` / `bg-muted` 조합이 4.34:1로 실패했다. 해당 문구가 기존 본문색을 상속하도록 수정했다. 디자인 리뷰에서는 C의 Dark hover 배경과 표면색이 비교 조건과 다른 것을 찾아 수정하고 브라우저 검사에 포함했다. 전역 token은 변경하지 않았다.

제품 라우트와 공유 Button 소스는 변경하지 않는다. 이번 UI의 실행 검증은 Storybook 브라우저 검사와 정적 Storybook build가 담당한다. 사용자 선호는 아래 실제 모바일 관찰로 기록했다. 모든 제품 배치의 터치 편의성과 스크린리더 발화는 미검증이다.

검사 중 6006 개발 서버를 다시 띄운 실행에서는 기존 manager 기반 테마 테스트들이 iframe의 첫 요소를 찾지 못했다. 두 서버는 같은 설정 경로에 따른 manager 출력·Vite 캐시를 공유한다. 해당 실행을 중단하고 개발 서버를 종료한 뒤, 정적 build와 6007 전체 검사를 순서대로 실행해 환경을 분리했다. 이 문제 때문에 제품 코드나 테스트 제한시간을 바꾸지는 않았다.

## 사용자 선택과 후속 적용 경계

2026-10-20, 사용자는 B를 제외하고 A/C를 비교한 뒤 실제 모바일 기기로 C를 선택했다. 보이는 크기를 유지하면서 조작 영역을 넓히는 점을 접근성을 고려한 좋은 패턴으로 평가했다. 기기 모델·브라우저와 오탭률은 기록하지 않았다. 자동 터치 검사와 사용자 직접 관찰을 구분한다.

이후 사용자는 검색 한 곳만 고치면 다른 곳과 파편화될 수 있으며 앞선 개선도 점검해야 한다고 지적했다. 제품 변경 전에 포커스·색·loading·타깃의 [공통 계약](./interaction-contracts.md)과 [적용 현황](./support-matrix.md#7-인터랙션-적용-현황)을 정리했다. C를 여러 소비처에 인라인 복제하지 않고 공통 표현과 실제 배치를 함께 검토한다. 다음 작업은 [NEXT.md](./NEXT.md)에서 관리한다.
