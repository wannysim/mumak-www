# 제품 원칙 (초안)

> P-1은 키보드 조작과 현재 위치 식별, P-2는 브랜드 기준색과 테마별 변형, P-3은 글의 실제 성숙도와 성장 단계, P-4는 모바일 본문의 읽기 밀도에 대한 본인 판단으로 정리했다.
> 기존 구현·측정 기록과 본인 관찰, 앞으로 적용할 판단 예시를 구분한다. 시스템 필요성 설명과 자기 비평은 아직 남아 있다.

원칙은 아래 4개로 정리한다. 원칙의 조건은 하나다: **실제 UI 결정을 통과시키거나 기각시킬 수 있어야 한다.** 통과·기각 예가 없는 문장은 원칙이 아니라 감상이다.

---

## P-1. 키보드로도 같은 일을 할 수 있고, 현재 위치를 알 수 있어야 한다

마우스로 클릭하거나 입력할 수 있는 기능은 키보드로도 사용할 수 있어야 한다. 이동할 때는 어느 링크나 버튼, 입력창을 조작하는지 바로 알아볼 수 있어야 한다.

### 본인 판단과 관찰 — 2026-09-17

- **본인 기준:** 마우스로 클릭하거나 입력할 수 있는 요소는 키보드로도 이동하고 상호작용할 수 있어야 한다.
- **직접 관찰:** 메인 페이지에서 Tab으로 이동하고 상호작용했을 때, 본인이 확인한 범위에서는 모두 동작했다. 현재 포커스 위치도 바로 알아볼 수 있었다. 테스트 URL, 브라우저, 테마와 개별 요소 목록은 기록하지 않았다. 에이전트의 재현 검증은 아니다.
- **본인 판단에서 정리한 사용자 문제:** 키보드로 글을 탐색하거나 입력하려는 사람이 마우스로만 조작할 수 있는 요소를 만나면 원하는 작업을 이어갈 수 없다. 현재 조작 위치를 알아보기 어려워도 다음 동작을 판단하기 어렵다. 이번 메인 페이지 관찰에서는 이런 막힘을 발견하지 않았으며, 앞으로도 방지하려는 문제다.
- **기준 보완:** WCAG 2.1.1은 기능을 키보드로 수행할 수 있는지를 다룬다. 모든 클릭 영역을 각각 Tab 순서에 넣어야 한다는 뜻은 아니다. 탭 목록·라디오 그룹처럼 Tab으로 진입한 뒤 방향키로 내부 항목을 이동하는 패턴도 있다. 포커스 위치를 알아볼 수 있는지는 별도로 확인한다 ([Keyboard](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html), [APG keyboard interface](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/), [Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)).
- **설계 관점:** 요청한 `apple-design` 스킬의 입력 방식에 대한 유연성과 조작 피드백 관점을 참고한다. 구체적인 웹 키보드 동작 기준은 위 W3C 자료로 대조했다.

### 통과시킨 결정

- **태그 칩을 `<span>` + `onClick`에서 실제 `<a>`로 바꿨다.**
  `widgets/post-card/ui/post-tags.tsx:12` — "키보드·스크린리더로 도달/활성화가 불가능했다(마우스 전용)."
  주석이 남아 있다는 건 이 판단을 되돌리지 말라는 표시다.
- **카드 전체를 링크로 감싸는 대신 stretched-link 패턴을 썼다.**
  `shared/ui/content-card.tsx` — 카드를 통째로 `<Link>`로 감싸면 안의 태그 anchor가 중첩 interactive가 되어 axe `nested-interactive`를 위반한다. 제목만 실제 링크로 두고 `after:absolute inset-0`로 표면을 덮었다. 태그는 `z-10`으로 올려 독립적으로 포커스된다.
  "카드 어디나 클릭 가능"이라는 편의를 접근성 위반 없이 얻은 사례다.
- **이어 읽기 목록은 행 전체가 링크다.**
  `widgets/next-reading/ui/next-reading.tsx:36` — "제목만 링크로 두면 타깃이 한 줄 높이로 얇아진다."
- **그래프 범례 스와치를 32px로 잡았다.**
  `features/graph/ui/graph-legend.tsx:62` — "size-8 = 24px 최소치(WCAG 2.5.8)에 여유를 둔 32px."

### 기각 기준과 남은 검토

- **기각 예시: 키보드로 조작할 수 없는 태그를 다시 도입한다.** `<span>` + `onClick`만으로 이동을 구현하면 P-1에서 지키려는 동등한 조작 경로를 잃는다. 위에서 고친 사례의 재발을 막는 기준이다.

- **light 모드 포커스 링이 2.82:1이다.** 비텍스트 최소치 3:1에 미달한다 (`audit.md` §3-1).
  전역 `*:focus-visible` 규칙과 `ContentCard` ring이 전부 이 색을 쓴다. 기존 측정은 포커스 표시의 대비가 부족하다는 근거이며, 모든 사용자가 표시를 보지 못한다는 뜻은 아니다. 이번 메인 페이지의 이동·조작 성공만으로 기존 대비 측정이 해소되지는 않는다.
  axe 7개 시나리오가 전부 통과하는데도 남아 있다. 자동 검사가 안 잡는 축이라서다.
- **본문 첫 카드까지 Tab 14회.** `/ko/blog` desktop 기준. skip link가 있지만 실제 비용이 이 숫자다.
  줄일 수 있는지, 아니면 이게 헤더 기능의 정당한 대가인지 판단이 필요하다.

## P-2. 브랜드 기준색을 두고, 용도와 테마에 맞게 읽기 쉬운 색을 적용한다

브랜드를 대표하는 기준색은 하나로 두되, 실제 UI에는 용도와 light/dark 테마에 맞는 변형 값을 적용한다. 링크 글자, 버튼 배경, 버튼 위 글자, 포커스 표시가 각각 놓이는 배경과 구분되는지 확인한다. 컴포넌트는 용도별 토큰을 사용하고, 테마가 그 토큰의 실제 값을 결정하도록 한다.

### 본인 판단과 근거 — 2026-09-17

- **본인 기준:** 브랜드 메인 컬러는 하나로 잡고, 접근성에 따라 dark/light 토큰으로 나눠 상황에 맞게 적용한다.
- **본인 판단에서 정리한 사용자 문제:** 글이나 링크를 읽으려는 사람이 배경과 구분하기 어려운 브랜드색을 만나면 내용을 읽거나 이동할 곳을 찾기 어렵다. 브랜드의 인상을 유지하면서도 테마별로 읽고 조작할 수 있는 색을 제공한다.
- **공식 사례:** Material의 공개 토큰 예시는 같은 `md.sys.color.primary`를 light에서 `primary40`, dark에서 `primary80`에 연결한다. Atlassian도 용도별 색 토큰과 light/dark 테마를 구분한다 ([Material token example](https://github.com/material-foundation/material-tokens/blob/main/tokens.md), [Atlassian color](https://atlassian.design/foundations/color)).
- **저장소의 현재 기반:** `packages/ui/src/styles/globals.css`는 이미 `--primary`와 `--accent-foreground`를 light/dark에서 다른 값으로 정의한다. 브랜드 기준색 하나에서 모든 값을 자동 생성하는 구조와는 구분한다.
- **후속 설계 범위:** 팔레트는 사용할 색 값, semantic token은 용도, 테마는 용도별 값의 대응이다. 실제 소비처가 있는 역할부터 정리하고, 단계 0에서는 새 토큰이나 생성 파이프라인을 추가하지 않는다. 값이 파생됐다는 사실만으로 대비가 보장되지는 않으므로 실제 배경·상태와 함께 검증한다.

### 통과시킨 결정

- **링크 색이 `--primary`가 아니라 `--accent-foreground`다.**
  `shared/ui/wikilink.tsx:17`, `widgets/linked-notes-section/ui/linked-notes-section.tsx:46` — "3.48:1로 AA 미달이라 같은 hue의 accent-foreground(7.92:1 / 11.58:1)를 쓴다."
  같은 색조를 유지하면서 명도만 내렸다. 브랜드를 버린 게 아니라 역할에 맞는 값을 골랐다.
- **카드 제목도 hover에 `accent-foreground`를 쓴다.**
  `ContentCard`의 20px / 600을 large-scale text 예외로 해석하지 않고 normal text 4.5:1 기준을 적용했다. 같은 surface recipe를 쓰는 `GardenOverview`의 16px / 600 제목도 함께 고쳤다. 실제 hover 대비는 light 7.66:1, dark 10.70:1이다 (`decision-log.md` D-007).
- **그래프 budding 색을 앰버에서 어둡게 내렸다.**
  `features/graph/lib/graph-config.ts:18` — "라이트 앰버(#e8a317)는 흰 배경 대비 2.17:1이라 비텍스트 최소치(3:1)에 미달했다. 8px 스와치가 색-라벨 매핑의 유일한 전달 수단이므로 명도를 내려 3.82:1로 맞춘다."
  **"이 색이 유일한 전달 수단인가"**를 먼저 물은 게 핵심이다. 그 답에 따라 기준선이 달라진다.
- **notes 카테고리에 고유 색조를 줬다.**
  같은 파일 — 중성 회색 fallback을 쓰다 보니 범례에서 태그 노드와 구분되지 않았다.

### 기각시켜야 하는 것 (지금 살아 있음)

- **`--ring` 2.82:1** — P-1과 같은 항목이지만 원인은 이쪽이다. 색값 자체가 기준에 못 미친다.

추가 기각 예시: **브랜드색을 통일한다는 이유로 light 본문 링크를 대비가 부족했던 `--primary`로 되돌린다.** 현재 발생한 변경이 아니라, 역할별 색 선택을 되돌리는 결정을 막는 기준이다.

### 이 원칙이 만드는 빈틈

`--primary`를 텍스트에 쓰면 안 된다면, **"링크 텍스트 색"에 해당하는 semantic 이름이 없다는 게 문제다.** 지금은 여러 소비자가 "primary 말고 accent-foreground"를 직접 기억해야 한다.
단계 1의 semantic token 후보: 값이 아니라 **역할 이름**이 빠져 있다.

## P-3. 글의 실제 성숙도와 완성도를 성장 단계로 보여준다

독자가 글의 성장 단계를 보고 어느 정도 다듬어진 내용을 기대할 수 있는지 알게 한다. 단계는 글의 현재 상태에 맞춰 표시하며, 목차의 존재뿐 아니라 제목·목차·본문의 연결과 읽기 쉬움을 함께 판단한다.

### 본인 정의와 원칙 재검토 — 2026-09-17

- **본인 정의:** 성장 단계는 글의 성숙도와 완성도를 보여주는 척도다. 가장 낮은 단계는 아이디어만 있고 제대로 작성하거나 다듬지 않은 초본이며, 위로 갈수록 완성되어 간다.
- **현재 단계와 대응:** `apps/blog/AGENTS.md`의 `seedling`(초기 아이디어·미완성 메모), `budding`(발전 중·구체화된 생각), `evergreen`(성숙하고 다듬어진 노트) 정의와 같은 방향이다.
- **새싹으로 올리는 본인 기준:** 글이 적어도 문단별로 나뉘고 `index`를 갖춘 상태다. 여기서 `index`는 목차로 해석했다. 독자가 목차로 전체 구성을 파악하고 문단별로 내용을 읽을 수 있는 수준이며, 근거·예시의 완비를 별도 조건으로 정하지는 않았다.
- **상록수로 올리는 본인 기준:** 목차가 제대로 갖춰져 있고, 그에 맞춰 문단이 잘 나뉘며, 제목에 맞는 내용이 읽기 쉽게 정리된 완성본이다. 새싹과의 차이는 목차·문단의 존재를 넘어 구성과 내용이 충분히 다듬어졌는지에 있다.
- **본인 판단에서 정리한 사용자 문제:** 독자가 아이디어 초본과 다듬어진 글을 구분하지 못하면 글에서 어느 정도의 설명과 완성도를 기대할지 판단하기 어렵다.
- **기존 근거의 한계:** `evergreen`이 0건이라는 사실만으로 성장 단계가 관리되지 않는다고 단정할 수는 없다. 아직 그 수준까지 다듬은 글이 없을 수도 있다. 기존 홈 비노출 정책과 성장 단계의 의미는 구분하며, 이번 정의만으로 노출 위치 변경을 결정하지 않는다.

### 단계별 기대

| 단계               | 본인이 정한 글의 상태                                                    |
| ------------------ | ------------------------------------------------------------------------ |
| 씨앗 `seedling`    | 아이디어만 있거나 아직 작성·정리가 덜 된 초본                            |
| 새싹 `budding`     | 문단과 목차를 갖춰 구조가 잡힌 글                                        |
| 상록수 `evergreen` | 목차와 문단 구성이 잘 맞고, 제목에 맞는 내용이 읽기 쉽게 다듬어진 완성본 |

### 이 기준으로 통과·기각할 예시

아래는 본인 기준에서 도출한 판단 예시다. 실제 글의 상태를 이번에 변경하거나 검증했다는 뜻은 아니다.

- **통과:** 아이디어 메모를 씨앗으로 표시해 독자가 초본임을 알고 읽게 한다.
- **통과:** 제목에 맞는 내용을 목차와 문단으로 읽기 쉽게 다듬은 글을 상록수로 표시한다.
- **기각:** 목차는 있지만 내용이 비거나 문단 연결이 미완인 글을 목차가 있다는 이유만으로 상록수로 표시한다.
- **기각:** 글이 길거나 오래됐다는 이유만으로, 구성과 읽기 쉬움을 확인하지 않고 단계를 올린다.

기존 홈 비노출 정책은 `apps/blog/AGENTS.md`에 남아 있다. 성장 단계 정의를 구체화한 이번 작업에서 배지의 노출 위치는 바꾸지 않았다.

## P-4. 작은 화면에서도 본문의 줄과 문단을 편하게 따라 읽을 수 있게 한다

모바일에서 여러 줄의 본문이 빽빽한 덩어리로 느껴지지 않도록 읽기 간격을 조정한다. 본인이 더 크게 느낀 불편은 같은 문단 안의 줄 밀도이므로 행간을 먼저 비교하고, 남는 자간 불편을 이어서 확인한다.

### 본인 관찰과 확인 범위 — 2026-09-17

- **본인 관찰:** 모바일 글 상세 본문은 글자 사이와 여러 줄의 밀도가 모두 촘촘하게 느껴지며, 특히 같은 문단 안의 여러 줄이 빽빽한 것이 더 불편했다. PC에서는 그 느낌이 덜하다. 메인 페이지의 카드 목록이 아니라 글 상세 본문에 대한 관찰이다.
- **사용자 문제:** 모바일 독자가 본문을 읽을 때 한 문단의 여러 줄이 촘촘한 덩어리로 느껴져 읽기 부담이 생긴다. 행간 비교를 우선할 근거가 생겼으며, 실제 변경의 효과와 남는 자간 불편은 아직 확인하지 않았다.
- **현재 코드:** `apps/blog/mdx-components.tsx`의 문단은 `my-4 leading-relaxed`이며 모바일·PC 분기가 없다. 기본 Tailwind 값으로 문단 위아래 여백은 `1rem`, 줄 높이는 글자 크기의 `1.625`배다. 본문 글자 크기는 상속하며, 기본 16px 환경이라면 줄 높이는 26px이다. 문단 자간을 별도로 좁히는 설정은 확인되지 않았다.
- **별도 확인:** 상세 페이지에는 `prose`가 있으나 공유 CSS에 typography 플러그인 등록이 없고, 현재 PostCSS 설정으로 CSS를 생성했을 때 `.prose` 규칙은 0개였다. 다만 MDX 요소가 간격을 직접 지정하므로 본문 간격 자체가 없는 것은 아니다. 플러그인 활성화를 이번 관찰의 해결책으로 단정하지 않는다.
- **검증 한계:** 실제 기기의 computed style이나 특정 글 화면을 측정한 결과는 아니다. URL·기기·브라우저는 미확인이다.

### 비교 제안 — 최종 수치와 적용 여부는 미정

1. 동일한 한국어 본문으로 현재 설정과 줄 높이 `1.75`를 비교한다. 기본 글자 크기 16px 기준 26px → 28px이며, 자간·글자 크기는 먼저 유지해 줄 간격의 영향을 구분한다.
2. 행간 비교 뒤 글자 사이의 답답함이 남는지 확인하고 자간을 별도로 비교한다. 자간을 넓히면 줄바꿈도 늘어나므로 행간 변경 효과와 구분한다.
3. 문단 경계가 여전히 흐리면 문단 여백 `1rem`과 `1.5rem`을 비교한다. 글자 자체가 작게 느껴지면 별도 안에서 `1rem`과 `1.125rem`을 비교한다. 문단 여백만으로 같은 문단 안의 줄 간격 문제를 해결했다고 보지 않는다.
4. 같은 글의 mobile/desktop, light/dark와 확대·텍스트 간격 변경을 확인한다. WCAG 1.4.12는 사용자가 간격을 변경해도 내용·기능이 손실되지 않아야 한다는 기준이며, 그 값을 기본 스타일로 강제하는 규칙은 아니다 ([Text Spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)).

이 수치는 비교를 위한 제안이다. 본인 관찰을 원칙으로 정리했으며, 본문 스타일의 최종 값이나 새 type/spacing token 도입을 결정하지 않았다. 실제 비교·구현은 단계 2의 본문 시각 기준 작업으로 연결한다.

### 이 기준으로 통과·기각할 예시

아래는 후속 비교에서 사용할 판단 예시이며, 구현·실기기 검증 결과가 아니다.

- **통과:** 같은 모바일 본문에서 행간만 다르게 비교해 여러 줄을 따라 읽기 편한 안을 선택한다.
- **통과:** 행간을 조정한 뒤에도 남는 글자 사이의 답답함을 실제 글꼴과 줄바꿈으로 확인해 자간을 별도로 조정한다.
- **기각:** 문단 사이 여백만 늘리고 같은 문단 안의 빽빽함이 해결됐다고 판단한다.
- **기각:** PC에서 편하다는 이유로 모바일 본문의 읽기 불편을 검토 없이 넘긴다.

## 원칙끼리 부딪힐 때

원칙을 실제 화면에 적용할 때 함께 검토할 지점이다.

**P-2(용도·테마별 색)와 시각적 일관성.** 본인은 브랜드 기준색을 유지하면서 테마와 접근성에 맞게 변형하는 방식을 선택했다. `--accent-foreground`처럼 용도에 맞는 값을 쓰되, 링크로 알아보기 쉬운지는 **밑줄·위치·문맥**까지 함께 확인한다. 대비 확보만으로 링크의 발견 가능성까지 검증된 것은 아니다.

**P-1(도달) vs 밀도.** 타깃을 키우면(행 전체 링크, 32px 스와치) 목록이 성글어진다. `NextReading`이 카드 대신 nav + ul을 쓴 이유가 여기 있다 — "본문을 다 읽은 뒤 붙는 블록이라 목록 페이지와 같은 밀도로 쌓으면 무겁다."

P-1·P-2는 조작과 식별, P-3은 콘텐츠의 상태에 대한 기대, P-4는 화면에서 본문을 따라 읽는 경험을 다룬다. 이전 초안의 고정 우선순위는 본인이 확정한 결정이 아니므로 적용하지 않는다.
